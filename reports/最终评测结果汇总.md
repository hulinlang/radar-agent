## 一、一句话说清这个项目

给一个 20 亿参数的小模型（Qwen3-VL-2B-Instruct）配一套「开卷考试」的外挂：
把 1 本教材（363 页）+ 35 篇英文论文（501 页）+ 21 篇毫米波文档切成 **3693 张卡片**，
做成可查的索引；提问时翻出最相关的几张，让模型照着答，并且能自己决定
「该翻资料还是该按计算器」。

### 2.1 语料与切分

### 2.2 检索能力（174 道教材题）

| 指标 | 数值 |
|---|---|
| 前 1 张就翻对 | 47.7% |
| **前 5 张里翻到** | **75.3%** |
| 前 10 张里翻到 | 83.3% |
| 排序质量（MRR@10） | 0.590 |

⭐ **关键结论**：加入 1639 条英文文献后，教材题召回**零损失**（全库 vs 教材-only 的 MRR 差 0.001）。
当初担心的「文献挤占 top-k」没有发生 → 三源统一入库是安全的。

### 2.3 跨语言（33 道中文题 → 英文论文）

| | 全部一起翻 | 只翻英文论文 |
|---|---|---|
| 前 5 张里翻到 | 24.2% | 33.3% |
| **前 10 张里翻到** | 39.4% | **63.6%** |

⚠️ 两层原因并存，别只认一个：
1. **中文语料抢位置**——屏蔽中文后 R@10 从 39% 跳到 64%；
2. **跨语言本身有上限**——即使只翻英文，R@10 也只有 63.6%。

### 2.4 工具调用（205 道题，工具清单交给模型）

| 指标 | 数值 |
|---|---|
| 该用工具时会用 | **97.0%** |
| **挑对工具**（计算器 vs 检索） | **94.5%** |
| 计算题 | **调用率 100% ／ 选对 100%** |
| **常识题瞎调**（1+1、水的化学式…） | **0.0%** ✅ |

对照组 5 条常识题全部直接答，没去翻雷达教材。

### 2.5 答题质量（200 道冻结题，不给任何工具）

| 指标 | 基座 | tool5 | **tool6** |
|---|---|---|---|
| 全部 F1 | 0.120 | 0.319 | **0.322** |

## 三、端到端：开了检索到底有没有用（P7，200 题）

这是本项目**最重要也最诚实**的一组数字。

### 3.1 整体

| | A 什么都不给 | B 完整系统 |
|---|---|---|
| 综合得分 | **0.370** | 0.295（−0.075） |
| 内容相似度 F1 | 0.287 | 0.274（基本持平） |
| **该说"不知道"时** | **94.7%** | 78.9%（**−15.8pp**） |
| 引用出处编号 | 0 个 | **130 个，坏引用 0** ⭐ |
| 平均耗时 | 5.2 s | 22 s |

⚠️ **结论是负面的**：开检索后最终答案没有变好，且模型变得更不肯说"不知道"
（检索几乎总能翻出点东西，它就认为"有依据"）。
**唯一确定性收益是引用可溯源**——130 个编号全部真实存在，零编造。

### 3.2 计算题——改进前后对照（这是本次改造的成果）

| 版本 | 计算器接口 | calc 得分 | 与"不给工具"基线（0.700）的差距 |
|---|---|---|---|
| `tool5` | 传 **公式名 + 参数名** | 0.400 | −0.333 |
| **`tool6`** | **只传算术表达式** | **0.633** | **−0.067** |

**+0.233（+58%）**，差距缩到原来的五分之一。

### 3.3 ⭐ 失败模式被彻底改写（30 条逐条 trace 统计）

| 栽在哪 | tool5 | tool6 |
|---|---|---|
| **猜名字**（漏传/参数名猜错/臆造公式名/选错公式） | **13 条** | **0 条** ✅ |
| 压根没调工具 | 1 条 | **0 条** |
| 工具算对且采纳 | — | **14 条** ✅ |
| 工具算对但没采纳 | — | 2 条 |
| **式子写错 / 写不全** | — | **14 条** ❌ |

→ **失败从「接口把模型搞乱」变成了「模型自己写不全式子」**。
前者是设计问题、已修完；后者是 2B 模型的能力边界。这个转变本身就是改造成功的证明。

典型剩余失败：
```
题：RCS 从 1 增大到 50，作用距离变为几倍？  公式 (σ₂/σ₁)^(1/4)
它传给工具：50.0/1.0        ← 漏了 1/4 次方
自己补算：2.924（真值 2.659）
```

## 3.4 阶段 B：自研引擎与业务闭环（2026-10-08 补）

> 上面 3.1–3.3 是**应用层**的结论。此后项目补上了**引擎层**：从零手写 C++/CUDA 推理引擎
> （`radar-agent/cpp/`，~3000 行，里程碑 B0–B9），并把雷达 Agent 的生成后端
> 从 llama-server 换成它。完整方案与验收见 `docs/20`–`30`，里程碑总总结见 `docs/27`。

| 项 | 结果 |
|---|---|
| 端到端对拍（F16 同路线） | **440/440 token 与 llama.cpp 逐一相同**（阶段 B 总 DoD） |
| Q4 路线差异的比法 | teacher-forcing 一致率：自研 **49/50** vs llama.cpp 48/50 |
| decode 性能 | CUDA F16 **62.5** tok/s（llama.cpp 同 session 60.8 的 **103%**）｜**Q4-on-GPU 119.4 vs 116.9（102%）** |
| 显存 | Q4-on-GPU：**3.9 GB → 1.6 GB** |
| 批处理 | prefill **567–616 tok/s（4.8–5.3×，随 prompt 长度）**｜B=8 聚合 **469.6 tok/s（3.96×）**；逐 id 8/8 + 连续批 16/16 一致 |
| 服务化 | `radar-serve` 会话级 LCP 前缀复用，与全量重跑**逐字节相同** |
| **业务闭环** | 22 题（口径 v3）自研引擎 vs llama-server：**Δ = +0.0000**，16/22 输出逐字一致 |

⭐ **一句话**：自研引擎不是玩具——**它已经在跑真实的 RAG + Agent 链路，且分数与 llama.cpp 完全一致**。
项目由此从"应用层 demo"变成 **算子层 → 引擎层 → 系统层** 三层都有实测的闭环。

⚠️ **引用纪律**：上表的 llama.cpp 值（60.8 / 116.9）是 **B6/B7 同 session 对打**测得的；
阶段 A（A3）那次 session 测得的是 49.0 / 118.6。本项目实测**跨 session 漂移 17.3% ≫ 组内 0.6–3.6%**
（`docs/03` 已知局限 6）→ **绝对吞吐必须同 session 配对引用**。

## 四、三条如实记录的负面结论

1. **检索没能提升最终答案**（0.370 → 0.295）。检索本身能翻到（R@5 75.3%），
   但小模型拿到资料后组织得并不更好，且更不肯拒答。
2. **公式概念索引是负收益，已默认关闭**。按"名字"给公式建索引，
   实测会让整体 MRR 从 0.590 掉到 0.573——术语太宽 + 强制置顶挤掉了正常结果。
3. **改检索策略的收益都在个位数百分点，数据侧问题却是几十个百分点**。
   → 真正的杠杆在数据与模型侧，不在检索算法。（详见 `docs/11_项目讲解素材.md`）
