### 2.2 特殊 token —— 为什么必须实测而不是推断

| 项 | 实测值 |
|---|---|
| `eos_token` | `<|im_end|>`（id **151645**） |
| `pad_token` | `<|endoftext|>`（id **151643**） |
| `bos_token` | `None` |
| `tokenizer.vocab_size` | **151,643** |
| `len(tokenizer)` | **151,669** |
| `config.text_config.vocab_size` | **151,936** |

⚠️ **这里有一个三值不一致**（151,643 / 151,669 / 151,936），且**不报错**：

- `151,643` = BPE 基础词表大小；
- `151,669 − 151,643 = 26` = `tokenizer_config.json` 里注册的 `additional_special_tokens` / added tokens
  （`<|im_end|>`、`<|vision_start|>`、`<|image_pad|>`、`<tool_call>`、`<think>` 等）；
- `151,936 − 151,669 = 267` = **Embedding 矩阵里被 padding 出来的空行**（预留位，永远训不到）。

**工程后果**：
1. 统计 "tokens/s" 或做 vocab 对齐时，**用错哪个数都会偏**；
2. 做**词表裁剪 / 加新 token** 时必须知道有 267 行是空的；
3. 这也说明 `config.vocab_size ≠ len(tokenizer)` 是**常态而非异常**——凡涉及它俩的代码都要显式处理。

> 这条正是 §4.6「静默错误」清单里那一项：「`eos_token` 按版本惯例推断」的近亲。
> 本次没有靠推断，而是 `processor.tokenizer.eos_token` 直接读出来 + 断言钉死。

### 2.3 视觉 token 是怎么来的（可验算）

Qwen3-VL 把图像切成 patch，再在空间维度做 2×2 合并（`spatial_merge_size=2`）：

```
视觉 token 数 = (H / patch_size / merge_size) × (W / patch_size / merge_size)
             = (448 / 16 / 2) × (448 / 16 / 2) = 14 × 14 = 196
```

**实测交叉验证**：多模态用例的 `input_ids` 长度 = **220**，纯文本用例 = **17**。
差值为 203 ≈ 196（视觉 token）+ 7（模板/换行差异）。**量级吻合，说明视觉特征确实注入了**，
而不是"图像被忽略但程序照跑"这种静默失败。

> 这也是 §5.8 要求的**跨阶段契约断言**：`visual_token_count == expected_from_formula`
> 可以直接写成机器断言，防止"换了分辨率导致 token 数变了但没人发现"。

### 2.4 显存构成（实测，非估算）

| 阶段 | allocated | reserved | free | total |
|---|---|---|---|---|
| 加载前（桌面占用约 1.4 GB） | – | – | 6.94 GB | 8.00 GB |
| **加载模型后** | **3.96 GB** | 3.97 GB | **2.97 GB** | 8.00 GB |
| 文本生成峰值（974 token 输出） | – | – | – | 峰值 4.11 GB |
| 多模态生成峰值（196 视觉 token） | – | – | – | 峰值 4.05 GB |

**结论**：
- 权重 3.96 GB ≈ 2.128B × 2 B = 4.255 GB（十进制）→ 与实测吻合，**没有额外的加载开销**；
- **留给 KV Cache 的余量 = 2.97 GB**；
- 模型加载耗时 **2.55 s**（从磁盘读 4.25 GB ≈ 1.67 GB/s，说明是本地 SSD，非网络盘）。

**KV Cache 单 token 开销（本模型）：**
```
KV bytes/token = 2 × num_layers × num_kv_heads × head_dim × dtype_bytes
               = 2 × 28 × 8 × 128 × 2 = 114,688 B ≈ 112 KiB/token
```
→ 2.97 GB 余量约可容纳 **2.6 万 token 的 KV**。
→ 若单请求上下文 2048 token，理论上限约 **12 路并发**（未计框架开销与碎片，实际更低）。

> 对照 P4 的 RAG：一个 5-chunk 的上下文大约 1500–2500 token，**正好卡在单请求能跑、
> 但并发上不去的区间**。这是 P8 部署时必须实测的关键约束。

### 2.5 性能基线（§5.9 要求：延迟与吞吐成对 + 3 次重复）

| 用例 | 输入 token | 输出 token | 耗时 | 吞吐 | 峰值显存 |
|---|---|---|---|---|---|
| 文本：一句话解释雷达 | 14 | 25 | 1.36 s | **18.35 tok/s** | 3.98 GB |
| 文本：SAR vs 普通雷达区别 | 17 | 974 | 40.27 s | **24.19 tok/s** | 4.11 GB |
| 多模态：读合成距离-多普勒图 | 220 | 275 | 11.78 s | **23.34 tok/s** | 4.05 GB |

**3 次重复基准（同一 prompt，1 次预热后计时）：**

| run | 输出 token | 耗时 | 吞吐 |
|---|---|---|---|
| 1 | 25 | 1.06 s | 23.55 tok/s |
| 2 | 25 | 1.00 s | 25.01 tok/s |
| 3 | 25 | 1.02 s | 24.53 tok/s |

→ **均值 24.36 tok/s，波动 6.0%**（min 23.55 / max 25.01），测量稳定。

**与带宽上限的差距：**
```
理论带宽上限 = 256 GB/s ÷ 4.255 GB(权重) ≈ 60.2 tok/s
实测利用率   = 24.36 / 60.2 = 40.5%
```

> ⚠️ 这是一个**必须诚实标注的估算**：256 GB/s 取自 RTX 4060 Laptop 的官方规格（GDDR6 128-bit），
> **未在本机实测带宽**。因此"60.2 tok/s"应标注为**推算值**，"40.5% 利用率"同理。
> 它的价值在于给出**优化空间的量级**（约 2.5 倍），而不是当作精确结论。
> P1/P8 会用 llama.cpp 与不同量化等级做同条件对照，届时替换为实测。

### 常见报错 → 根因 → 修复（本次真实踩到的 4 个）

#### ① `ModuleNotFoundError: No module named 'torchvision'`（**最隐蔽**）
- **表象**：`AutoProcessor.from_pretrained()` 报 `Qwen3VLVideoProcessor requires the Torchvision library`。
- **根因**：`Qwen3VLProcessor` 的组合里包含 video processor，它**在 import 阶段**就
  `requires_backends(torchvision)`。**哪怕你只处理静态图片、完全不用视频，也会失败。**
- **修复**：`pip install torchvision --index-url https://download.pytorch.org/whl/cu128`（仅 9.6 MB）。
  **必须用与 torch 同源的 index**，否则会拉到 CPU 版把 torch 一起换掉。
- **教训**：我一开始推断"传 PIL 对象就能绕开 torchvision"——**错了**。依赖在 processor 构造时就触发了，
  跟输入类型无关。**"我觉得不需要"不等于"真的不需要"，跑一次比推断可靠。**

#### ② `pip install torch` 卡在 `Uninstalling setuptools-83.0.0:` 近 10 分钟
- **根因**：conda 给 py3.12 装的 `setuptools` 是 83.x，torch 要求 `setuptools<80`，
  于是 pip 去**逐文件卸载**它。实测卸载速率约 **90 KB/s**，CPU 占满但几乎不动，**极易误判为死锁**。
- **修复**：**建环境时就钉版本** → `conda create -n qwen3vl python=3.12 "setuptools<80" -y`。
- **对比实测**：未钉版本 → 9 分 39 秒仍未装完 torch；钉版本 → 同样安装直接进入解压阶段，全程无卸载。

#### ③ 控制台中文乱码（如 `P0 鐜涓庢ā鍨嬫牳楠岃繍琛?`）
- **根因**：Python 以 UTF-8 输出，PowerShell 按 GBK 解码，**在管道里**发生转码错配。
- **修复**：运行前设 `$env:PYTHONIOENCODING="utf-8"` 且 `[Console]::OutputEncoding=[Text.Encoding]::UTF8`。
- **兜底**：即使控制台乱码，**`run.log` 由 Python 用 `encoding="utf-8"` 自己落盘，永远正确**——
  所以判断结果一律以 `run.log` / `metrics.json` 为准。这就是 §4.4 那条规则存在的意义。

#### ④ `generation flags not valid: ['top_k']` 警告
- **根因**：`do_sample=False`（贪心）时传 `top_k`，transformers 5.x 会警告并忽略。
- **修复**：`src/modeling.py` 改为**只在 `do_sample=True` 时才组装 `temperature/top_p/top_k`**。
- **为什么值得修**：日志噪音会掩盖真正的警告。**"能跑就别管"的告警，是下一个静默错误的温床。**

## 【⑤ 面试延伸】

### Q1. 给你一个模型，2B 参数，bf16，你怎么估它要占多少显存？推理时还要留多少给 KV Cache？

**答题骨架：**
1. **权重**：`参数量 × dtype 字节数` = 2.128e9 × 2 B = 4.255 GB（十进制）= 3.96 GiB。**实测吻合，无额外开销**（`low_cpu_mem_usage=True`）。
2. **KV Cache**：`2 × 层数 × KV头数 × head_dim × 序列长 × batch × dtype字节`。
   本例 = `2 × 28 × 8 × 128 × 2` = **112 KiB / token**。注意**不是 `num_attention_heads`（16）而是 `num_kv_heads`（8）**——因为是 GQA。
3. **激活**：推理阶段极小（单 token），可忽略；**训练阶段才是大头**。
4. **框架开销**：CUDA context、cuBLAS workspace、PyTorch 缓存分配器的 reserved 碎片，通常预留 0.3–0.8 GB。

**追问方向：**
- *"为什么用 bf16 不用 fp16？"* → Ada(sm_89) 原生支持 bf16；bf16 动态范围与 fp32 一致，**不需要 GradScaler**，溢出风险远低于 fp16。
- *"GQA 对 KV Cache 的影响？"* → 本例 16 Q : 8 KV，KV 只缩了 **2 倍**；若是 MHA(16:16) 则翻倍。
  对比 Qwen2.5-0.5B 是 14:2（缩 7 倍），**GQA 的收益取决于 KV 头数比例，不是"用了 GQA 就一定省"**。
- *"2.97 GB 余量能开多少并发？"* → `2.97e9 / 114688 ≈ 25,900 token` 的 KV 总量。
  2048 token/请求 → 约 12 路；**但这只是理论上限，实际要扣掉碎片与框架开销**，必须实测。

**加分回答：** 主动指出 **"模型加载耗时 2.55 s / 读 4.25 GB ≈ 1.67 GB/s"** 可以反推存储介质（SSD 而非网络盘），
并说明冷启动优化（预热、常驻进程、模型缓存）在服务化里比推理本身更重要。

### Q2. 多模态模型里，一张图会变成多少个 token？这对显存和延迟意味着什么？

**答题骨架：**
1. **公式**：`视觉 token 数 = (H/patch_size/merge_size) × (W/patch_size/merge_size)`
   → 448×448 的图，patch=16、merge=2 → **196 个视觉 token**。
2. **实测验证**：多模态输入 220 token vs 纯文本 17 token，差值 203 ≈ 196 + 模板差异。**量级吻合。**
3. **影响**：
   - 视觉 token **参与 attention**，所以既进 KV Cache（196 × 112 KiB ≈ **21 MiB**），
     又拉长 prefill（attention 是 O(L²)）；
   - **提高分辨率是平方代价**：448→896 会让视觉 token 从 196 涨到 784（**4 倍**）。
4. **推论**：多模态的显存/延迟瓶颈**在图像分辨率，不在图像数量本身**（除非有 temporal 维）。
   Qwen3-VL 还有 `temporal_patch_size=2`，视频会再乘一个时间维度。

**追问方向：**
- *"DeepStack 是干什么的？"* → 从 ViT 第 5/11/17 层**取多级特征**融合进 LLM，增强细粒度图文对齐（本模型 `deepstack_visual_indexes=[5,11,17]` 实测确认）。
- *"视觉塔能不能省掉？"* → 可以冻结也可以完全不用（纯文本任务），**但权重仍占 406.9 M × 2 B ≈ 0.76 GB**，
  省显存要靠量化或换纯文本模型。
- *"为什么我们在项目里选择不训练视觉塔？"* → 详见 §9.2 风险：① 8GB 显存下视觉塔前向激活不可控；
  ② 本项目 SFT 数据是术语/公式/问答文本，**没有需要视觉理解才能答对的监督信号**，
  训它等于用噪音污染 406.9 M 参数。

**加分回答：** 指出"**视觉 token 数可公式化 ⇒ 可写成断言**"。
我们已经在 P0 用"图像 token 显著增加输入长度"做了弱断言；
更严格的做法是断言 `input_len == text_len + visual_tokens + template_overhead`，
这样**换分辨率、换 processor 版本时不会静默漂移**。

### Q3. Decode 阶段为什么慢？你用 2B 模型只跑到带宽上限的 40%，瓶颈在哪？

**答题骨架：**
1. **Decode 是 memory-bound**：每生成 1 个 token，要把**全部权重从显存读一遍**，
   却只做约 1 FLOP/Byte 的运算 → GPU 算力利用率常低于 5%。
2. **理论上限** = `显存带宽 / 权重体积` = `256 GB/s / 4.255 GB ≈ 60.2 tok/s`。
   实测 24.36 tok/s → **利用率 40.5%**。
3. **差距从哪来**（按可能性排序）：
   - **kernel 启动开销**：小 batch 时每个 kernel 只跑几十微秒，CPU 下发指令的时间与之相当；
   - **框架调度**：HuggingFace `generate()` 是 Python 逐 token 循环，Python 开销不可忽略；
   - **算子未融合**：RMSNorm+残差、RoPE、SwiGLU 各读写一次 HBM，带宽浪费在搬运上；
   - **实测带宽可能低于规格值**（笔记本 GDDR6 受功耗/温度限制）。
4. **优化方向**：换引擎（llama.cpp / vLLM）、CUDA Graph、算子融合、量化（**直接减少要读的字节数**，
   对 memory-bound 是**线性收益**）。

**追问方向：**
- *"为什么量化对 decode 收益特别大？"* → decode 瓶颈是"读权重"，W4 把要读的字节数降到 1/4，
  **吞吐理论上接近 4 倍**；而 prefill 是 compute-bound，收益小得多。这是 W4A16 在 decode 场景流行的根本原因。
- *"为什么 batch 变大能提高吞吐但延迟上升？"* → 权重只读一次却服务 N 个请求，
  算术强度提升；但每个请求要排队，且 KV Cache 竞争显存。**本质是"延迟-吞吐-成本"三者的取舍。**
- *"你怎么知道瓶颈是带宽而不是算力？"* → 做**算术强度分析**：这个 workload 约 1 FLOP/Byte，
  而 4060 Laptop 的 roofline 拐点远高于此 → 落在**带宽受限区**。也可以用 `ncu` 实测 DRAM 利用率确认。

**加分回答：** 主动承认 **"256 GB/s 是我引用的规格值，本机没实测"**，
并给出验证方法：`ncu --metrics dram__throughput.avg.pct_of_peak_sustained_elapsed`，
或跑一个纯 memcpy benchmark。**在面试里主动标注"这是推算、那是实测"，比报一个漂亮数字更得分。**

### Q4. 你怎么验证"模型身份"没有搞错？为什么不能只看模型卡？

**答题骨架（这就是我们 P0 做的）：**
1. **文件级**：读 `config.json` 的 `architectures` / `model_type` / 层数 / hidden size。
2. **权重级**：直接解析 `model.safetensors` 头部（8 字节长度 + JSON header），
   统计张量数与参数量，**完全不加载模型**。→ 得 2,127,532,032。
3. **对象级**：加载后 `sum(p.numel())`。→ 得 2,127,532,032。**两者必须相等**，否则说明
   加载器丢/补了参数（例如 tied weights 被重复计数）。
4. **行为级**：读 `tokenizer.eos_token` 实测值，与代码里假设的值比对。
5. **三方交叉**：`README.md`（模型卡）↔ `config.json` ↔ 权重张量命名 ↔ 实际行为。

**追问方向：**
- *"模型卡为什么不可信？"* → 模型卡是**人写的文档**，可能与代码/权重不同步。
  本项目的直接证据：`plan.txt` 写的 "Qwen3.5-2B" **根本不存在**；
  官方 README 写"V4.57.0 尚未发布"，但本机实际装到了 5.17.0。
  **文档会漂移，权重不会。**
- *"tied embeddings 对参数量统计有什么影响？"* → 本模型 `tie_word_embeddings=True`，
  Embedding 与 lm_head **共享同一份权重**。若统计时把两者都算，会虚增 311 M 参数（14.6%）。
  **我们的口径是"实际存储的张量"**，所以 2.128B 是存储值，不是"逻辑参数量"。

**加分回答：** 把"身份核验"工程化成**断言**而不是人工检查：
`assert st_param_count == model_param_count`。
这正是 §5.8 的精神——**把"人恰好注意到"升级成"机器必然报错"**。
本次 P0 的 25 条断言里，第 13 条就是这个。

## 六、本次实践暴露的 2 个自身缺陷（自我更正记录）

> §4.6 要求：抓到错误当场更正 + 记录。以下两条都是**我自己的**代码/推断错误。

### 缺陷 1（静默错误）：`mem_get_info()` 解包顺序写反

```python
# 错误代码（P0 首轮）
total, _ = torch.cuda.mem_get_info()      # ← mem_get_info() 返回的是 (free, total)！
fp["gpu_total_bytes"] = int(total)
```

- **现象**：报出 `gpu_total_bytes = 7451181056`（7106 MiB），而 nvidia-smi 显示 8188 MiB。
- **性质**：**静默错误**——数字看着像个合法显存值，不报错、不崩溃，但它其实是**空闲量**不是总量。
- **发现方式**：在 P0 报告里把 `nvidia-smi` 与 `torch` 两个信源并排放；如果只信 torch，
  这个错会一路带进 P4/P8 的显存预算估算。
- **修复**：`free_bytes, total_bytes = torch.cuda.mem_get_info()`，并**新增断言第 2 条**：
  用两条独立代码路径读同一个物理量并强制相等。**缺陷 → 断言，而不是"下次注意"。**

### 缺陷 2（错误推断）：以为"传 PIL 对象"可以绕开 torchvision

- **我的推断**："processor 支持 PIL image / 路径 / URL，所以只要传 PIL 对象就不需要 `qwen_vl_utils`，
  也就不需要 torchvision。"
- **实测**：`AutoProcessor.from_pretrained()` **在构造 processor 时**就触发了
  `Qwen3VLVideoProcessor` 的 import，直接 `requires_backends(torchvision)` 失败。
  **跟输入什么类型毫无关系。**
- **性质**：**未验证的推断**被当成了结论。这违反 §7「环境实测优先」。
- **修复**：`pip install torchvision`（9.6 MB），并把这个依赖写进 `docs/README.md` 的依赖表，
  标注"**P0 必需**"。

> **两条缺陷的共同点**：都不是崩溃，都是"我以为对"。这正是 §4.6 把**静默错误**排在
> 响亮错误之前的理由——响亮错误会自己找上门，静默错误需要**双信源 + 断言**才能逼出来。
