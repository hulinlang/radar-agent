## 2. 项目侧：四个能改造成 JD 弹药的方向

> 原则：**不另起炉灶**，把已有资产升级成这个岗位看得懂的形态。

### 方向 A（最推荐）把"带宽推算"升级成真正的 Analytical 性能模型 ⭐

**为什么最值**：JD 明写「性能建模与仿真」是加分项，而公司核心命题恰恰是「算力用不满」。**你手上已有真实锚点**：

| 已有实测资产 | 数值 |
|---|---|
| HF bf16 实测吞吐 | 24.0~24.36 tok/s |
| 纯带宽推算上限 | **60.2 tok/s**（利用率仅 **40.5%**） |
| llama.cpp Q4_K_M 实测 | 128.8~158.2 tok/s（**×5.2~6.6**） |
| 纯带宽能解释的部分 | 仅 **3.107×** → 其余来自 Python 逐 token 循环与 kernel 派发 |
| 显存 / 能效 | 峰值 −19%；0.50 → 1.82 tok/J |

**要做的事**（约 1 天）：
1. 写 `perf_model.py`：输入模型结构（层数 / hidden / heads / head_dim / 参数量 / dtype）+ 硬件参数（带宽 GB/s、峰值 TFLOPS），输出 **prefill 与 decode 各自的算力、访存、耗时估算**
2. 用上表四个数字**标定修正系数**（报"实测 / 模型预估"的比值，别只报理论值）
3. **敏感性分析**：带宽 ×0.5（LPDDR 场景）、量化 4bit（访存 ÷3.5）、并发 ×4，看瓶颈怎么迁移
4. 产一张 **Roofline 图**：把 prefill 与 decode 两个点画上去，标出各自离拐点多远

**验收**：能回答「把 HBM 换成 LPDDR6（带宽降到 1/3、容量翻 3 倍），decode 掉多少？该怎么补？」——这正是 S3 的产品命题。

### 方向 B：KV Cache 与并发的量化建模

**已有**：112 KiB/token（bf16，本模型实测）。
**要做**（半天）：给定 8 GiB 显存，画「并发数 × 上下文长度」可行域曲线，并反推「要支持 N 并发 × 8K 上下文，需要多少显存、权重能留多少、`-ngl` 给几层」。
**延伸（加分）**：做一张 **三层 KV Cache 的容量—延迟权衡表**（显存 / CPU DRAM / NVMe），对应 S3 的同名架构。
**验收**：能说出「什么时候该把 KV 分层放、每层放多少」的判据，而不是背名词。

### 方向 C：跑通 GGUF 部署链 + 量化精度—性能曲线

承接 `docs/14` §5 S1（那条链至今没跑通，**这里一并解决**）。跑通后额外做：
- Q4_K_M / Q8_0 / F16 三档 × 冻结评测集 → 任务级掉点（3-gram F1 + 数值命中）
- 每档配 tok/s 与显存 → 画 **精度—性能 Pareto 图**

**验收**：能讲「在 8 GiB 上，从 F16 压到 Q4_K_M，掉了多少分、换回多少速度」——这就是 JD 说的「**精度—性能联合调优**」。

### 方向 D：多模态推理加速实测（加分项的稀缺弹药）

**已有真货**：视觉塔 0.41 B（19.1%）；mmproj 与语言侧拆成两个文件；视觉 token 196（448 分辨率）→ 784（896 分辨率，**平方增长**）。
**要做**（半天，纯测量）：
1. 分辨率 / 视觉 token 数 对 **TTFT 与显存** 的影响曲线（验证"平方增长"这个理论预期）
2. mmproj F16 vs Q8_0 的延迟与精度对比（P1 计划的 E3，一直没做）
3. `--no-mmproj-offload`（视觉塔留 CPU）的延迟代价 vs 省下的显存

**验收**：产一张"多模态推理成本构成"表（视觉前向占多少、视觉 KV 占多少）。**这个岗位里做过 VLM 推理实测的人不多，是差异点。**

按「**学到什么程度**」给验收判据——不是"看过"，是"能讲 / 能写"。

### K1 · C/C++（🔴 最高优先，硬门槛）

| 项 | 目标 |
|---|---|
| 学到哪 | 能读懂并小改 **llama.cpp / ggml** 的 C++ 源码；能写多线程 + 简单内存池 |
| 为什么是它 | JD 第一条就是「熟练掌握 C/C++」；且他家 GPGPU 兼容 CUDA，学了不浪费 |
| 验收 | ① 说清 ggml 的 tensor / 计算图 / backend 抽象；② **提交一个真实的小改动**（哪怕只是一条日志或一个小算子），有 commit 可讲 |
| 捷径 | 从 llama.cpp 入手——你已经在用它，比从零学 C++ 高效得多 |

### K2 · vLLM / SGLang 源码级（本机跑不了，但能读）

| 项 | 目标 |
|---|---|
| 学到哪 | **scheduler 主循环**、**block table 分配与抢占**、**prefix cache**、**chunked prefill**、**PD 分离的 KV 传输路径** |
| 验收 | 能画出一次请求从进队到出队的完整路径，并指出每一步的瓶颈 |
| 补充做法 | 写一个**最小 continuous batching 调度模拟器**（Python 即可，约 200 行）：模拟 N 个请求 + 显存上限，观察吞吐与 P99 —— 把"没法实机"变成"我自己量化了它" |

### K3 · FlashAttention / FlashDecoding

| 项 | 目标 |
|---|---|
| 学到哪 | ① IO 复杂度为什么从 O(L²) 降到 O(L²/M)；② online softmax 怎么做（为什么不用存整个 attention 矩阵）；③ **为什么 decode 阶段要用 FlashDecoding（split-KV 再归约）** |
| 验收 | 能解释"为什么 prefill 用 FA、decode 要用 FlashDecoding"，以及 batch 大小怎么影响这个选择 |

### K4 · 并行策略与通信

| 项 | 目标 |
|---|---|
| 学到哪 | TP / PP / **EP** / SP / CP 各自切什么、通信什么；**AllReduce / AllToAll 通信量公式**；计算通信 overlap（分块 + 双缓冲） |
| 边界 | 单卡本机**跑不了**多卡并行 → 只能补理论 + 手算。**老实说"没实机跑过多卡，但算过通信量"** |
| 验收 | 手算：某 MoE 模型 EP=8 时一次 All-to-All 的字节数，在 200 Gbps 下耗时多少、能否被计算掩盖 |

### K5 · 量化算法（从"会用"到"会做"）

| 项 | 目标 |
|---|---|
| 学到哪 | **GPTQ**（OBQ + Hessian，逐列量化并补偿误差）、**AWQ**（activation-aware，保护显著权重通道）、**SmoothQuant**（把激活 outlier 迁移到权重）、**FP8**（E4M3/E5M2、per-tensor vs block-wise）、**FP4**（为什么 S3 敢原生支持）、**KV cache 量化**的风险点 |
| 验收 | ① 说清 GPTQ 与 AWQ 的**根本差异**（一个靠二阶信息补偿，一个靠激活分布挑重点）；② 能解释「为什么 FP4 在 DeepSeek 上接近无损，在我 2B 模型上不敢这么压」 |
| 起点 | 已有 Q4_K_M 使用经验（k-quants 分层 scale、mmproj 不量化），往上补算法原理即可 |

### K6 · 投机采样 与 PD/AF 分离

| 项 | 目标 |
|---|---|
| 投机采样 | 草稿模型 + 大模型批量验证；**接受率的数学**（加速比 ≈ 平均接受长度）；EAGLE / Medusa 的区别 |
| PD 分离 | 为什么划算（prefill 算密集、decode 访存密集，混在一起互相干扰）；**代价是 KV 要跨节点搬**（正是 S3 用 RDMA 优化的点）；什么条件下不划算（短 prompt，传 KV 的时间 > 省下的时间） |
| **AF 分离** | **已核实**：Attention–FFN Disaggregation，2025–2026 新兴方向——把 decode 里 **Attention（有状态、KV 主导、访存密集）** 与 **FFN（无状态、batch 大时算密集）** 拆到不同 GPU 组，中间只传 hidden state；MoE + 长上下文收益最大，Dense 小模型收益有限；SGLang/vLLM 尚无成熟生产实现 |
| 验收 | 能讲清 PD 与 AF 是**两个正交的切法**（PD 切阶段、AF 切模块），以及为什么 MoE 是 AF 最大受益者 |

## 5. 面试切入话术（针对这家公司）

**最能打开话题的一句**（用你自己的实测，反着他们的叙事说）：

> "我看到 S3 主打把 GEMM 和 FlashAttention 的算子利用率做到 99% 和 98%，核心命题是'算力用不满'。
> 我在自己机器上做过一个反方向的观察：**HF transformers 跑 2B 模型只到带宽上限的 40.5%**，
> 换成 llama.cpp 之后实测快了 5.2~6.6 倍——而**纯带宽减少只能解释其中的 3.107 倍**。
> 也就是说，**一半以上的加速不是省了数据搬运，而是干掉了 Python 逐 token 循环的框架开销**。
> 这让我意识到芯片侧的利用率和软件侧的利用率是两个不同的损失来源：我这个项目测到的是后者，
> 所以我特别想搞清楚你们在硬件和算子层是怎么把那 60% 找回来的。"

**为什么有效**：① 引用了他们的公开参数（做过功课）；② 拿自己的实测数字对照（不是背书）；③ 结尾把话题抛回面试官（变成对话而不是答辩）。

约束 → 我在约束下做了什么 → 约束解除后我会怎么改。**每条都要说出"切过去的条件"**。
