### 2.1 你现在手上有什么（三层各自的实测点）

| 层 | 你已有的实测 | 数字 | 形态 |
|---|---|---|---|
| **① 算子层**（微观，芯片能跑多快） | 手写 FP32 GEMM 调优 | **5542 GFLOPS**＝Naive 的 7.2×、**cuBLAS 的 96%**；Nsight Compute 定位瓶颈 | ✅ **你亲手写的** |
| **② 引擎层**（宏观，推理框架实际用多少） | HF vs llama.cpp 端到端对比 | 吞吐 **24.0 → 128.8~158.2 tok/s（×5.2~6.6）**；**HF 只到带宽上限的 40.5%**；纯带宽只能解释 **3.107×**；显存 −19%、能效 0.50→1.82 tok/J | ✅ **你亲手测的** |

> ⚠️ **2026-10-08 订正 —— 本行的"断裂点"已经闭合，但有两处数字要改**：
>
> ① **KV 每 token 应为 224 KiB，不是 112 KiB**。本自研引擎的 KV 是 **F32**
>    （`cpp/src/gpu_model.cu` 以 `float` 分配；`docs/28` §2.2 亦标注「KV cache 读（F32）」）。
>    112 KiB 是按 F16 误算出来的，与 `docs/20` §2.3 的公式笔误同源（那处已一并订正）。
> ② 上表「纯带宽上限 **60.2 tok/s**」是**雏形推算**（且按 F16 KV）。**已由正式模型取代**：
>    `reports/P11_Roofline性能模型.md`（2026-10-08，参数唯一来源 `configs/perf_model.yaml`）。
>    该模型对自研 CUDA F16 的预测与实测吻合到 **0.8%**（预测 63.0 vs 实测 62.5 tok/s），
>    并给出了 decode 的算术强度（≈1.0 FLOP/Byte vs 转折点 59.3 → 定量确认带宽受限）
>    与 prefill 由访存受限转算力受限的临界 prompt 长度（**≈59 token**）。

**关键观察**：**①和②是在同一块 RTX 4060 Laptop 上测的**。
一个从微观摸到了它的算力天花板，一个从宏观发现了它只被用到 40.5%。
**这两个数字之间的矛盾，就是你要讲的故事。**

### 2.2 缺的那座桥：Roofline

```
                 算  力  上  限  ────────────────────
                                        ╱
                             ╱  ① 你手写的 GEMM
                           ╱      （算密集，算术强度高）
                         ╱
    ──────────────────╱
   ／   ② LLM decode ← 桥（Roofline 模型）
 ／      （访存密集，算术强度≈1 FLOP/Byte）
／
带宽上限
```

- **① 在右边**（算力受限区）—— 你已经摸到天花板了，还拿到 cuBLAS 的 96%
- **② 在左边**（带宽受限区）—— HF 只跑到 40.5%，换引擎后 ×5.2~6.6
- **桥 = 一个 `perf_model.py`**：输入模型结构 + 硬件参数 → 输出 prefill / decode 各自的算力、访存、耗时估算，并把四个实测点标在同一张图上

**搭完桥之后，"prefill 算密集、decode 访存密集"这句话就不再是背书，而是你亲手从两端验证过的结论。**

### 2.3 为什么这个组合稀缺（面试价值）

> **推测**，依据：应届生常见形状是"只做过一层"。

| 常见形状 | 缺什么 |
|---|---|
| 只做过 CUDA 算子（科班高性能方向） | 不知道这些算子在真实 LLM 推理里占多少、瓶颈在不在自己写的那部分 |
| 只做过模型应用/微调（绝大多数 LLM 方向） | 不知道芯片在干什么，只能报"换引擎快了 5 倍"但说不出为什么 |
| **你（补齐后）** | **两层都有实测 + 中间有模型把它们连起来** |

而曦望的商业叙事**正好横跨这两端**：
- **S3 的 GEMM 99% / FlashAttention 98%** → 在跟右边（算力区）较劲
- **S3 用 LPDDR6 而非 HBM（功耗降 50%，但带宽降到约 1/3）** → 在跟左边（带宽区）妥协

→ **你能从两端分别接话，这是别人接不上的。**

### 2.4 备选（大概率不用）：雷达 STAP 方向的同源性

STAP 的核心是**协方差矩阵 R = E[xx^H]**（维度 N×M，H 为共轭转置）与**求逆**，计算量随维度三次方增长；
所谓"降维 STAP"（JDL / mDT / 3DT 等）本质就是**在不损失检测性能的前提下砍计算量**。
→ 抽象出来是「**在算力约束下做计算量优化**」，与推理加速属于同一个问题族。

> ⚠️ **用户 2026-09-29 口径：雷达方向与 AI 无关，不作为弹药。**
> 本节仅作**备用**：只在被追问"你为什么对性能有直觉"时用一句话带过，**不要展开**。
> 主线永远是推理/算子，雷达只是你的背景，不是你的卖点（对这家公司而言）。

## 3. 修订后还剩哪些缺口

### 3.1 通用 C++（非 CUDA）—— 🟡 中等风险

会写 CUDA kernel **不等于**能答这些。曦望既然写"熟练掌握 C/C++"，大概率会问：

| 必答 | 一句话要点 |
|---|---|
| 内存模型 | 栈/堆/全局区布局；`new` 背后是 `malloc` 再构造；内存对齐为什么影响 SIMD 与合并访存 |
| 多线程 | `std::thread` / `mutex` / 原子操作；**伪共享（false sharing）**；你写 GEMM 时的 bank conflict 与之类比 |
| 指针/引用/右值 | 左值右值、`std::move` 只是类型转换不搬数据、RAII |
| 虚表 | 虚函数表指针带来的**间接跳转**——可以类比 kernel 里的函数指针导致无法内联 |

**捷径**：不要从头学 C++。读 **llama.cpp / ggml 的 C++ 源码**（你已经在用它推理），
目标不是"会写"，是"能讲清 ggml 的 tensor / 计算图 / backend 抽象"，并**提交一个真实的小改动**（哪怕是一条更有用的日志或一个缺失的小算子）。
**有 commit 可讲 ≫ 说"我熟悉 C++"。**

### 3.2 分布式 / 高性能网络 —— 🔴 唯一真正的硬缺口

**本机约束**：WSL 被安全策略封禁、无 Docker → vLLM 都跑不起来，更别提多卡。
**诚实策略**（与 `docs/14` §6 同构的三段式）：约束 → 约束下我做了什么 → 约束解除后怎么改。
**补偿手段**：**手算通信量**（这条能撑住大部分追问）：

- TP：每次 AllReduce 传输量 = `2 × batch × seq × hidden × dtype_bytes × (world_size−1)/world_size`
- EP（MoE）：一次 All-to-All 的字节数 = `tokens × top_k × hidden × dtype_bytes × (world_size−1)/world_size`
- 再除以链路带宽（200 Gbps ≈ 25 GB/s）→ 得到耗时 → **与计算耗时比较，判断能否 overlap**

**验收**：能手算"某 MoE 模型 EP=8 的一次 All-to-All 在 200 Gbps 下多少毫秒、能否被计算掩盖"。
S3 主打「超节点 256 卡一级互联，大 EP 下 MoE 吞吐 20×」——**EP 是他家重点**，这块必须能算。

### 3.3 架构表述（⚠️ 小缺口）

会用 CUDA 不等于能讲清架构。补到能画一张图并说清：
**Grid → Block → Warp（32 线程，SIMT）→ SM（含几个 warp scheduler）→ 存储层次（寄存器 / Shared Memory / L1 / L2 / HBM）**，
以及**为什么 bank conflict 会让 Shared Memory 带宽打折**、**合并访存（coalescing）意味着什么**。
→ 这些你在写 GEMM 时**一定已经踩过**，只是需要组织成能讲的语言。

## 4. ⚠️ 手写的 GEMM 数字，先自己扛住追问（**必做，30 分钟**）

简历上的数字会被追着问。**5542 GFLOPS 是相对 cuBLAS 的 96%，但相对硬件峰值是多少？**

### 4.1 我按公式推的（**推算**，假设需你确认）

- RTX 4060 Laptop 用 AD107：**3072 CUDA core ＝ 24 SM**（3072 / 128）
- FP32 峰值 ＝ `3072 × 2 × f(GHz)` TFLOPS
  - f = 2.0 GHz → **12.29 TFLOPS** → 你的 5542 GFLOPS 占 **45.1%**
  - f = 1.5 GHz → 9.22 TFLOPS → 占 **60.1%**
  - f = 1.0 GHz → 6.14 TFLOPS → 占 **90.2%**
- → **5.54 TFLOPS 大约是硬件 FP32 峰值的 38%~60%**（取决于实测时的实际 boost 频率，笔记本功耗墙下往往远低于标称）

### 4.2 三个必须提前准备答案的问题

1. **"占硬件峰值多少？"** → 别猜，**去 Nsight Compute 里读 `sm__cycles_elapsed.avg.per_second`**（实测 SM 频率）和
   **`sm__throughput.avg.pct_of_peak_sustained_active`**（SOL 算力利用率）。这是权威数字，比自己算可信。
2. **"为什么 cuBLAS 在 1024³ 上也只有 5.77 TFLOPS？"** → **wave quantization**：
   128×128 tile 下 1024³ 有 `8×8 = 64` 个 tile，分给 24 个 SM 需要 **3 个 wave**，最后一个 wave 只占 2/3
   → tile 级效率上限就只有 `64 / (3×24) = 88.9%`，再叠功耗墙与访存，**落到 45% 完全合理**。
   ⭐ **能答出 wave quantization 是加分项**，因为这说明你知道"小矩阵测不出真峰值"。
3. **"为什么不用 tensor core？"** → FP32 GEMM 走的是 CUDA core；4060 上 FP16 + tensor core 的峰值通常是 FP32 的
   2~4 倍。**这正是 §5.2 要补的方向。**

> ⚠️ **口径纪律（本项目 §5.2）**：上面 4.1 的百分比是**推算**，不是你的实测。
> **讲之前必须用自己的 Nsight 数字替换**，否则就是"拿估算当实测"——这正是本项目反复禁止的事。

## 5. 算子侧的延伸动作（把"串起来"落地）

> 原则：**你已经会写 GEMM 了，下面每一步都是"换一个瓶颈区"，不是从零学新东西。**

### 5.1 ⭐ GEMM → GEMV（最高优先，2~3 天）

**为什么是它**：
- **GEMM（矩阵×矩阵）是 prefill 的核心算子** —— 你已经写过，在 Roofline 的**右侧（算力受限）**
- **GEMV（矩阵×向量）是 decode 的核心算子** —— batch=1 时每次前向就是一堆 GEMV，在 Roofline 的**左侧（带宽受限）**
- **你只差左边这一个点。** 补上它，Roofline 上"prefill 算密集 / decode 访存密集"这句话
  **两个端点就都是你自己的实测**，而不是从论文里看的

**具体做**：
1. 写一个 `gemv` kernel（或 `split-K GEMV`，即把 K 维切开并行归约——这正是 **FlashDecoding** 的同构思路）
2. 用 **Nsight Compute** 对 GEMM 与 GEMV 各出一份报告，对比：
   - SOL 算力利用率 vs SOL 显存利用率（**一个应该算力高、一个应该带宽高**）
   - 各自卡在哪个 stall reason
3. 把两个点画到 Roofline 图上

**验收**：能说出「我手写的 GEMM 在这个算力利用率、GEMV 在这个带宽利用率，
两者差 X 倍，这就是 prefill 与 decode 瓶颈不同的**算子级证据**」。

> ⭐ 这一步做完，**"CUDA 算子"和"LLM 推理性能归因"就焊死了**——这是本次最关键的一个动作。

### 5.2 FP32 → 低比特（3~5 天，对上曦望"原生 FP4"卖点）

你已经会写 FP32 GEMM，下一步是 **FP16 + tensor core**（`wmma` / `mma` PTX），有余力再上 **INT8**。
产出：**同一规模下 FP32 / FP16 / INT8 三档的 GFLOPS 与相对 cuBLAS 的百分比**。
→ 这份数据直接对上 JD 的「**低比特计算**」与「**精度—性能联合调优**」，
并且与 `docs/15` 方向 C（量化精度—性能 Pareto 图）**合流成一张图**。

### 5.3 与方向 A 的合流点

`docs/15` 的方向 A（`perf_model.py` + Roofline）现在有了**天然素材**：
Roofline 图上不再只有两个"模型推理"的点，而是有**四个你自己的实测点**：
`手写 GEMM`、`手写 GEMV`、`LLM prefill`、`LLM decode`。
**这四点亮在同一张图上，是别人给不出来的东西。**

## 7. 90 秒自我介绍主线（针对这家公司）

> "我做两块事，都在同一块 4060 上。
> **一块是自底向上**：手写 CUDA GEMM，从 Naive 调优到 5542 GFLOPS、cuBLAS 的 96%，
> 用 Nsight Compute 定位瓶颈——我知道这块芯片单算子的天花板在哪。
> **另一块是自顶向下**：跑 2B 多模态模型的推理，实测发现 HF transformers
> **只跑到带宽上限的 40.5%**，换成 llama.cpp 之后快了 5.2~6.6 倍，
> 但**纯带宽减少只能解释 3.107 倍**——一半以上的加速来自干掉框架开销，不是省了数据搬运。
> 这两件事的矛盾让我去做第三件事：**建一个解析性能模型把算子层和系统层连起来**，
> 现在 prefill 和 decode 各自的算力、访存、耗时我都能估算出来。
> 我看到 S3 主打把 GEMM 和 FlashAttention 做到 99% 和 98%，同时又用 LPDDR6 把带宽降到约 1/3——
> **这正好是 Roofline 的两端**。所以我很想搞清楚，你们在硬件和算子层是怎么把那 60% 找回来的。"

**为什么这样讲**：① 三层都有数字；② 有矛盾、有追问、有我的解法（不是流水账）；
③ 引用了对方产品参数；④ 结尾把话抛回去，变成对话。
