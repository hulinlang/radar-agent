## 0. 为什么先做这个（而不是 dp4a prefill）

`docs/27` §4 的遗留项里有两条够格当"下一个里程碑"：

| 候选 | 来源 | 收益 | 代价 |
|---|---|---|---|
| **A. 分页 KV + 跨请求前缀复用**（本方案） | `docs/27` §4 第一项；`docs/README` §二候选表第一项 | 补上**生产级服务引擎的另一根支柱**（B8 是 continuous batching，B10 是分页 KV）；显存从"按 max_len 预留"变"按实际用量分配"；跨请求前缀只 prefill 一次 | 触及 6 个 KV/attention kernel；与 CUDA Graph 捕获有冲突要解决 |
| B. prefill 的 GEMM 级性能（dp4a + int8 激活） | `docs/29` §7.3（B8 的 DoD#2 "≥1000 tok/s" **只算部分达成**） | 关掉一个未达标的 DoD | **会改变数值口径**（int8 激活），对拍方法要整体换成 teacher-forcing；kernel 工作量大 |

**选择 A 的三条理由**：

1. **先补能力，再补性能**。B8 已经证明了"批量"这件事；分页 KV 是另一半。做完 A，本项目就有了
   一个真正意义上的 serving engine（continuous batching + paged KV + prefix cache），
   而 B 只是把已有路径再调快一截。
2. **A 能保持 bitwise 对拍**（见 §3.4 的正确性论据），B 不能。项目全部验收方法论建立在
   "每次优化都过同一份对拍"上（`docs/27` §2），**能保住这条纪律的方案优先**。
3. **A 是面试点名率最高的技术**（vLLM 的 S3 卖点）；B 的 dp4a/MMQ 属于第二层追问。

> ⚠️ **一条诚实的前提说明**：本项目当前的业务负载（ReAct 串行链路、单会话）**用不满**分页 KV 的吞吐收益
> —— 单会话下 B9 的会话级 LCP 已经吃掉了前缀复用。
> 所以 B10 的收益要落在**两处可实测的地方**：
> ① **显存效率**（不再按 `kv_cap` 预留，实测 `cudaMemGetInfo` 差值）；
> ② **多请求共享前缀的吞吐**（N 个共享 system prompt 的请求，第 2..N 个的 prefill 开销 → 0）。
> 如果这两条测不出收益，就应该如实记录"本项目场景下不值得"，而不是硬讲。

## 2. 现状与数据（已核实源码）

### 2.1 当前 KV 布局：每槽位**预留满** `kv_cap`

`cpp/src/gpu_model.cu`：

```
kv_elems   = n_layer × 2(K,V) × n_kv_head × kv_cap × head_dim
d_kv       = cudaMalloc(kv_elems × n_slots × sizeof(float))   // F32
slot_stride = n_kv_head × kv_cap × head_dim
head_stride = kv_cap × head_dim
```

- 槽位数 `n_slots = max_batch + 1`，**末尾槽是 padding 行的 scratch**（`gpu_model.h` 注释已写明）。
- ⚠️ **关键代价**：一条只用了 100 个 token 的序列，和一条用满 8192 的序列，**占用完全一样**。
  `docs/29` §4 的显存预算就是这条的直接后果：
  `KV 槽位池（8 × 2048 × 224KB）= 3.67 GB`。
- KV 是 **F32**（`cudaMalloc(..., sizeof(float))`）→ 224 KiB/token。
  ⚠️ 这个数字在 `docs/20` §2.3 曾被写成「×2B」的笔误，已于 B11/P11 订正（见 `reports/P11_Roofline性能模型.md`）。

### 2.2 `radar-serve` 只维护**一个**会话

`cpp/src/serve.cpp`：会话状态是 `std::vector<int32_t> history; int pos = 0;` 两个变量，
`prefill_batch(..., slot=0, pos0=pos)` **恒用 slot 0**。
新 prompt 与 history 做 token 级 LCP，只 prefill 后缀 → 这是 B9 的**会话级**前缀复用，
**跨会话不共享**：两个不同用户问同一个 system prompt，各自都要从头 prefill。

### 2.3 CUDA Graph 与"块数可变"的冲突（本方案最大的设计约束）

B8b 的批量 decode 是**整步 CUDA Graph 捕获**的（`gpu_model.h` 注释："Graph-captured after the first call"）。
Graph 捕获会把 **kernel 参数值**烘进图里。若把"这条序列有几个块"当 kernel 参数传，块数一变图就失效。

**对策**（写进 §3.3）：每序列的**有效块数放在 device buffer 里**（不是 kernel 参数），
kernel 从显存读；块表本身也是 device buffer，内容可随时改而不影响已捕获的图。
这与 vLLM 的做法同源。

`cpp/tests/test_b{4,6,7,8,9}.sh` —— 见 §6 的基线记录。

## 3. 设计

### 3.1 块池与寻址

- **块大小 `block_size = 16`**（与 B8a 的 16-token 分块一致，便于复用已有的多列 gemv 分块）。
- 新 KV 布局：

```
[layer][k/v][block][kv_head][block_size][head_dim]
```

  即**块内按 head 优先、位置次之**，保证"固定 head 下块内位置连续"——
  与现有 `head_stride` 的访问模式同构，attention 内层循环只需加一层块间接。

- **块表**：每序列一条 `int32 block_table[max_seq][max_blocks_per_seq]`（device 数组）。
- **有效块数**：`int32 n_blocks[max_seq]`（device 数组，**不进 kernel 参数**，见 §2.3）。
- 一次 KV 写入/读取的地址：

```
byte_off(seq, layer, kv, head, pos) =
    ((layer*2 + kv) * n_block + block_table[seq][pos/block_size])
  + head * (block_size * head_dim)
  + (pos % block_size) * head_dim
```

### 3.2 需要改的 kernel（共 6 个，全部在 `gpu_model.cu`）

| kernel | 改动 |
|---|---|
| `kv_store` / `kv_store_rows` / `kv_store_batch` | 写入地址从 `slot_stride + h*head_stride + pos*head_dim` 换成块表寻址 |
| `attention`（decode 单序列） | 位置循环外层加"按块"循环；块内层顺序不变 |
| `attention_prefill`（B8a） | 同上（T 个 query 对 T 个 key 的因果掩码按块切） |
| `attention_batch`（B8b） | 同上，且每行的块表/块数从 device 数组按行取 |

> ⚠️ **BLOCK_SIZE 作为编译期常量**（`#define`/`constexpr`）而不是运行时变量：
> 让编译器仍能展开内层循环，且块内位置可用位运算（16 是 2 的幂）→ 不引入除法。
> 这也让"是否引入性能回退"成为一个可测问题（见 §5 风险）。

### 3.3 与 CUDA Graph 的兼容（关键）

- kernel 参数只保留**不变的形状量**（`max_blocks_per_seq`、`block_size`、`max_batch` 等）。
- **每序列的有效块数**与**块表内容**都放 device buffer；每步由 host 侧用 `cudaMemcpyAsync` 更新
  （这一步在 graph 之外的 stream 上做，或用 graph 的 memcpy 节点）。
- 于是"某序列本轮用了 3 块、下轮用了 9 块"**不需要重捕获** —— 循环上界取 `max_blocks_per_seq`，
  块数之外的块读到的是垃圾值，与 B8 的 padding 槽位同一套处理哲学（**不做分支，浪费一点算力**）。

### 3.4 正确性论据（为什么能做到逐 id 相同）

与 B9 的 LCP 论证同构：

> 位置 p 的 KV 只由 token p 与该位置之前的前缀状态决定。
> 分页只改变**这些值存放的地址**，不改变**计算它们的算子顺序**，也不改变 attention 的
> **求和顺序**（块内位置仍按原顺序累加，块按 pos 递增顺序遍历）。
> ⇒ 浮点累加顺序不变 ⇒ 结果**逐位相同**。

⚠️ 唯一的例外是 `attention_prefill`：它在 B8a 就已经是"并行归约、allclose 非 bitwise"
（`docs/29` §7.4 已记录）。所以 DoD#1 的硬口径用于 **decode 路径**；
prefill 路径沿用 B8a 的既有口径（allclose + 逐 id 未翻转）。

### 3.5 跨请求前缀复用（B10b）

- **块粒度共享**：一个块被填满（16 个 token）后，对其 token id 序列算哈希，
  查 `hash → block_id` 表；命中则**共享**（refcount++），不重新 prefill。
- **写时复制**：向一个 refcount>1 的**未满**块追加位置时要 COW。
  简化：**只共享"已满且前缀对齐"的块**，未满块永不共享 → 免去 COW 的绝大多数场景。
- **淘汰**：LRU + 只淘汰 refcount==0 的块。
- ⚠️ **前缀必须按块对齐才命中**：system prompt 长度不是 16 的倍数时，最后一个不满块不共享。
  这是 vLLM 也有的限制，写进文档而不是假装没有。

### 3.6 B10c：`radar-serve` 多会话化

- 会话表 `{id → {block_table 行号, pos, history}}`；`RESET` 只清该会话。
- 新增 `SESSION <id>` 请求字段与 `GET /stats`（块池占用、命中率、节省的 prefill token 数）。
- ⚠️ **保持向后兼容**：不传 `SESSION` 时退化为 B9 的单会话行为 →
  `p9_compare_radarinfer.py` 与 22 题评分子集**仍能照跑**（这是 DoD#6 的一部分）。

## 5. 风险

| 风险 | 等级 | 应对 |
|---|---|---|
| **性能回退**：块寻址多一层间接 → attention 内层循环可能变慢 | 中（**已降级**） | ✅ **用户 2026-10-10 拍板：先不管性能，先把正确性做对。** 所以本里程碑**不设性能门槛**，但仍要**如实测并报**分页前后的 tok/s（§5.9 要成对报延迟与吞吐），把回退量作为记录项而非阻塞项；`block_size` 取 2 的幂用位运算是顺手做的优化，不作为验收条件 |

## 7. 明确不做（防范围蔓延）

- **KV 量化（F32→F16）**：`docs/27` §4 把它与本项并列，但它**会改变数值口径**（KV 精度影响
  attention 值 → 可能改变 greedy id），性质与 dp4a 相同 → **另立项**，本里程碑不动它。
  这也是为什么 §1 的 DoD#1 敢用"逐 id 相同"这种硬口径。
- PagedAttention 的**跨序列块迁移**（vLLM 的 swap/preemption）：本项目 `max_batch` 小、无抢占需求。
- **beam search / 多序列并行采样**：与分页无关，属另一个话题。
- int8 激活 / dp4a prefill（见 §0 候选 B）。
- 视觉塔进引擎（`docs/15` 方向 D）。

## 8. 实施进度与验收（B10a-1/2/3 已完成）

### 8.1 已完成：块池 + 块表 + 块寻址（三条路径全改）

| 层 | 改动 |
|---|---|

「块递增 → 块内位置递增」枚举 `t`，与原 `for t=0..T` **完全同一个累加顺序** ⇒ 浮点逐位相同。
`attention_prefill` 因 B8a 起就是并行归约（`docs/29` §7.4 已记录 allclose 非 bitwise），
沿用既有口径。

### 8.4 ⚠️ 一个可解释的**疑似**性能收益（需配对测量才能落定为结论）

同一 session、改动前后对比：

| 项 | 分页前（本次基线） | 分页后 | 变化 |
|---|---|---|---|
| B6 自研 CUDA F16 | 58.24 tok/s | **61.08** | +4.9% |
| B7 自研 Q4-on-GPU | 113.28 tok/s | **130.41** | **+15.1%** |
| 参照 llama.cpp Q4（未改动） | 132.23 tok/s | 141.47 | +7.0%（session 漂移） |

**机理假设**（可验证）：旧布局的 `head_stride = kv_cap × head_dim` = 4096×128×4B = **2 MB**，
即同一位置上不同 KV head 相距 2 MB；新布局一个块 = 8 头 × 16 位置 × 128 维 × 4B = **64 KB**，
8 个 head 的工作集能落进 L1/L2。attention 的 K/V 读取局部性因此改善。

⚠️ **纪律**：按 §5.9 与 `docs/03` 已知局限 6，**性能结论必须同 session A/B/A/B 配对**才算数。
上表只是"改动前后各一次"，且参照系自身也漂移了 7% ⇒ **暂记为观察项，不写进任何结论**。

#### 🔻 2026-10-10 更正：**这个疑似收益是噪声，不成立**

B10b 完成后又测了一次（**B10b 并未改动 Q4 的 decode kernel**）：

| B7 自研 Q4 的测量次序 | 值 |
|---|---|
| 基线（B10 之前） | 113.28 tok/s |
| B10a 之后 | 130.41 tok/s |
| **B10b 之后**（Q4 decode 代码未变） | **111.85 tok/s** |

同一 session 内三次跨距 **17%**（111.85 ↔ 130.41），**与 `docs/03` 记录的跨 session 漂移量级一致**。
⇒ §8.4 那个"+15%"落在噪声内，**"分页改善了 attention 局部性"这个机理假设目前没有证据支持**。
**结论撤销**，机理假设保留为待验证项。

> 这条更正本身是 `docs/00` §5.2「禁止编造指标」与 §5.9「单次测量不足以定论」的落地：
> **同一个 session 内的 run-to-run 波动就足以吞掉一个 15% 的"效果"** ——
> 这正是本项目坚持"关键结论至少 3 次重复 + 同 session A/B/A/B"的原因。

### 8.5 ⭐ DoD#3 达成：显存不再按 max_len 预留（B10a-4 实测）

CLI 已透出 `--num-blocks`（`radar-infer` 与 `radar-serve` 都有）。

**用例**：p1 prompt（**5 token**）+ `--n-predict 100`、`--kv-cap 4096`、Q4_K_M、单序列。
`n_slots=1` ⇒ `max_blocks = 4096/16 = 256`；每块 = 28 层 × 2(KV) × 8 头 × 16 位置 × 128 维 × 4 B = **3.5 MiB**
⇒ **分页前等价占用 = 256 × 3.5 MiB = 896 MiB**。

| `--num-blocks` | 计算池大小 | **`cudaMemGetInfo` 实测差值** | 分页前等价 | 省 | 跑完实际用了 |
|---|---|---|---|---|---|
| `0`（auto） | 896.0 MiB | **896.0 MiB** ✅ | 896.0 MiB | 1.0× | 7 块 |
| `32` | 112.0 MiB | **112.0 MiB** ✅ | 896.0 MiB | **8.0×** | 7 块 |
| `8` | 28.0 MiB | **28.0 MiB** ✅ | 896.0 MiB | **32.0×** | 7 块 |

**三处要点**：

1. **跨信源一致**（§5.8）：计算值与 `cudaMemGetInfo` 实测差值**逐档吻合到 0.1 MiB**，
   所以这个数字不是"算出来的"而是"量出来的"。
2. **`used=7`**：113 个 token 的序列实际只占 7 块（24.5 MiB），**分页前却要为它预留 256 块（896 MiB）**
   —— 这就是 32× 的来源，与 §0「诚实的前提说明」里承诺要落地的"① 显存效率"对上了。
3. **正确性与池容量解耦**：`auto` / `32` / `8` 三种池大小下生成的 **id 完全一致**（脚本内 diff 断言）。
   即省显存**不以改变数值为代价**。
4. 吞吐无回退：三档 decode 均为 **94–98 tok/s**（差异在测量噪声内）。

> ⚠️ 反过来说清楚了分页前的**实际限制**：`--kv-cap 4096` 在批量模式下分页前**根本跑不起来**
> （9 槽 × 256 块 × 3.5 MiB ≈ **7.9 GiB**，VRAM 自动降级会把 `max_batch` 一路砍到 1）。
> 分页把这个配置从"不可行"变成"可行"。

## 9. B10b 验收：跨请求前缀共享（DoD#4 达成）

### 9.1 实现（相对方案 §3.5 的一处简化）

| 机制 | 做法 |
|---|---|
| 共享粒度 | **只共享已满的块**（16 个 token 全已知）⇒ 未满块永不共享 ⇒ **免去写时复制（COW）** |
| 内容寻址 | **前缀链式哈希** `h_b = FNV1a(h_{b-1}, block_b 的 16 个 token)`；命中后**逐 token 比对**（不信任哈希），碰撞只损失一次复用机会 |
| 释放语义 | 块 refcount 归 0 时**回到空闲栈，但保留在前缀索引里** —— 这正是跨请求复用的来源 |
| 淘汰 | ⭐ **不需要单独 LRU**：分配路径是"先查哈希命中 → 再取空闲块"，而被复用的空闲块在 pop 时顺手清掉自己的旧索引项 |
| 计算跳过 | `prefill_batch` 把「前导的缓存命中块数 × 16」作为 `skip`，**只从 `skip` 开始算**；命中块不重算、也不重复占显存 |
| A/B 开关 | `RADAR_NO_PREFIX_CACHE=1` 关掉缓存（用于配对验证） |
| 控制 | 新增 `GpuModel::begin_sequence(slot)`（调度器把复用槽位交给新请求时调用）；`last_reused_tokens()/prefix_hits()/prefix_misses()` 自省 |

**一处必须做对且不报错的细节**（已写进代码注释）：调用方以 `pos0 > 0` 续写时（serve 的会话 LCP），
`hist` 必须**先截断到 pos0**，否则历史变成「旧尾巴 + 新后缀」、后续所有块哈希都错。
最坏后果是复用永不命中（而非算错），但历史正确性是前提。
