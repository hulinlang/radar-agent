# 阶段 B · B5 详细方案：性能——多线程 / OpenBLAS 主线 / Q4_K·Q6_K 反量化

> 前置：B4 总 DoD 已达成（440/440 token 对拍 llama.cpp），性能基线 **decode 0.35 tok/s**
> （朴素单线程 F32，F16 模型）。边界决策（docs/20 §5.2b）：**重计算接库**——
> OpenBLAS 为主线，手写版作教学对照；dequant kernel 无库可接，手写。
> 目标（已拍板）：BLAS 主线 ≥ llama.cpp CPU Q4 实测值（37.8 tok/s）的 50%（≈19 tok/s）。
> 本文是 B5 的开工前方案，确认后才写码。

## 1. 性能预算（先把账算清楚再动手）

decode 单 token 的本质是"把整个模型读一遍"（docs/20 §2.3）：

| 路径 | 每 token 读取量 | 达成 19 tok/s 所需带宽 |
|---|---|---|
| F16（现状） | 3.44 GB | 65 GB/s（笔记本 DDR5 多核上限 ~40-60，**偏紧**） |
| F16→F32（BLAS 需要） | 6.9 GB | 131 GB/s（**无望**，BLAS 主线瓶颈在内存不在计算） |
| **Q4_K_M** | **1.05 GB** | **20 GB/s（从容）** ← 真正的主线 |

结论：**BLAS 主线（sgemv，F32 权重）注定撞内存墙，它的价值是验证"接库"路径 +
提供第二实现对照；Q4_K_M + 多线程 dequant-matvec 才是性能主线**。
这与生产一致：llama.cpp/llamafile 的 CPU 推理也从不走"转 F32 调 BLAS"，
而是量化权重 + 融合 dequant 的 matvec kernel。

## 2. 三个工作项

### B5a 多线程（OpenMP，语义零变化）

- `matvec_f16` 按**行分区**并行（`#pragma omp parallel for`）：每行点积的累加顺序不变
  → **与单线程逐 bit 相同**，B4 对拍必须原样全绿（这是验收，不是期望）；
- OpenMP 是编译器内建（gcc `-fopenmp`），不算第三方依赖；
- attention 的 16 头循环、FFN 的逐元素循环同样并行化；RoPE/norm 量级太小不动。
- 顺带修一个结构问题：**prefill 目前逐 token 循环**，本里程碑只加"行并行"，
  批量 prefill（矩阵×矩阵）明确不做（B6+）。

### B5b OpenBLAS 路径（对照 + 接库验证）

- WSL 内 `apt install libopenblas-dev`；加载时 F16→F32 全量转换（~6.9GB 内存，可接受）；
- `matvec` 后端接口 `--backend naive|omp|blas`，`cblas_sgemv` 替换热点；
- **数值口径变化要明写**：sgemv 分块累加 ≠ 朴素顺序累加 → 与 B4 参照可能出现
  数值平局分叉。验收改为：B3 逐层对拍（allclose 阈值内）+ B4 前 20 token 对拍
  允许个案分叉（按 docs/24 §5 预案：top-2 概率差 <1e-3 属合法平局，记录之）；
- 预期结果：比 omp 快但撞内存墙（§1），**用数字证明"BLAS 不是 CPU 推理的答案"**。

### B5c Q4_K / Q6_K 反量化 + 融合 matvec（性能主线）

- 照 ggml 语义手写（本仓库 `tools/llama.cpp/ggml/src/ggml-quants.c` 可读定义）：
  - **Q4_K**（144 B / 256 权重）：超块 f16 双 scale（d, dmin）+ 8 子块 6-bit 压缩 scale/min
    + 4-bit 量化值；`w = d·sc·q − dmin·min`；
  - **Q6_K**（210 B / 256 权重）：ql[128] 低 4 位 + qh[64] 高 2 位 + int8 scales[16] + f16 d；
    `w = d·sc·(q − 32)`；
- 形态：**逐行 dequant 到 F32 缓冲再点积**（第一版不追求 fused SIMD，正确性优先）；
  外层照样 OpenMP 行并行；
- 模型侧：`Model::load` 按张量类型分派（F16 走 matvec_f16，Q4_K/Q6_K 走对应 kernel），
  类型断言放宽为"F16|Q4_K|Q6_K"。

## 4. 性能矩阵（§5.9 纪律：单变量、重复 3 次取中位、配对报告）

统一用 p1 prompt（5 token）+ 50 token decode：

| 配置 | 变量 | 预期 |
|---|---|---|
| naive 单线程 F16（B4 基线） | — | 0.35 tok/s |
| omp F16 | +多线程 | 3-6× |
| blas F32 | +接库 | 与 omp 互有胜负，撞内存墙 |
| **omp Q4_K_M** | +量化 | **主线目标 ≥19 tok/s** |
| llama.cpp CPU Q4（参照驱动） | 引擎差距 | 37.8 tok/s（A3 实测值，复测） |

每个配置打印 prefill/decode tok/s；报告分析**差距分解**（我们缺的到底是
SIMD、fused dequant-dot、还是 cache 阻塞——用每配置实测反推）。

## 5. 风险清单

1. **Q4_K 的 6-bit scale 解包**（`scales[12]` 的分裂位布局）写错 → dequant 单元对拍兜底；
2. OpenMP 行并行若引入假共享/调度开销，小矩阵（2048×1024）可能负优化 → 性能矩阵会暴露，
   对策：按行数阈值跳过并行；
3. OpenBLAS 线程数与 OpenMP 冲突（嵌套并行）→ BLAS 路径显式 `openblas_set_num_threads`；
4. WSL apt 装 openblas 的版本差异 → 只调 cblas_sgemv 标准接口，无版本敏感点；
5. Q4 对拍的平局分叉率超预期 → 若 <95%，先查 dequant 精度再谈接受。

## 6. 明确不做

批量 prefill、KV cache 量化/分页、SIMD intrinsics 手写（AVX2 版本留 B6 或"深入项"）、
投机采样、多请求批处理、CUDA（B6+）。

## 8. 验收结果（2026-10-07 实测，7/7 全绿）+ 性能矩阵分析

### 正确性（全绿）

| 验收项 | 结果 |
|---|---|
| 构建零警告 | ✅ |
| dequant 单元对拍（Q4_K/Q6_K vs libggml，5 张量 3.3 亿值） | ✅ **逐位 EXACT** |
| B3 前向回归（omp 后端） | ✅ allclose 全过 |
| B4 抽查回归（omp F16, 50 token） | ✅ **bit 级一致**（OpenMP 行分区不改动累加顺序，验证成立） |
| Q4 teacher 实验 | ✅ 自研 **49/50** vs llama.cpp 48/50（F16 轨迹教师强制） |

**Q4 对拍口径修订（重要）**：方案原定"自研 Q4 vs llama.cpp Q4 ≥95% id 一致"——实测发现
llama.cpp 的 Q4 matvec 用 **Q4_K×Q8_K 融合 kernel（激活也被量化到 8bit）**，与自研的
"精确 dequant + F32 激活"存在 ~0.2 量级的 logit 系统性差异，**不是平局而是路线差异**。
自研路线数值上**更忠实于 F16**（teacher 实验 49 vs 48 实证）。验收口径改为 teacher-forcing 一致率。

### 性能矩阵（decode tok/s，50 token × 3 次取中位，WSL2，p1 prompt）

| 配置 | tok/s | 倍率 | 读带宽反推 |
|---|---|---|---|
| naive F16 单线程 | 0.35 | 1× | 10 GB/s |
| **omp F16** | 3.67 | 10.5× | 12.6 GB/s |
| blas F32（OpenBLAS sgemv） | 1.45 | 4.1× | 9.9 GB/s（6.9GB F32 权重） |
| **omp Q4_K_M（主线）** | 3.27 | 9.3× | 0.34 GB/s（1.05GB）→ **已转为计算瓶颈** |
| llama.cpp CPU F16 | 14.15 | 40× | 49 GB/s |
| llama.cpp CPU Q4_K_M | 37.90 | 108× | 40 GB/s |

### 差距分解（本里程碑的核心产出）

1. **OpenMP 多线程 ×10.5**：访存瓶颈下 24 逻辑核摊到 ~10×，符合预期（带宽饱和而非线性）。
2. **BLAS 反证成立**：blas_f32 比 omp_f16 **慢 2.5×**（6.9GB vs 3.44GB，比值≈2 与字节数成正比）——
   用数字证明了"CPU 推理的答案不是 BLAS，是量化 + 融合 kernel"。**生产口径获验证。**
3. **Q4 未达预期反而略慢于 F16**（3.27 vs 3.67）：朴素 dequant 是标量运算且每行多写读一次
   F32 缓冲（6144×4B×2 次/行），**此时已转为计算瓶颈**，量化省的带宽没兑现。
   → 这正是"量化必须配融合 SIMD kernel 才有效"的教科书现象，被我们自己实测复现。
4. **与 llama.cpp 的差距（11.6× @Q4）归因**：AVX2 融合 dequant-dot kernel（寄存器内完成，
   无 F32 中间缓冲）+ Q8_K 激活整数量化点积 + cache 阻塞。这是 B6 手写 SIMD 的明确靶子。

### 目标达成判定

方案目标"主线 ≥ llama.cpp CPU Q4 的 50%（19 tok/s）"：**未达成（3.27 / 19 = 17%）**。
差距定位清晰且全部落在已声明留出的范围（SIMD intrinsics 留 B6/深入项）。
B5 的正确性资产（dequant 逐位对拍、bit 级并行回归、teacher 实验方法论）全部交付。
