## 0. 结论速览

| 决策 | 结论 | 一句话理由 |
|---|---|---|
| **推理 / 部署引擎** | **llama.cpp（GGUF）** | 唯一同时满足「Windows 原生 + 官方 Qwen3-VL 多模态 + 可控量化 + OpenAI API」的引擎 |
| **训练 / 评测引擎** | **保留 HuggingFace transformers** | LoRA 训练需要梯度、评测需要 logits 与灵活改 prompt —— llama.cpp 做不了 |
| **Ollama** | **可选演示壳，不作为学习主线** | 它把 mmproj / 量化等级 / 显存卸载这些**正是我们要学的细节**全藏起来了 |

| **MLC-LLM** | 暂缓 | 若 P8 要碰移动端再单独评估 |

> **核心判断**：**引擎选型不是选"最强"，是选"约束下最优"。**
> 面试里最容易失分的回答是"vLLM 最快，所以选 vLLM"——因为它同时错了两件事：
> ① 忽略了可运行性约束；② 忽略了"最快"是指**吞吐**，而单用户场景要的是**延迟**。

## 【① 这一步要解决什么】

P1 在链路里的位置：**P0 证明了"能跑"，P1 决定"以什么形态跑"**。

**不做这一步会发生什么（反面场景）**：
- **最贵的错误**：一路用 `transformers` 走到 P8 才想部署，结果发现想要 GGUF 量化、想要 OpenAI 兼容 API、想要 CPU 兜底，**整条服务层要推翻重写**。
- **第二贵的错误**：为了"上 vLLM"去装 WSL/Docker，在本机撞上安全策略，**花掉一整个晚上，最后什么都没跑起来**（而且这个问题已经在本次探测里被提前发现）。
- **面试层面的错误**：P1 是**最容易在面试里被追问的环节**。面试官几乎必问
  「你为什么选这个引擎」+「同模型同参数，不同引擎的 tok/s 差距从哪来」。
  答不出"约束驱动"，就暴露出你只是跟着教程跑通，没有工程判断力。

> P1 的真正产出**不是"跑起来了"**，而是 **① 可复用的性能测量台 + ② 一份能讲清取舍的选型依据**。

## 【② 核心原理】

### 2.1 第一性原理：推理引擎到底在优化什么？

一切从 **Prefill 与 Decode 的瓶颈不同**开始。

| 阶段 | 干什么 | 瓶颈类型 | 关键指标 | 优化手段 |
|---|---|---|---|---|
| **Prefill** | 一次性算完整个输入 prompt，生成 KV Cache | **compute-bound**（注意力是 O(L²)） | **TTFT** | FlashAttention、Chunked Prefill、Prefix Cache、变长批处理 |
| **Decode** | 逐个 token 生成，每次读一遍全部权重 | **memory-bound**（算术强度 ≈ 1 FLOP/Byte） | **TPOT / ITL** | PagedAttention、连续批处理、CUDA Graph、算子融合、**量化** |

**由此推出三类引擎的技术栈定位：**

```
① 框架级（HF transformers）
   ← 优化对象：灵活性。代价：Python 逐 token 循环、无 KV 分页、无算子融合
        ↓ 瓶颈：框架开销 > 真实计算时间

② 调度级（vLLM / SGLang / TensorRT-LLM）
   ← 优化对象：多请求并发下的显存利用率与 GPU 占用率
      核心：PagedAttention（KV 分页）+ Continuous Batching（连续批处理）
        ↓ 前提：必须有并发。单请求下几乎无收益

③ 内核 + 量化级（llama.cpp / GGUF）
   ← 优化对象：单请求的绝对速度 与 极致的资源占用
      核心：C++ 实现绕过 Python 循环、算子里程碑式融合、权重量化直接减少要读的字节数
        ↓ 优势：CPU/GPU 混合、消费级硬件、端侧
```

> **⭐ 最重要的一句话（面试必答）**：
> **"PagedAttention 不让任何单个请求变快，它让更多请求同时跑。"**
> 这是 vLLM 官方文档与多篇技术分析反复强调的定位[^1]。所以判断"该不该用 vLLM"的标准是
> **并发度**，不是"它快不快"。

[^1]: 出处：vLLM 相关技术分析（convly.ai《What Is vLLM》2026）；vLLM 官方文档平台支持矩阵。

### 2.2 本项目的六条硬约束（全部实测 / 已核实）

引擎选型的输入不是"哪个好"，而是"我有什么"。先把约束钉死：

| # | 约束 | 证据 | 影响 |
|---|---|---|---|
| **C1** | GPU 只有 **8188 MiB**，桌面占用 1.4GB，**可用 6.94 GB**；权重已占 3.96 GiB | **本机实测**（P0） | 大模型/高并发方案全部出局；量化是刚需 |
| **C2** | 操作系统 **Windows 11**；**WSL 被本机安全策略封禁**（`wsl.exe` 在黑名单，无法绕过）；**Docker 未安装** | **本机实测** | **vLLM / SGLang / TensorRT-LLM / LMDeploy 的所有 Windows 路径全部不可用** |
| **C3** | 模型是 **Qwen3-VL（多模态）**，视觉塔占 19.1% | **本机实测**（P0） | 引擎必须支持 **mmproj 双文件**架构 |
| **C4** | P8 要求 **GGUF 量化 + Ollama 部署**；P5 会产出 **LoRA 适配器** | plan.txt | 需要一条 `HF → merge → GGUF → quantize` 的工具链 |
| **C5** | P5 需 **LoRA 训练**、P7 需 **RAGAS 评测**（要 logits / 要改 prompt / 要算概率） | 规范 §11 | **必须保留一个可训练、可改前向的引擎**——llama.cpp 不能替代 |
| **C6** | 演示场景是 **单用户交互式**（FastAPI + Gradio），并发 ≈ 1 | plan.txt 阶段 8 | 调度级优化（PagedAttention/连续批处理）**收益接近于零** |

**约束 C2 是本次最关键的发现**：它把"要不要用 vLLM"这个看起来需要权衡的技术题，
变成了一道**有唯一答案的事实题**。这正是 §7「环境实测优先」的价值——
如果照搬网上的通用建议去装 vLLM，会在这一步浪费整晚。

### 2.3 候选引擎逐个分析

|---|---|---|---|---|---|

| **vLLM** | PagedAttention + 连续批处理 | ❌ 无原生包（仅 WSL2/Docker） | 部分支持 | 边际 | 仅知识储备 |

| **TensorRT-LLM** | 图优化 + 定制 kernel + FP8 | ❌ | 弱 | 边际 | 略过 |
| **LMDeploy** | TurboMind 引擎 | ❌ | 弱 | 边际 | 略过 |

### 2.4 排除过程（把约束代进去）

```
C2（Windows + WSL 封禁 + 无 Docker）
   └─→ 排除 vLLM / SGLang / TensorRT-LLM / LMDeploy        ← 决定性排除
C6（单用户，并发≈1）
   └─→ 即使能装，调度级优化几乎零收益 → 排除的"代价"也很低  ← 佐证，不是主因
C3（多模态，需 mmproj）
   └─→ ONNX Runtime GenAI 等对 VL 支持弱 → 排除
C5（要训练/评测）
   └─→ 必须保留 HF transformers                            ← 双引擎的必然性
C1 + C4（8GB + 要 GGUF 量化）
   └─→ llama.cpp 是唯一同时满足"可控量化 + 低显存 + Windows 原生 + VL 支持"的
```

**对 Ollama 的判断（需要展开说，因为很多人会直接选它）**：

| 维度 | Ollama | llama.cpp |
|---|---|---|
| 上手速度 | ✅ 更快（`ollama run`） | 需手动指定 `-m` / `--mmproj` |
| **显存精细控制** | ❌ **无等效 `--no-mmproj-offload`**（已核实：社区仍在提 issue 要求加） | ✅ 有 |
| **量化等级** | 部分封装，需自己导 GGUF | ✅ `llama-quantize` 任意等级 |
| **KV Cache 量化** | 受限 | ✅ `--cache-type-k / --cache-type-v` |
| **GPU 层数控制** | 自动 | ✅ `-ngl N` 显式 |
| **性能调参空间** | 小 | 大（`-b` `-ub` `-fa` `--mlock` …） |
| **对学习/面试的价值** | 低（黑盒） | **高（每一步都可解释）** |

> **结论**：Ollama **不是不能用**，而是**不该当作学习主线**。
> 它把 mmproj、量化等级、显存卸载这些**恰恰是面试要问的工程细节**包装成了黑盒。
> 正确用法：**用 llama.cpp 学会原理 → 用 Ollama 做 P8 的一键演示**（两者底层同源，学会一个就懂另一个）。

### 2.5 最终架构：双引擎分工（不是二选一）

```
                  ┌─────────────────────────────────────────┐
   P2 语料解析 ───→│  HF transformers 侧（训练 + 评测）        │
   P3 数据构造     │  · LoRA 训练（要梯度）                    │
   P5 微调     ───→│  · RAGAS 评测（要 logits / 要改 prompt）  │
   P7 评测         │  · 「无检索基线」对照（P0 已建好测量台）    │
                  └────────────────┬────────────────────────┘
                                   │  merge LoRA
                                   │  convert_hf_to_gguf.py
                                   │  llama-quantize  (+ mmproj)
                                   ▼
                  ┌─────────────────────────────────────────┐
   P1 引擎选型 ───→│  llama.cpp 侧（推理 + 部署）              │
   P8 部署         │  · llama-mtmd-cli  命令行多模态推理        │
                  │  · llama-server    OpenAI 兼容 API + WebUI │
                  │  · 量化等级 / KV 量化 / -ngl 卸载 全可控    │
                  └─────────────────────────────────────────┘
```

**为什么这比"选一个"更好（面试加分点）**：
两个引擎服务的**需求本质不同**——一个是**可微、可改**（训练/评测），一个是**极致执行效率**（推理/部署）。
把它们的职责混在一起，只会得到一个"哪边都不够好"的方案。
**能主动讲出"引擎按链路分层"而不是"挑一个最强的"，是明确的加分回答。**

### 2.6 GGUF 与 mmproj 的工程细节（面试高频）

#### (a) 为什么 VL 模型要拆成两个 GGUF？

已核实：官方 `Qwen/Qwen3-VL-2B-Instruct-GGUF` 明确说
> "split into two components: **Language model (LLM)**: FP16, Q8_0, Q4_K_M；**Vision encoder (`mmproj`)**: FP16, Q8_0"

拆开的四个理由：
1. **量化敏感度不同**：语言侧是 1.72B 参数、大量均匀的 FFN 权重，压到 4bit 掉点可控；
   视觉塔只有 0.41B，本身已很小，**压它省不下多少，却可能让整条视觉链路掉点**。
   → 社区实践（VLM-MCP 等）明确建议 **mmproj 用 F16，不要量化**。
2. **使用场景分离**：纯文本 RAG 主链路**可以完全不加载 mmproj**，省 ~0.45–0.9 GB 显存和一次加载。
3. **精度可自由组合**：官方原话 "You can **mix precision levels** for the language and vision components"。
   → Q4_K_M 语言侧 + F16 视觉侧 是最常见的"省显存不掉能力"组合。
4. **工程解耦**：视觉塔换成更高分辨率的变体时，不必重转整个语言模型。

#### (b) 量化等级的命名与含义

```
Q4_K_M
 │ │ │
 │ │ └── M = Medium：不同张量用不同等级（"混合"），关键张量保更高精度
 │ └──── K = k-quants：分块量化（super-block 内再分子块，分层 scale）
 └────── 4 = 权重约 4 bit
```

**k-quants 相比老式 Q4_0 为什么更好**：
- `Q4_0`：每 **32** 个权重一个 scale（单层缩放）；
- `Q4_K`：**super-block 256 个权重** → 切成 **8 个子块（每个 32 个）**，
  子块各有 scale，super-block 再有一个全局 scale/min，scale 本身用 6-bit 存。
- 效果：**分层缩放**显著降低离群值（outlier）对整块量化的破坏。这就是 `Q4_K_M` 常被标为
  **"fast, recommended"** 而 `Q4_0` 逐渐被冷落的原因。

**为什么某些张量要更高精度**：实测与社区共识是 `attn_v`（value 投影）和 `ffn_down`
对量化更敏感——它们直接决定残差流的信息保真度。`_M` 后缀就是"对这些张量抬档"的意思。

#### (c) 已核实的量化体积（社区仓库文件大小，2B）

| 文件 | 体积 | 说明 |
|---|---|---|
| `Qwen3-VL-2B-Instruct-F16.gguf` | **3.45 GB** | 16 bpw，overkill |
| `Qwen3-VL-2B-Instruct-Q8_0.gguf` | **1.83 GB** | "fast, best quality" |
| `Qwen3-VL-2B-Instruct-Q4_K_M.gguf` | **1.2 GB** | "fast, recommended" |
| `mmproj-f16.gguf` | **0.819 GB** | 建议不量化 |
| `mmproj-q8_0.gguf` | **0.445 GB** | 省显存可选 |
| （对照）HF bf16 全量 | **4.25 GB**（3.96 GiB） | **P0 本机实测** |

**从体积推到吞吐上限**（decode 阶段每个 token 要把语言侧权重读一遍）：

| 配置 | 语言侧权重 | vs HF bf16 | 带宽推算上限（÷） | 备注 |
|---|---|---|---|---|
| HF bf16（P0 基线） | 4.25 GB | 1.0× | **60.2 tok/s** | **实测 24.36 tok/s → 利用率 40.5%** |
| Q8_0 | 1.83 GB | 2.3× | ~140 tok/s | — |
| Q4_K_M | 1.2 GB | **3.5×** | ~213 tok/s | — |

> ⚠️ **以上除 HF 基线外全部是推算，不是实测。**
> 假设：256 GB/s 带宽（规格值，**未本机实测**）、且**纯带宽受限**。
> 实际必然达不到——因为 ① 真实带宽低于规格值；② 吞吐升高后 kernel 效率反而下降；
> ③ KV Cache 读写、采样、调度开销会随 token 数线性累加。
> **"推算 3.5× 能拿到多少"正是 P1 要回答的第一个问题。** 先把预期写下来，再让实测打脸或验证。

## 【③ 代码 / P1 实验设计】

### 3.1 P1 要产出什么

**一个可复用的性能测量台**（`scripts/p1_bench.py` + `src/bench.py`），而不是几条一次性命令。
原因：§5.9 要求任何性能数据必须**成对报告延迟与吞吐**、必须给 **P50/P99**、
必须**声明"只改了一个变量"**。这些只有做成 harness 才能保证。

### 3.2 实验矩阵（每组只改一个变量）

| 组 | 变量 | 取值 | 固定项 |
|---|---|---|---|
| **E1** | 引擎 | HF / llama.cpp | 模型、prompt、输出长度、解码参数 |
| **E2** | 量化等级 | Q8_0 / Q6_K / Q4_K_M / Q4_K_S | llama.cpp、mmproj=F16 |
| **E3** | mmproj 精度 | F16 / Q8_0 | llama.cpp、LLM=Q4_K_M |
| **E4** | GPU 层数 `-ngl` | 0 / 全部 / 中间值 | llama.cpp、Q4_K_M |
| **E5** | KV Cache 量化 | f16 / q8_0 | llama.cpp、Q4_K_M |
| **E6** | 多模态 vs 纯文本 | 有图 / 无图 | 同模型同量化，测视觉塔的前向开销 |

**每组测量项**（缺一不可）：
- `TTFT`、`TPOT`/`ITL`、`E2E`（延迟）
- `tok/s`（吞吐，**必须标注 batch=1**）
- **P50 / P99**（不只是均值）
- **显存峰值**（`nvidia-smi` 与进程内双信源交叉校验，沿用 P0 的断言）
- 负载后的**输出质量抽检**（多模态用例是否仍能读对合成图的轴标签与目标数——**用 P0 的自建图做回归**）

### 3.3 安装与运行命令（待批准后执行）

```powershell
# ① 安装 llama.cpp（Windows 原生，走 winget）
winget install llama.cpp
# 若 winget 源不可用，回退：从 github.com/ggml-org/llama.cpp/releases 下载
#   llama-<build>-bin-win-cuda-12.x-x64.zip（CUDA 版），解压后把目录加入 PATH

# ② 下载 GGUF（注意：本机 HF_ENDPOINT 已是 hf-mirror.com）
#    建议先用 Q4_K_M + mmproj-F16 组合
#      语言侧 ~1.2 GB + 视觉侧 ~0.82 GB ≈ 2.0 GB

# ③ 多模态命令行推理（验证 VL 通路）
llama-mtmd-cli `
  -m  <path>\Qwen3-VL-2B-Instruct-Q4_K_M.gguf `
  --mmproj <path>\mmproj-f16.gguf `
  --image reports\p0_synthetic_rd_map.png `
  -p "这张图里有什么？请描述坐标轴标签和曲线形状。" `
  -n 512 --temp 1.0 --top-k 40 --top-p 1.0

# ④ OpenAI 兼容服务（后续 P6/P8 直接用）
llama-server `
  -m  <path>\Qwen3-VL-2B-Instruct-Q4_K_M.gguf `
  --mmproj <path>\mmproj-f16.gguf `
  -ngl 99 --ctx-size 8192 -fa `
  --host 127.0.0.1 --port 8080
# 浏览器打开 http://127.0.0.1:8080 即为内置 WebUI；
# 接口 http://127.0.0.1:8080/v1/chat/completions
```

> 用 **P0 的合成距离-多普勒图**做验证图是关键设计：它的真值是写死的（3 个目标、轴范围 0–100km / ±500Hz），
> 所以能**客观判断量化有没有把视觉能力打坏**，而不是"看起来还行"。

### 3.4 预算预告（§2 要求 >500MB 需你点头）

| 项 | 体积 | 说明 |
|---|---|---|
| llama.cpp CUDA 预编译包 | ≈ 300–500 MB | 解压后约 1 GB |
| Qwen3-VL-2B Q4_K_M GGUF | ≈ 1.2 GB | 主推 |

### Q1. Ollama 和 llama.cpp 是什么关系？你为什么不用 Ollama？

**答题骨架**
1. **关系**：Ollama 是 **llama.cpp 的上层封装**（模型管理 + 守护进程 + CLI + 自动显存管理）。
   底层推理还是 GGML/llama.cpp 的 kernel，所以**性能上限同源**。
2. **封装带来什么代价**：它把参数暴露面收窄了。具体可举例：llama.cpp 有
   `--no-mmproj-offload`（禁止把视觉投影器卸载进显存），**Ollama 至今没有等效开关**（社区仍在提 issue）。
3. **选择理由**：我的场景是**学习 + 需要能解释每一步**，而不是"最快跑起来"。
   需要显式控制量化等级、`-ngl` 卸载层数、KV Cache 数据类型、mmproj 精度——这些在 Ollama 里要么被自动决策、要么无法触及。
4. **诚实补充**：Ollama 在"交付一个能演示的东西"上确实更好，所以我把它定位成 **P8 的演示壳**，而不是学习主线。

**追问方向**
- *"那 Ollama 有什么优势？"* → 模型管理/多版本切换/一键启动/Modelfile 可复现环境，**团队交付**比个人研究更看重这些。
- *"既然同源，性能会有差别吗？"* → 底层 kernel 相同，差别来自**默认参数**与**打包版本**（Ollama 的 llama.cpp 版本常落后上游）。**这需要实测，不能想当然。**
- *"你会怎么公平地比这两个？"* → 同量化等级、同 `-ngl`、同 ctx、同 prompt 与输出长度，各跑 3 次取 P50。

**加分回答**：主动说"**我不把 Ollama 当对手，把它当前端**"——这正是工程上常见的
「底层引擎 + 上层平台」分层，能体现你不做非此即彼的技术站队。

### Q2. VL 模型为什么要拆成 LLM + mmproj 两个 GGUF？mmproj 为什么常建议不量化？

**答题骨架**
1. **拆分的本质**：GGUF 里语言侧和视觉塔是**两套参数量级、两套敏感度、两套使用场景**的权重。
   官方 `Qwen3-VL-*-GGUF` 明确拆成 `LLM`（FP16/Q8_0/Q4_K_M）+ `mmproj`（FP16/Q8_0），并说明**可以混精度**。
2. **为什么 mmproj 通常不量化**：
   - **收益小**：2B 模型的视觉塔只有 **406.9 M 参数**（P0 实测，占 19.1%），F16 也才 ~0.82 GB；
   - **风险大**：视觉特征是**整条多模态链路的入口**，量化误差会沿 attention 放大；
     而且视觉塔没有语言侧那种海量均匀 FFN，**离群值更难压**。
   - → 社区实践的结论是"**mmproj must be F16, do not quantize**"。
3. **工程收益还有一个**：纯文本 RAG 主链路可以**完全不加载 mmproj**，直接省下显存。

**追问方向**
- *"那为什么还有 mmproj-q8_0 版本？"* → 给 8GB 以下机器留余量；**是否可用必须用任务级评测验证**，不能假设。
- *"视觉 token 会不会进 KV Cache？"* → 会。196 个视觉 token × 112 KiB/token ≈ **21 MiB/图**（按 P0 实测的 KV 公式）。
  多图/高分辨率时**平方增长**（448→896 分辨率，视觉 token 196→784）。
- *"你怎么验证量化没打坏视觉能力？"* → **用真值已知的合成图做回归**（P0 已建好：3 个目标 + 轴范围写死）。

**加分回答**：指出"**量化评估的粒度应该跟风险粒度对齐**"——
语言侧可以整体看指标，但视觉侧要看**细粒度任务**（OCR 数字、坐标读值），
因为平均指标会掩盖"轴标签读错"这种致命退化。

### Q3. `Q4_K_M` 里的 K 和 M 分别是什么意思？为什么有的张量要用更高精度？

**答题骨架**
1. **K = k-quants**：分块量化。老式 `Q4_0` 每 **32** 个权重一个 scale；`Q4_K` 用
   **super-block（256 个权重）→ 8 个子块（每个 32 个）** 的两级结构，
   每个子块有自己的 scale，super-block 再有全局 scale/min，scale 以 6-bit 存储。
   **分层缩放降低了离群值对整块的破坏**。
2. **M = Medium**：**混合精度策略**。同一文件内不同张量用不同量化等级，
   对量化敏感的张量档位更高。
3. **哪些张量敏感**：`attn_v`（value 投影）与 `ffn_down` 常被抬档——
   它们处在残差流的关键通路上，误差会被逐层累积。
4. **这套命名的工程意义**：它把"**每 bit 花在哪最值**"做成了一个可选的旋钮，
   让 4-bit 在有限体积下尽量逼近 6-bit 的质量。

**追问方向**
- *"Q4_K_S 和 Q4_K_M 差在哪？"* → S=Small，抬档的张量更少、体积更小、质量略低。
- *"为什么不用 IQ-quants？"* → IQ（i-quants）用**码本/网格**逼近更优的量化格点，
  同体积下质量常更好，但**解码更慢**（需要查表）。是"质量 vs 速度"的又一档权衡。
- *"量化到 2bit 会怎样？"* → 语言侧尚可勉强跑，但**推理/数学能力会显著崩**；
  本题讨论的雷达公式推导类任务对精度敏感，**不建议低于 Q4**。

**加分回答**：把量化和 **memory-bound** 联系起来——
"decode 时每 token 要读一遍全部语言侧权重，**字节数就是延迟**。
Q4_K_M 把 4.25 GB 压到 1.2 GB（**3.5×**），理论上限直接抬 3.5 倍。
所以**量化对 decode 是'换个量纲'级别的优化，不是微调**。"

### Q4. 量化为什么对 decode 收益巨大，对 prefill 却收益有限？

**答题骨架**
1. **两者瓶颈不同**：Prefill 是 **compute-bound**（大矩阵乘 + O(L²) attention），
   Decode 是 **memory-bound**（每 token 读全部权重，算术强度 ≈ 1 FLOP/Byte）。
2. **量化改变的是什么**：量化减少的是**权重的字节数**，也就是**访存量**。
   - Decode 的时间几乎正比于访存量 → **量化直接线性加速**；
   - Prefill 的时间主要由算力决定，权重访存只在加载时占一小部分 → **收益有限**。
3. **推论**：所以 W4A16（只量化权重、激活保持 16bit）在**对话/长输出场景**是性价比最高的方案；
   而长 prompt 的 RAG 场景，**光靠量化救不了 TTFT**，得靠 FlashAttention、前缀缓存、Chunked Prefill。
4. **这也是我项目里的实测靶子**：P0 实测 HF 只跑到带宽上限的 40.5%，
   说明**当前瓶颈甚至不是带宽，而是框架开销**——所以 P1 的首要变量是"换引擎"，其次才是"降精度"。

> **这段是本项目最漂亮的一条推理链，面试时可以直接讲**：
> 不是"量化越快越好"，而是**先定位瓶颈在带宽还是算力还是框架开销，再决定优化手段**。

**追问方向**
- *"RAG 长上下文该怎么优化？"* → ① 前缀缓存（system prompt + 检索模板固定 → 复用其 KV）；
  ② Chunked Prefill 避免长 prompt 独占 GPU；③ KV Cache 量化（`--cache-type-k/v q8_0`）省一半显存换并发；
  ④ 减少 chunk 数/长度，从源头降低 prefill 成本。
- *"KV Cache 量化有风险吗？"* → 有。KV 是每 token 都参与 attention 的活跃数据，
  q8_0 通常安全，更激进（q4_0）在长上下文会明显掉点。**必须实测。**

**加分回答**：主动区分 **"带宽受限"与"框架开销受限"**，并说出**如何判断**：
如果实测吞吐远低于 `带宽 ÷ 权重体积`，说明瓶颈不在带宽；
此时换更小的量化收益有限，**换实现（C++ 引擎）才是解**。

### Q5. 8GB 显存怎么把模型塞进去？`-ngl` 你会怎么定？

**答题骨架**
1. **先算账**（P0 实测口径）：权重 1.2 GB（Q4_K_M）+ mmproj 0.82 GB + KV Cache + 框架开销。
   KV = `2 × 层数 × KV头数 × head_dim × 序列长 × batch × dtype` = **112 KiB/token**（bf16, 本模型实测）。
2. **`-ngl N` 是"把前 N 层放 GPU"**：不是全部放 GPU 就最好——因为要同时给
   KV Cache 和 mmproj 留显存。放太多层会挤掉 KV，反而限制可用上下文。
3. **决策顺序**：先定**目标上下文长度**（RAG 需要 4–8K）→ 算出 KV 需求 →
   剩余显存给权重 → 由此反推 `-ngl`。
4. **兜底手段**（按代价排序）：`--no-mmproj-offload`（视觉塔留 CPU）→ KV 量化 → 降 `-ngl` → 更低量化等级。

**追问方向**
- *"KV 量化能省多少？"* → f16→q8_0 约省一半 KV 显存；这是**换并发数**最便宜的一招。
- *"mmproj 放 CPU 有什么代价？"* → 图像前向变慢（据报道从几百毫秒到数秒），
  但**语言侧获得了更多显存**。是典型的"吞吐/延迟换容量"。
- *"为什么笔记本更麻烦？"* → **热节流**：功耗墙 95W（本机 `nvidia-smi` 实测），
  持续负载会降频，导致 P99 明显劣化。所以**必须报 P99，不能只报均值**。

**加分回答**：强调"**先定 SLO，再定参数**"——
`-ngl` 不是调出来的，是从"要支持多长上下文 + 多快"**倒推**出来的。

### Q6. 为什么 PagedAttention 在你的场景没有意义？

**答题骨架**
1. **PagedAttention 解决的是显存碎片**，不是计算速度：KV Cache 预分配整块会浪费 60–80% 显存。
   分页后按需分配，**让更多序列能同时驻留**。
2. **关键一句**：**"它不让任何单个请求变快，它让更多请求同时跑。"**
   → 收益正比于**并发度**。我的场景并发 ≈ 1，收益 ≈ 0。
3. **连续批处理同理**：它是提升 GPU 在**多请求交错**下的占用率；
   单请求时 GPU 本来就"只服务你一个"，没有别的东西可塞。
4. **诚实补充**：如果未来要做**多用户服务**（例如 P8 上线给同学试用），
   vLLM 就会重新变得有意义——**技术选型要跟着场景走，不是跟着热度走**。

**追问方向**
- *"那你为什么还要学 vLLM？"* → ① 面试必问；② 它是理解"KV Cache 管理"这个概念最好的载体；
  ③ 我确实需要知道**在什么条件下该切过去**。
- *"Prefix Caching 和 PagedAttention 是一回事吗？"* → 不是。PagedAttention 是**内存管理机制**，
  Prefix Caching 是**复用它**的应用（SGLang 的 RadixAttention 用基数树做前缀复用），
  两者常配合但不是同一层的东西。
- *"RAG 场景里前缀缓存有用吗？"* → **非常有用**：system prompt + 检索模板 + 固定指令是共享前缀，
  多轮对话里前面的 KV 可以直接复用 → 直接降低 TTFT。

**加分回答**：把选型讲成**一张二维图**：
横轴是**并发度**，纵轴是**单请求延迟要求**。
低并发 + 低延迟 → llama.cpp；高并发 → vLLM/SGLang。
**能主动给出"什么时候该换回来"的判据，比只说"我选 llama.cpp"强得多。**

### Q7. 你怎么评估量化掉点？（这一题答错会暴露外行）

**答题骨架**
1. **明确反对**："只看困惑度（PPL）是不够的，甚至是误导的。"
   PPL 对**任务能力**的退化不敏感——尤其量化常先坏掉的是**格式遵循、长链推理和细粒度读取**。
2. **正确做法是分层评测**（对应我项目规范 §5.5）：
   - **任务级指标**：本项目是雷达问答的**忠实度 / 引用正确率 / 答案相关性**；
   - **规则级指标**：格式合规率、拒答率、**引用是否指向真实 chunk**；
   - **能力回归**：用**真值已知的自建测试**（P0 的合成图：3 个目标 + 轴范围）；
   - **对照纪律**：同一批固定 prompt、同解码参数、**多次重复**。
3. **本项目特有的一条**：多模态场景要**单独测视觉侧**（OCR 数字、坐标读值），
   因为平均分会掩盖"轴标签读错"这类致命退化。
4. **诚实补充**：2B 模型本身能力弱，**量化掉点可能被基座噪声淹没**——
   所以对比必须用**同一批样本 + 配对比较**，不能比"平均分"。

**追问方向**
- *"那 perplexity 还有什么用？"* → 快速冒烟、判断是否量化到崩坏（比如 2bit 会 PPL 暴涨）；
  但它**不能替代任务级评测**。
- *"你会用 LLM-as-judge 吗？"* → 会，但本地 2B 当裁判噪声大，这会引入**新的不确定性**，
  所以我的评测设计里把它当**辅助**，主判据是任务级规则指标 + 人工抽检。

**加分回答**：说出"**量化掉点要配对比较、不能比平均分**"，
以及"**评测集必须在微调前冻结**"（否则等于自己出题自己满分）。

### Q8. LoRA 微调完之后，怎么变成 GGUF？中间有哪些坑？

**答题骨架**
1. **两个方案**：
   - **方案 A（推荐）：先 merge 再转换**
     `merge_and_unload() → HF 全量权重 → convert_hf_to_gguf.py → f16 GGUF → llama-quantize → Q4_K_M`
   - **方案 B：llama.cpp 直接加载适配器**（`--lora <adapter>` / `export-lora`）
     省一次转换，但**对模型架构覆盖面窄、调试困难**。
2. **为什么推荐 A**：① 只有一条路径要维护（量化也只做一次）；
   ② 中间产物（f16 GGUF）可复现、可回溯；③ 与 VL 的 mmproj 流程统一。
3. **坑点清单**：
   - **merge 必须用 bf16 或 fp32**，用低精度合并会引入误差；
   - **视觉塔要一起正确导出**（本模型 `model.visual.*` 命名需被转换脚本识别）——
     所以**先确认 convert 脚本支持该架构，再开训**，否则 P5 白干；
   - **词表对齐**：P0 实测本模型有 **151936 / 151669 / 151643 三值不一致**，
     转换时若按 `config.vocab_size` 走而 tokenizer 不同，会**静默错位**（§4.6 高危项）；
   - **mmproj 必须单独转**，不能塞进语言侧文件。

**追问方向**
- *"merge 的数学是什么？"* → `W' = W + (α / r) · B·A`。
  `B`（零初始化）与 `A`（随机初始化）是低秩矩阵，`r` 是秩，`α` 是缩放。
  **推理时 merge 是等价的**（线性可加），而训练时必须分开以省显存。
- *"rank 怎么选？"* → `r` 越大容量越强但越易过拟合且越慢。8–32 是常见区间；
  本项目是**领域适配**（术语 + 格式 + 引用规范），不是学新知识，**不需要大 rank**。
- *"LoRA 该打在哪些模块上？"* → 通常 `q/k/v/o_proj` 与 `gate/up/down_proj`。
  **本项目明确冻结视觉塔**（P0 实测它占 19.1% 参数，而我们的 SFT 数据是文本问答，
  训它等于用噪音污染 406.9 M 参数）。

**加分回答**：主动指出"**转换链路的每一环都可能静默错位，所以必须用断言守护**"——
词表三值不一致就是最好的例子（P0 已实测）。

### Q9. 同一个模型、同一份参数，换个引擎快好几倍，差距从哪来？

**答题骨架（按贡献排序）**
1. **Python 调度开销**（HF 侧最致命）：
   `generate()` 是**逐 token 的 Python 循环**，每步都要经过 Python 解释器 + 多次 kernel 派发。
   小 batch 时 kernel 只跑几十微秒，**CPU 下发指令的时间与之同量级**。→ C++ 引擎直接消除这项。
2. **算子融合**：RMSNorm+残差、RoPE、SwiGLU 在 HF 里是多个独立算子，
   每个都要读写一次 HBM；融合后中间结果留在寄存器/SRAM，**省的是带宽**。
3. **CUDA Graph**：把一串 kernel 启动录制成图，回放时一次提交，消除逐 kernel 的 CPU 开销。
   代价是要求**静态 shape**（需 padding/分桶）。
4. **量化**：直接减少要读的字节数（见 Q4）。
5. **KV Cache 管理**：更紧凑的布局、量化、复用。

**本项目已经拿到的实证**：P0 实测 HF **24.36 tok/s**，而带宽推算上限 **60.2 tok/s** →
**利用率仅 40.5%**。这意味着"当前瓶颈大概率不是带宽，而是 1/2/3 那三项框架开销"。
**所以 P1 的正确实验顺序是：先换引擎（E1），再调精度（E2）** ——
顺序错了，就会把"框架开销"误判成"精度不够"，然后做出错误的优化决策。

**追问方向**
- *"你怎么证明瓶颈在哪一项？"* → ① 对比"实测吞吐 / 带宽上限"的比值；
  ② 换引擎前后同条件对照；③ 用 profiler（`ncu`）看 DRAM 利用率与 kernel 间隔。
- *"那为什么不干脆一步到位上 TensorRT-LLM？"* → 它需要**为特定 shape 编译 engine**，
  迭代成本极高；且对 VL 支持弱、Windows 不可用。**优化收益要除以迭代成本才是真实性价比。**
- *"你怎么保证对比公平？"* → **只改一个变量** + 固定 prompt/输出长度/解码参数 + **3 次重复** + **报 P50/P99**。
  这正是我 P1 要建那个测量台的理由。

**加分回答**：说出"**先定位瓶颈，再选手段**"这条方法论，
并举自己项目里的例子（40.5% 利用率 → 先换引擎而不是先量化）。
**这是把"我知道很多引擎"升级为"我会做工程判断"的关键一步。**
