# 阶段 B · B12 详细方案：int8 MMA（tensor core）prefill

> 状态：**方案，待确认**（2026-10-11）
> 上游：`docs/34`（B11，int8 激活 + dp4a）、`docs/35` §2（本项在路线图中的位置）
> 一句话：**把 prefill 的 Q4_K dp4a 换成 int8 tensor core MMA，走完 B11 未达标的 D3。**

---

## 0. 为什么做这一项

### 0.1 B11 的 D3 未达标，且已证明**在 dp4a 路线上不可达**

| 项 | 结果 |
|---|---|
| D3 目标 | prefill ≥ 1000 tok/s |
| D3 实测 | 同会话配对 **1.43–1.53×**（701 vs 459 tok/s） |
| dp4a 管道上限 | **2.00×**（实测，`docs/34` §7.1） |

结论：dp4a 的通道宽度决定了这条路的天花板。要过 1000 tok/s，必须换管道。

### 0.2 本机实测：MMA 是 dp4a 的 **4×**（`dsh_scratch/mma_probe.cu`）

单波次（每 SM 恰好一个块）、三轮轮转取最小值：

| 管道 | MAC/SM/clk | vs FFMA | vs dp4a |
|---|---|---|---|
| FP32 `FFMA` | 113.8 | 1.00× | 0.44× |
| INT8 `dp4a` | **256.0** | 2.25× | 1.00× |
| INT8 `IMMA` | **1023.9** ≈ 1024 | **9.00×** | **4.00×** |

- SASS 实测下发 `IMMA.16832.S8.S8.SAT`（sm_89 原生支持，已被 ptxas 接受）
- 正确性 sanity：全 `1` 的 int8 操作数 → `D[0] = 32`（32 个 1×1）✓
- `dp4a = 256.0` = 64×4，**独立复现了 `docs/34` §7.1 的 2.00× 天花板**（256/128）
- 两个数字都落在硬件精确宽度上（256、1024），**不是探针虚高**

### 0.3 ⭐ 与 B11 的关键区别：这一项**风险低得多**

B11 换的是**数值路线**（fp32 激活 → int8 激活），所以它必须自建三层对拍。
B12 换的只是**算这条乘加用的指令**：

> MMA 的累加是 **int32 精确整数**，与 dp4a 逐位相同。
> 只要 fp32 尾声（`d4*sumf_d - dmin*sumf_m`、`__fmul_rn`/`__fadd_rn`、sub-block 升序）不变，
> **结果逐位相同**。

⇒ B11 钉死的 Q8_1 语义、独立 NumPy 参考、`cpp/tests/int8_ref/` 的 24 个 golden payload
**全部直接复用**。本项**预期保持 Tier A**（`docs/35` §0）。

## 2. 现状与数据

### 2.1 要改的东西

B11 之后的 prefill 路径（`cpp/src/gpu_model.cu`）：

```
prefill_chunk(pos_base, nr, slot)        # nr ≤ MAX_MC = 16
  └─ gemv_prefill(w, x, y, in, out, ncol)
        ├─ quantize_q8_1(x, d_q8s, d_q8ds, in, MAX_MC, stream)   # 激活 → Q8_1
        └─ gemv_q4k_q8_1_tile(...)                                # ← 本项替换这里
```

### 2.2 ⭐ 三个硬约束（都是实测/推导出来的，比"换指令"更关键）

#### (a) 权重重复读：T=16 的 chunk 把权重读了 103 次

`prefill_chunk` 是**外层循环**：每个 16-token chunk 都要把全部权重从 DRAM 走一遍。
Q4_K_M 权重 ≈ 1.18 GB，L2 只有 24 MB（命中率 ~2%），所以：

```
每 chunk 权重流量 = 1.18 GB × 103 chunk = 121 GB
带宽下限 = 121 GB / 256 GB/s ≈ 473 ms
```

B11 的 dp4a 只跑在 ~69 GB/s（17 ms/chunk），远未触及带宽，所以**这条约束在 B11 不显现**。
但 MMA 把算术时间砍 4× 之后，**473 ms 会成为新的地板**。

#### (b) ⭐ 权重解包开销：T=16 会吃掉 86% 的 INT32 管道（**已实测，见 §7.1**）

Q4_K 的权重是 4 bit，而 MMA 的操作数必须是 int8。**不能在显存里物化成 int8**
（体积 0.5 B → 1 B，流量翻倍，直接撞上约束 (a)），只能在寄存器/shared 里**现场解包**。

一个 16-bit 字里的 4 个 nibble 展开成 4 个 int8 需要 `c` 条 INT32 指令，
**`c` 是实测出来的（§7.1 测得 `c = 1.77`），不是估的**：
计划阶段估的是 0.75，实测翻了一倍多 —— 编译器生成的是"3 次移位 + 若干 `LOP3`"，
而不是单条 `PRMT` 技巧。解包结果可按 N 方向复用 `T/8` 次（MMA 的 N=8 列），于是：

```
解包占用 INT32 管道的比例 = c × 1024 / (64 × T) = 16c / T = 28.3 / T   (c = 1.77)
```

| chunk T | 解包占用（模型 28.3/T） | **实测合并吞吐**（§7.1） | 结论 |
|---|---|---|---|
| 16（当前） | 177% | **550.6 MAC/SM/clk = 天花板的 53.8%** | 解包是主导瓶颈 |
| 32 | 88% | 821.7（80.3%） | 拐点，收益已经拿到大半 |
| 64 | 44% | 854.5（83.5%） | 边际收益变小 |
| 128 | 22% | 913.0（89.2%） | 基本到顶 |

> ⚠️ **模型在 T 小时高估**：实测开销 T=8 是 199%（模型 354%）、T=16 是 86%（模型 177%）。
> 原因是 INT32（解包）与 tensor core（MMA）是**两条独立管道，可以重叠**，
> 所以开销不是简单相加。**趋势对，绝对值要用实测。**

> ⭐ **结论（已按实测修正）**：解包这条约束要求 **T ≥ 32**（不是原估的 64），
> 且 T=32 之后边际收益迅速变小。所以 **T 的选择不该由解包决定**，而应看约束 (a) 的带宽。
> 两条约束的交点见 §7.2。

#### (c) `MAX_MC = 16` 是多个机制的共享常量

`MAX_MC = 16` 同时是：KV 块大小（`BLOCK`）、prefill chunk 宽度、dp4a tile 宽度、
int8 激活缓冲的 `ncol`（`d_q8s[MAX_MC][q8_k]`）、以及 `max_batch` 上限。
放大它要一并核对：激活缓冲显存、`d_scores`（`kv_cap × n_head × max_batch`）、
padding-scratch 槽位逻辑、以及 B8 的"断长连续批"行为。

### 2.3 时间账（T≈1645，B11 实测，每 chunk）

| 部分 | fp32 | B11 (dp4a) | 每 chunk |
|---|---|---|---|
| prefill GEMM | 29.2 ms | 17.0 ms | 103 chunk |
| attention | 5.7 ms | 5.7 ms | 103 chunk |
| 合计 | 34.9 ms → 459 tok/s | 22.9 ms → **701 tok/s** | — |

**注意 attention 的占比**：B11 之后 attention 已占 42%（5.7 / 13.5... 实际 5.7/22.9 = 25%，
按"GEMM 之外的固定成本"看则是 5.7 ms 对 22.9 ms）。
MMA 把 GEMM 砍到 ~4–6 ms 后，**attention 会成为主要项** ⇒ B12 与 B14（attention 重写）
需要一起看才能过 1000。

## 3. 设计

### 3.1 范围控制

- **只改 `prefill_chunk` 的 Q4_K GEMM 派发**；Q6_K 本轮仍走 fp32/dp4a（与 B11 同决策）
- decode 路径、F16 路径、attention 一律不动
- 新 kernel 独立文件 `gpu_mma.cu`，不动 B11 的 `gpu_quants.cu`（保证可回滚）

### 3.2 数值语义（**必须与 B11 逐位相同**）

MMA 的指令形状 `m16n8k32`：

```
D(16×8, int32) = A(16×32, int8) · B(32×8, int8) + C(16×8, int32)
```

映射到我们的问题：

| 维度 | 含义 | 值 |
|---|---|---|
| M = 16 | 输出行（`out_features` 的 16 个） | 16 |
| N = 8 | token 列 | 8（T/8 个 N-tile） |
| K = 32 | **一个 Q4_K sub-block** | 32 |

⇒ **一条 MMA 正好覆盖一个 sub-block 的 16 行 × 8 列**，和 B11 的逐 sub-block 循环一一对应。

逐位相同的三个条件（缺一不可）：

1. **`dot1_j` 精确**：MMA 输出 int32 精确整数，与 B11 的 dp4a 累加**逐位相同** ✓
   （Q4_K 的 4-bit 值作非负 int8、Q8_1 作有符号 int8；32 项最大 15×127×32 = 60960，不溢出）
2. **`sum_q` 复用**：`dot2_j = Σ q8 = sum_q` 仍取自 B11 的 `Q8_1Ds`（MMA 不负责这一项）
3. **fp32 尾声顺序不变**：`sumf_d = Σ_j d8_j * f32(dot1_j*sc_j)`、
   `sumf_m = Σ_j d8_j * f32(sum_q_j*m_j)`、`part = d4*sumf_d - dmin*sumf_m`、`acc += part`
   —— 全部用 `__fmul_rn`/`__fadd_rn`，j 升序（与 `docs/34` §3.2.1 一致）

### 3.3 分片布局与数据流

`m16n8k32` 的寄存器分片（`groupID = lane>>2`，`tig = lane&3`）：

| 分片 | 寄存器 | 内容 |
|---|---|---|
| A（16×32，row） | 4 × int32 | `a0`: 行 `groupID`、k 字节 `[tig*4, +3]`；`a1`: 行 `+8`；`a2/a3`: k 字节 `+16` |
| B（32×8，col） | 2 × int32 | `b0`: k 字节 `[tig*4, +3]`、列 `groupID`；`b1`: k 字节 `+16` |
| C/D（16×8） | 4 × int32 | `c0`: 行 `groupID`、列 `tig*2`；`c1`: 列 `+1`；`c2/c3`: 行 `+8` |

⚠️ 准确的 lane 映射**实现时照 PTX 文档抄**，不凭记忆。

**⭐ B11 的激活布局天然兼容**：B11 定的 block-major `qs[blk][col][32]`（列最内），
每个 int32 恰好是 k 方向连续的 4 个 int8 —— 正好是一个 B 分片寄存器，**不需要 shuffle**。

数据流（每个 row-tile × k-block）：

```
全局显存 Q4_K 字节 ──load──> 寄存器 ──解包 4bit→8bit──> A 分片 ──┐
B11 的 d_q8s/d_q8ds（已是 int8）──load──> B 分片 ────────────────┼─> IMMA ×(T/8) ─> int32
                                                                 ┘        │
                                          fp32 尾声（§3.2 条件 3）<────────┘
```

### 3.4 权重现场解包（红线）

- **禁止**把 Q4_K 物化成 int8 权重张量（流量翻倍，撞约束 (a)）
- 解包放在寄存器（A 分片直接解出）或用 shared memory 暂存后 `ldmatrix`
- 解包结果按 N 方向复用 `T/8` 次（这是选项 §3.5 的收益来源）

### 3.5 chunk 放大（本项的前置改造，二选一）

| 选项 | 做法 | 收益 | 改动面 |
|---|---|---|---|
| **A. 放大 chunk** | `MAX_MC`：16 → 64 或 128 | 解包占用 75% → 19%/9%；权重重复读降 4–8× | 中等（牵动 §2.2(c) 的共享常量） |
| **B. 层主序 prefill** | 循环对调：**每层处理整个 prompt**，权重只读 1 次 | 权重流量 121 GB → 1.18 GB（473 ms → 4.6 ms） | 大（要存全 prompt 的 hidden state ≈6.7 MB；attention 需按块做） |

**建议**：先做 **A**（局部、可回滚、已能过 DoD 量级）；把 **B** 作为 B12 内部的可选加分项，
仅当 A 之后实测仍不达标、或 attention 变成唯一瓶颈时再评估。
⚠️ 选 B 前必须核实：当前 `prefill_chunk` 的**逐 chunk 数值等价性**是 B8 已证的
（"多列 gemv 与单列 bitwise 相同"）；层主序会改变 attention 的分块边界，
**可能把 Tier A 打成 Tier B** —— 这是一个必须预先确认的口径风险。

### 3.6 三层对拍方法论（沿用 B11，**这是本项目的看家方法**）

| 层 | 内容 | 为什么不能省 |
|---|---|---|
| ① 路由内自证 | MMA gemv ↔ 独立 NumPy 参考，**逐元素 bit-exact** | B11 的教训（`docs/34` §7.4）：层①当时喂的是 host 量化激活，**漏掉了 CUDA 量化器**，导致一个 `__reduce_add_sync` 的 UB 溜到 D2 才炸（0/50） |
| ② 路由间对齐 | teacher-forcing vs llama.cpp CUDA ≥ 49/50，且 ≥ fp32 路线 | 防止"自洽但整体错" |
| ③ 质量代价 | 逐 id 比对 B11 + logit 位移分析 | Tier A 的直接证据 |

**本次层①必须覆盖**：A 分片的 lane 映射、解包正确性、k-block 边界（`k` 非 32 倍数时的尾块）。

### 3.7 A/B 开关

沿用 B11 的约定：`RADAR_Q4_MMA=1` 启用（默认关），`RADAR_B12_TILE` 供 tile 扫描。
参考 B11 的教训（`docs/34` §7.3）：**tile 不能用孤立的 L2-resident bench 选**，
必须在引擎里同会话 A/B 配对测。

## 4. 实施步骤

1. ✅ **roof 先量**（照 B11 的老办法）：`cpp/tests/b12_roof.cu`（+ CMake target `b12-roof`）。
   量了三件事：纯 MMA 天花板、解包系数 `c`、以及解包+MMA 在不同复用因子下的合并吞吐。
   **结果见 §7.1，并据此修正了 §2.2b 与 §3.5 的参数。**
2. ✅ **数学 oracle 复用，不新建 `ref_q4_mma.py`**（2026-10-11 核实后简化）。
   B11 的 `cpp/tests/ref_q4_int8.py` **已经就是 MMA 的数学 oracle**：
   - `ref_q4_int8.py:249`：`dot1` 是**精确 int32** 求和（源码注释原话：
     *"dot1 is an exact int32 sum -> integer addition order is irrelevant"*）——
     与 MMA 的 int32 累加**是同一个东西**；
   - `sum_q` 是精确整数（§3.2 条件 2）；
   - fp32 尾声的括号化与顺序已按 §3.2 条件 3 实现。

   ⇒ 新建一份"MMA 参考"只会算出**同样的数字**，属于重复。B12 新增的不是数学，
   而是**物理布局**（哪条 lane 拿哪个元素）与**解包**。
3. ✅ **host 侧语义原型**（2026-10-11 完成）：`ri::matvec_q4_k_q8_1_mma_host` +
   `ri::mma_fragment_coverage_ok`（`cpp/src/int8_act.{h,cpp}`），挂进 `int8_ref_test`。
   ⚠️ 关键：B11 参考是**逻辑索引、布局无关**的，所以它**抓不到 lane 映射写错**
   （映射错了照样是一个"精确但错误"的 dot）。因此原型**按物理布局取数**再算 ——
   这才是能抓映射错误的层①。**结果见 §7.6。**
4. **CUDA kernel**：`gpu_mma.cu`，先在固定 tile 下与 host 原型 bit-exact
5. **chunk 放大**（§3.5 选项 A）：`MAX_MC` 16 → 64，逐项核对 §2.2(c)
6. **接入引擎**：`gemv_prefill` 分派；先 Q4_K，Q6_K 不动
7. **对拍与验收**：§3.6 三层 + `test_b12.sh`
8. **文档回填**：`docs/27` §4、`docs/04` 索引

## 6. 明确不做（防范围蔓延）

- **FP8 MMA**（sm_89 支持但会改数值口径 → Tier C，属 `docs/35` Phase 3）
- **2:4 结构化稀疏**（需要离线稀疏化管线，且改变数值）
- **`wgmma`**（Hopper sm_90 专属，本机不可用）
- **Q6_K 走 MMA**（本轮与 B11 同决策，留在 fp32 路线）
- **decode 路径的 MMA**（decode 是 bandwidth-bound gemv，MMA 无收益）
- **attention 重写**（= B14，独立立项）
- **KV 量化 / 投机解码**（Tier C，属 `docs/35` Phase 3）

## 7. 验收结果

### 7.1 ✅ 步骤 1：roofline 已量（2026-10-11，`cpp/tests/b12_roof.cu`）

方法：每 SM 恰好驻留一个块（消除波次量化 —— 正是这个缺陷让 `mma_probe` 早期版把
dp4a 报成 191 而非 256），三轮轮转取最小值。

| 探针 | 结果 |
|---|---|
| A) 纯 MMA（A 在寄存器） | **1023.8 MAC/SM/clk**（复现 `mma_probe` 的 1023.9） |
| B) 只做 nibble 展开 | 36.2 values/SM/clk ⇒ **解包系数 c = 1.77 INT32 ops/权重值** |
| C) MMA + 现场解包，按复用因子 R（T = 8R） | 见下表 |

| R | T=8R | MAC/SM/clk | vs 天花板 | 开销 |
|---|---|---|---|---|
| 1 | 8 | 342.2 | 33.4% | 199% |
| **2** | **16（当前 chunk）** | **550.6** | **53.8%** | **86%** |
| 4 | 32 | 821.7 | 80.3% | 25% |
| 8 | 64 | 854.5 | 83.5% | 20% |
| 16 | 128 | 913.0 | 89.2% | 12% |

**三条结论**：

1. **`c = 1.77`，是计划阶段估值（0.75）的 2.4 倍。** 编译器把 nibble 展开编译成
   "3 次移位 + 若干 `LOP3`"，而不是单条 `PRMT` 技巧。`c` 是"chunk 该多宽"的正比因子，
   所以**必须实测而不是估**。
2. **模型在 T 小时高估**：实测开销 T=8 是 199%（模型 354%）、T=16 是 86%（模型 177%）。
   原因是 INT32（解包）与 tensor core（MMA）是**两条独立管道、可以重叠**，开销不是简单相加。
   → 趋势可用，绝对值必须实测（这条订正已回填 §2.2b）。
3. **T=16 时 MMA 只拿到天花板的 53.8% = 550.6 MAC/SM/clk，是 dp4a 管道（256）的 2.15×。**
   也就是说**在今天的 chunk 宽度下，换 MMA 相对 dp4a 几乎没有增量**。
   这不是"优化空间"，是**前置条件**：chunk 必须先放大。
   拐点在 **T=32**（821.7 = dp4a 的 3.21×），T=64 之后边际收益迅速变小。

### 7.2 ⭐ 两条约束的交点：chunk 该多大

把 (a) 带宽 与 (b) 解包 放在同一张表（全 prefill，T_total = 1645，权重 1.18 GB）：

| 方案 | 带宽下限 | 计算时间（按 §7.1 实测） | 谁主导 |
|---|---|---|---|
| T=16（现状） | 473 ms | 104 ms | **带宽 4.5×** |
| T=32 | 240 ms | 70 ms | 带宽 3.4× |
| T=64 | 120 ms | 67 ms | 带宽 1.8× |
| T=128 | 60 ms | 63 ms | **平衡** |
| **选项 B（层主序）** | **4.6 ms**（权重只读 1 次） | 67 ms | **计算主导 ✓** |

> ⚠️ **本表的"选项 B"一行有误导性，已由 §7.5 订正**：层主序**单独**并不减少带宽，
> 只有"每层一次算完整个 prompt"（W = T_total）才对应 4.6 ms。请以 §7.5 为准。

> ⭐ **修正后的结论**：解包这条约束只要求 **T ≥ 32**；真正把 W 往上推的是**带宽**
> —— 它与计算在 **W=128** 附近平衡，而 **W = T_total** 时带宽项几乎消失（4.6 ms）。
>
> **⇒ 但 W 的选择不该在写 kernel 之前拍**：A（放大 W）与 B（层主序 + 宽 GEMM）
> 需要的是**同一个 N 参数化的 MMA GEMM**，区别只是激活缓冲开多大（§7.5）。
> **先写 kernel，再用引擎内同会话 W 扫描定 W。**

**D3 目标（≥1000 tok/s）的量级判断**：attention 固定 587 ms（`docs/34` §7.1），
GEMM 按上表取 60–67 ms ⇒ 理论合计 ~650 ms ≈ 2500 tok/s。但真实 kernel 还要承担
访存延迟、fp32 尾声、寻址与 occupancy —— 参照 B11 的 dp4a gemv 只跑到其管道峰值的
~13%，若 B12 的**非算术开销**比例类似，实际落点会低得多。
**区间给 1000–2000 tok/s，且必须以真实 kernel 的同会话配对测量为准**（`docs/25` §5.9）。
这个不确定性只能靠步骤 4（写 kernel）消除，探针到此为止。

### 7.3 一个尚未验的降 c 杠杆（列为可选）

`c = 1.77` 来自编译器选用的"移位 + `LOP3`"序列。理论上可用 **`PRMT` 技巧**做到
约 5 条指令 / 4 个值（即 `c ≈ 1.25`，优于手写的 1.77）：先 `PRMT` 复制字节，
再分别取高低 nibble，最后 `PRMT` 交错。

**为什么值得留着**：`c` 直接决定所需 T（`T ≥ 16c`）。若 `c` 能从 1.77 降到 1.25，
解包要求的 T 从 32 降到 20 —— 那样**也许不必放大 `MAX_MC` 就能拿到大部分收益**，
改动面会小一个数量级。

**但现在不做**：它只影响 (b) 解包这一项，而 §7.2 已表明**带宽才是把 T 往上推的那一项**。
在 §7.2 的路线选定之前优化 `c` 是早优化。若最终选"放大 chunk 到 32"这条路，
再回来试 `PRMT`。

### 7.4 步骤 1 的净结论

- ✅ 管道天花板确认：**1023.8 MAC/SM/clk = dp4a 的 4.0×**，SASS 为 `IMMA.16832.S8.S8.SAT`
- ✅ 解包系数实测：**c = 1.77**，比估值差 2.4× —— 证明"先量再写"是对的
- ⭐ **新发现：W=16 时 MMA 只比 dp4a 快 2.15×，换指令本身几乎没有增量**
- ⭐ **真正的驱动因素是"每次读权重覆盖多少 token"（记为 W），不是循环嵌套顺序**
  —— 见 §7.5 的订正
- ⏭ 下一步：**先写 N 参数化的 MMA GEMM，再用引擎内同会话 W 扫描定 W**（§7.5）

### 7.5 ⚠️ 订正：层主序本身**不**减少带宽

**§7.2 表里"选项 B（层主序）⇒ 带宽 4.6 ms"这句话有误导性，必须订正。**

带宽只取决于**每次读权重时参与 GEMM 的 token 宽度 W**，与循环嵌套顺序无关：

| 结构 | 权重流量 |
|---|---|
| 现状（chunk 主序）：外层 103 个 chunk，每 chunk 读**全部层**权重 1.18 GB | 121 GB |
| 层主序 + 内层仍按 16 token 分块：外层 28 层，每层内层 103 块，每块读**该层**权重 42 MB ⇒ 28 × 103 × 42 MB | **121 GB（一模一样）** |

⇒ **单纯把循环对调，带宽一点都不会降。** §7.2 里那个 4.6 ms 对应的真实条件是
**W = T_total（每层一次算完整个 prompt）**，而这要求写一个**真正的 GEMM（N = T 宽）**，
不是重排两层 `for`。

**正确的表述 —— 唯一的杠杆是 W：**

| W（每次读权重覆盖的 token 数） | 权重流量 | 带宽下限 |
|---|---|---|
| 16（现状） | 121 GB | 473 ms |
| 32 | 61 GB | 240 ms |
| 64 | 31 GB | 120 ms |
| **128** | 15.3 GB | 60 ms |
| **T_total = 1645** | **1.18 GB** | **4.6 ms** |

**⭐ 由此得到一个更好的执行顺序：A 与 B 需要的是同一个 kernel。**

两者都是"一个 **N 可变**的 MMA GEMM"，区别只是**激活缓冲开多大、N-tile 循环跑多少圈**
—— 不是 kernel 结构。而激活缓冲本身很小：int8 的 `x` 是 `2048 × 1645 × 1 B ≈ 3.4 MB`，
Q8_1 的 `d/sum_q` 再加 0.85 MB。

> **结论：不要在写 kernel 之前就在 A/B 之间二选一。**
> 先写 **N 参数化**的 MMA GEMM，再用引擎内**同会话配对**的 W 扫描来定 W ——
> 这正是 B11 的教训（`docs/34` §7.3：tile 不能用孤立的 L2-resident bench 选）。

**另外两条独立结论（对两条路都成立）：**

1. **放大 W 不必动 `BLOCK`（KV 块大小）。** 代码里 `BLOCK = 16`（KV 块）与
   `MAX_MC = 16`（chunk 宽度 / `max_batch` 上限）是**两个独立常量**，只是恰好相等。
   真正要拆开的是 `MAX_MC` 的**双重身份** —— 建议引入独立的 `MAX_PREFILL`，
   这样放大 prefill 宽度就不会顺带把 `max_batch` 上限也抬起来
   （那会让 `d_scores` = `kv_cap × n_head × max_batch` 按倍数膨胀）。
2. ⭐ **Tier A 可以按构造保持，比我原判断（§3.5 风险 R5「可能降级」）乐观。**
   理由：每个输出元素的累加顺序由 **k 方向循环**决定，与 N（多少 token 并排算）无关；
   而 `gemv_mc` 各列独立、与单列 bitwise 相同（B8 已验证）。只要 N 方向加宽
   不改变 k 循环与 fp32 尾声的顺序，**逐位相同就该成立**。这条要用 §1.2 的 exact
   档案实测确认，但它是"可构造保证"而不是"听天由命"。

### 7.6 ✅ 步骤 3：host 分片原型（2026-10-11）

新增 `cpp/src/int8_act.{h,cpp}`：

| 产物 | 作用 |
|---|---|
| `mma_a_map` / `mma_b_map` / `mma_c_map` | `m16n8k32`（8-bit）的 PTX 分片映射（`gid = lane>>2`、`tig = lane&3`） |
| `mma_fragment_coverage_ok()` | 证明三张分片映射各是**双射**（16×32 / 32×8 / 16×8 每格恰好被覆盖一次）—— 与数值无关，能独立抓"映射不是双射"这类错误 |
| `matvec_q4_k_q8_1_mma_host()` | 与 `matvec_q4_k_q8_1_host` **同数学**，但每个 A/B 元素都**经分片映射取数** |

**实测结果**（`int8-ref-test`，4 个 Q4_K 张量，零编译警告）：

```
mma fragment maps  A 16x32 / B 32x8 / C 16x8  BIJECTIVE
host Q4_K int8 gemv via MMA FRAGMENTS  16 x 2048 x 1024  BIT-EXACT   (attn_k)
                                       16 x 2048 x 2048  BIT-EXACT   (attn_output)
                                       16 x 2048 x 2048  BIT-EXACT   (attn_q)
                                       16 x 2048 x 6144  BIT-EXACT   (ffn_up)
```

**这一步买到了什么：**

1. ⭐ **PTX 的 lane 映射被证实是对的** —— 而且是**逐位**证实的，不是"看起来对"。
   映射若写错（行错位、k 内序错、寄存器序错），取数就会配错乘积，
   于是**对不上布局无关的参考**。所以这条 bit-exact 同时验证了映射与解包。
2. **一个可在写 CUDA 之前独立运行的层①**：`int8-ref-test` 现在同时跑
   参考实现与分片实现；CUDA kernel 写完后只要与**分片原型**逐位一致，
   映射就自动是对的（不必再和 NumPy 比一次）。
3. **确认 `K=32` 的对应关系**：B11 的 Q4_K 子块 `j`（32 个值）**正好**是 MMA 的 K=32，
   一条 MMA 覆盖一个子块 × 16 行 × 8 列。`ffn_up` 的 `out=6144` 验证了大 out
   （6144/16 = 384 个 row-tile）；尾块逻辑（`out`/`ncol` 非 16/8 整数倍）已在原型里处理。
