## 二、新增实测：显存冒烟（`logs/probe/p5_mem_smoke.py`）

**方法**：加载 bf16 基座 → 造最坏样本（最长序列 + 最大图，实际 `input_ids=(1, 1278)`，
比数据集中真实最长样本 750 token 还长 70%）→ 一次 forward+backward → 记录峰值与耗时。
**注意：这是全参梯度（未装 peft，无 LoRA），所以是显存上界。**

| 配置 | 峰值显存 | 单次耗时 |
|---|---|---|
| 基座加载后 | 3.96 GiB | — |
| **不开** gradient checkpointing，batch=1 | **14.86 GiB** ❌ | **674.6 s** ❌ |
| **开** gradient checkpointing，batch=1 | 9.52 GiB | **21.9 s** |
| 开 checkpointing，batch=2 | 9.89 GiB | 81.4 s |

三条结论（直接决定参数）：

1. **`gradient_checkpointing=True` 是硬需求**，不是优化项。不开时峰值 14.86 GiB（超物理显存，
   靠 Windows 共享 GPU 内存兜底）→ 单次 675 秒，**慢 31 倍**。
2. 即便开了，全参梯度仍要 9.5 GiB > 8 GiB（溢出到系统内存，所以 21.9 s/step 依然偏慢）。
   → **LoRA 是唯一现实选择**：它把"梯度 + 优化器状态"从 11.9 GiB 降到约 0.3 GiB（见 §四）。
3. **batch=2 并不划算**：81.4 s 处理 2 个样本 = 40.7 s/样本，比 batch=1 的 21.9 s/样本更慢
   （显存溢出惩罚）。→ 取 **per_device_batch=1 + 梯度累积**。

## 四、训练配置与参数选择（逐条给依据）

| 参数 | 取值 | 依据 |
|---|---|---|
| 框架 | HF `Trainer` + `peft` | 不引入 `trl`：transformers 5.17 很新，trl 版本兼容性是额外风险；本项目只需 SFT，自写 Dataset/Collator 足够（~150 行） |
| 基座 | `Qwen3-VL-2B-Instruct`，bf16，attn=`sdpa` | P0/P1 实测口径（sdpa 是本机实测生效的实现） |
| **冻结视觉塔** | ✅ | 用户拍板 D2；同时省下 ViT 的激活与梯度 |
| 冻结 `embed_tokens` / `lm_head` | ✅ | 词表 151936 × 2048，单独嵌入层就 0.6 GiB；冻结后省显存且防词表漂移 |
| **LoRA r** | **16** | 2B 模型 + ~900 条数据的常用区间是 8–32。取 16：r=8 容量偏小（要同时改输出格式与领域知识），r=32 在小数据上有过拟合风险且参数量翻倍 |
| **LoRA alpha** | **32**（alpha/r = 2） | 2 是社区默认缩放比；等效缩放 2.0，配合 lr=1e-4 稳定 |
| **dropout** | 0.05 | 小数据防过拟合的轻正则；再大会拖慢收敛 |
| **target_modules** | `q,k,v,o,gate_proj,up_proj,down_proj`（语言侧 28 层） | 覆盖注意力+MLP 是 LoRA 事实标准；视觉塔整体不进 target（已冻结） |
| **lr** | **1e-4** | LoRA 典型区间 1e-4～2e-4；数据量小（<1k）取下沿更稳 |
| **scheduler / warmup** | cosine / **0.03** | 短训练（几百步）用小 warmup 防开局震荡 |
| **epochs** | **3** | 小数据集 2–4 epoch 常见；3 折中。**先 pilot 再定**（§五） |
| **per_device_batch** | **1** | 冒烟实测 batch=2 反而更慢（40.7 vs 21.9 s/样本） |
| **grad_accum** | **8**（effective batch = 8） | 900 条 / 8 = 113 步/epoch × 3 = **339 步**，步数足够优化器收敛 |
| **max_seq_len** | **1024** + 动态 padding + `group_by_length` | 数据实测 max 750，768 即 100% 覆盖，1024 留余量 |
| **gradient_checkpointing** | **True**（硬需求） | 冒烟实测：不开 14.86 GiB / 675 s，开 9.52 GiB / 22 s |
| **optim** | `adamw_torch`（**不用** 8-bit） | 8-bit Adam 依赖 bitsandbytes，Windows 有安装/运行风险；LoRA 优化器状态本身只有 ~0.24 GiB，没必要省 |
| **bf16** | True | 与 P0/P1 实测口径一致；4060（sm_89）原生支持 |
| 可复现 | `seed=42` | 便于对照实验 |

### 显存账（推算，待 pilot 实测校正）

| 项 | 全参微调 | **LoRA（本方案）** |
|---|---|---|
| 权重 bf16 | 3.96 GiB | 3.96 GiB |
| 梯度 | 3.96 GiB | ~0.06 GiB（仅 LoRA 参数） |
| Adam 状态（fp32 m+v） | 7.92 GiB | ~0.24 GiB |
| 激活（ckpt 后，batch=1） | ~2 GiB | ~2 GiB |
| **合计** | **≈ 15.8 GiB ❌** | **≈ 6.3 GiB ✅**（落在 8 GiB 内，不溢出） |

> ⚠️ 推算不是实测。**pilot 第一步就打显存峰值日志**，若 >7.2 GiB 立即降 `max_len`→768 或启 QLoRA。

### 耗时估算

- 冒烟：ckpt=True、batch=1、**seq 1278**（超实际 70%）→ 21.9 s/步，**且当时显存溢出**。
- LoRA 后不溢出 + 实际平均 seq 更短（文本 143 / 视觉 418）→ 期望 **3–8 s/步**。
- 步数：905 条 ÷ effective batch 8 = **113 步/epoch**，3 epochs 合计 **339 步**。
- 乐观 339 × 5 s ≈ **28 分钟**；保守（仍溢出或长样本多）按 3 倍 ≈ **1.5 小时**。
- 加每 epoch 的 dev 评测与 checkpoint 落盘 → **总计 2～5 小时**（pilot 后收窄）。

## 七点五、Pilot 实测（`outputs/p5_lora/pilot/run_summary.json`，2026-09-18）

先洗牌再截断，取 **300 条（视觉 23 / 文本 277）**，序列 mean 166 / max 700，1 epoch：

| 指标 | 实测 | 与方案推算对比 |
|---|---|---|
| **显存峰值** | **5.53 GiB** ✅ | 推算 ≈6.3 GiB，**未溢出**；对比冒烟全参梯度 9.52 GiB → LoRA 确实省了约 4 GiB |
| **速度** | **3.08 s/step** | 冒烟全参（且溢出）21.9 s/step → **快 7 倍**（不溢出是关键） |
| 步数 | 38（300/8） | — |
| loss | 3.156 → 1.501 | 正常下降，无发散 |
| 可训练参数 | 17.43 M（0.82%） | 全在语言侧（断言通过） |

→ **epochs 定 3**：953/8 = 120 步/epoch × 3 = 360 步 × 3.08 s ≈ **18 分钟**
（原方案估 2～5 小时，基于冒烟的全参+溢出数据，**当时高估了 5～15 倍**）。

### pilot 期间修掉的两个真 bug（都是静默/致命型）

1. **先截断后洗牌** → pilot 前 300 条全是文件前部的纯文本单元，**视觉题 0 条**，
   显存测的不是最坏情况。改为先洗牌再截断（现已在脚本里加注释与视觉条数打印）。
2. **collator 丢掉 `mm_token_type_ids`** → transformers 5.17 的 Qwen3-VL 需要它算 M-RoPE，
   forward 直接抛 `ValueError: mm_token_type_ids is missing`。
   修法：Dataset 原样保留 processor 的其余输出（注意 `pixel_values` 第 0 维是 patch 数，不能切 batch 维）。
3. 另：`TrainingArguments` 在 5.17 **没有 `warmup_ratio` 字段**（实测 dataclasses.fields 只有
   `warmup_steps`）→ 改为按总步数换算 warmup_steps。

### 显存"满"的根因与处置（实测，比推算更可信）

| 现象 | 实测 |
|---|---|
| allocated（真实需求） | 4.18–5.66 GiB |
| reserved（allocator 预留） | 常规 5.1–6.6，**最长样本时 8.25～8.54 GiB（超过物理 8.0 GiB）** |
| 后果 | 溢出到 Windows WDDM 共享显存（系统 RAM）→ 机器卡顿，这就是用户观感"满"的来源 |
| ❌ `expandable_segments:True` | **Windows 不支持**（实测 `UserWarning: expandable_segments not supported on this platform`） |
| ✅ 每 3 步 `empty_cache()` | reserved 从 8.54 → 5.1–6.6（**降约 2 GiB**），速度反而略快 |
| ✅ `max_len` 1024 → 768 | 封顶最长序列（数据 max 767，零截断） |
| 护栏判据修正 | 必须用 **allocated** 判危险；用 reserved 会把正常状态误判（7.0 上限时第 3 步就误停） |

### 另一个实测更正

`LoRA 参数已升 fp32：0 个张量` → **peft 0.21 创建的 LoRA 本来就是 fp32**（即使基座 bf16），
AdamW 状态也是 fp32。所以 §四 担心的"bf16 更新被舍入吞掉"**不成立**；
且 `LoraConfig` 在 0.21 **没有 `lora_dtype` 参数**（已实测参数列表确认）。

### 产物自检（`logs/probe/p5_check_adapter.py`）

加载 adapter 后问"带宽 4 GHz 的距离分辨率"，输出：

```
公式：\Delta R = \frac{c}{2B}
代入：\Delta R = \frac{3\times10^{8}}{2 \times 4\times10^{9}} = 0.0375\ \text{m}
最终答案：0.0375 m
```

格式完全对齐训练规范、数值正确、仅 70 token（简洁）→ **微调确实生效**。

## 七点七、CPU offload（混合训练）试验（2026-09-18，用户提议"64GB 内存可用"）

**做法**：用 `accelerate.hooks.add_hook_to_module` + `AlignDevicesHook(offload=True)`
把**冻结的视觉塔**（0.758 GiB）常驻 CPU、前向时搬到 GPU。语言层（含 LoRA）与计算仍在 GPU。

⚠️ **只 offload 视觉塔，不动 embed/lm_head**：这两者是 **tied（共享 storage）**，
同时挂两个 hook 需要 `tied_params_map`，风险高；收益也只有 0.58 GiB。

| 指标 | 无 offload（60 条探测） | offload 视觉塔（200 条探测） |
|---|---|---|
| reserved 峰值 | 8.25～8.54 GiB | 6.90 GiB |
| allocated 峰值 | 5.06 GiB | 5.43 GiB |
| 速度 | 2.76 s/step | 2.60 s/step |
| GPU 常驻 | 4.029 GiB | **3.271 GiB（确认释放 0.758）** |

### ⚠️ 但全量实测：**offload 对峰值无效**（2026-09-18 反转结论）

全量 3 epoch 加 `--offload-visual 1` 后：峰值 **8.28 GiB、仍停在 step 213**，
与不开 offload 的 8.25 **几乎完全一致**。

**原因**：hook 在**处理视觉样本时会把视觉塔临时搬回 GPU**，于是含视觉样本的那一 micro-batch
占用 = 语言层 3.271 + 视觉塔 0.758 = 4.029 GiB，**与常驻时完全相同**。
而 reserved 尖峰恰好发生在含视觉样本的步（数据里最长样本 750 token **全是视觉题**，
top6 长度样本无一例外是 vision）→ offload 只省了纯文本步，**对决定峰值的那一步毫无帮助**。

> 教训同"证据范围 ≠ 结论范围"：200 条探测看到 6.90 GiB 就下结论"有效"，
> 但探测批次里的最长样本没覆盖到真正决定峰值的组合。

### ✅ 真正有效的手段：每步 `empty_cache()`

| 配置 | 全量 reserved 峰值 | 结果 |
|---|---|---|
| 每 3 步 empty_cache | 8.25 GiB | 停在 step 213（1.78 epoch） |
| 每 3 步 + offload | 8.28 GiB | 停在 step 213（**offload 无收益**） |
| **每 1 步 empty_cache** | **7.92 GiB** | **跑到 step 342 / 360（2.856 epoch）** |

reserved 是 allocator 的"已向驱动申请但未归还"的量，会**在几步内累积**；
每步归还后峰值回到单步真实需求附近（allocated 5.66 → reserved 7.92）。
代价：2.65 s/step vs 1.55 s/step（**慢约 70%**，因为每步都 cudaFree/cudaMalloc），但这是本机唯一能压住峰值的办法。

## 七点九、⭐ 输出长度归因 + 判分口径 v2（2026-09-18）

> 起因：用户追问"输出变短是我们期待的吗？是不是因为训练数据答案本来就短？统计口径该怎么改？"
> 三个问题都用实测回答（脚本：`logs/probe/p5_len_attrib.py`、`p5_len_attrib2.py`）。

### A. 输出变短：**整体是期待的**，但存在分题型的过度压缩

**决定性证据是长度比（输出 ÷ 参考答案），不是绝对字数：**

| 层 | 基座 字数 / 长度比 | 微调 字数 / 长度比 |
|---|---|---|
| 全部 120 条 | 195 字 / **6.79×** | 66 字 / **1.18×** |
| 可答题 | 191 字 / **5.96×** | 69 字 / **1.03×** |

微调后长度比 **1.03**，即输出精确收敛到参考答案长度；基座是 **5.96 倍废话**。
训练答案 mean 84 / median 93 字 —— 微调后确实学到了这个尺度。

**变短不是"漏答"**：可答题的 P/R 双双上升 —— `P 0.118→0.459（+0.341）`、`R 0.297→0.424（+0.127）`。

**并且"变短"在本指标下是扣分的，不是加分的**（这条最关键）：

| 输出长度 | F1 |
|---|---|
| 截到参考答案的 25% | **0.333** |
| 50% | 0.616 |
| 100%（自比） | 1.000 |
| 注入 8× 无关废话 | **0.548** |

即：**对"过短"严厉、对"冗长"宽容**。所以 F1 从 0.137→0.423 不可能靠"变短"刷出来。

**但分题型有真问题（过度压缩）：**

| 题型 | n | 训练答案均长 | 微调输出均长 | 压缩比 | F1 基座→微调 |
|---|---|---|---|---|---|
| calc | 26 | 123 | 130 | **1.06 ✅** | 0.314 → **0.912** |
| choice | 14 | 19 | 19 | 1.03 ✅ | —（受限，见 C） |
| figure_qa | 8 | 95 | 77 | 0.81 ✅ | 0.099 → 0.130 |
| term | 12 | 96 | 64 | 0.67 ⚠️ | 0.090 → 0.116 |
| **concept** | 25 | 85 | 44 | **0.52 ⚠️** | 0.064 → 0.061（**没提升**） |
| **contrast** | 5 | 116 | 60 | **0.51 ⚠️** | 0.075 → 0.037（**下降**） |

concept / contrast / term 输出只有训练答案的一半，且得分没提升 —— 这是真缺陷，不是"变精炼"。

### B. ⭐⭐ 真正的原因：不是"学短了"，是**选择题格式泛化到了开放题**

微调后 **20 条**非选择题型输出了纯字母形式（基座 0 条）。其中 13 条是 concept 开放题：

```
evt_000411  Q: 模糊函数关于原点对称，这一性质在实际分析模糊函数图时能省掉多少工作量？
            微调输出: "最终答案：B"      ← 开放题被答成选择题
```

训练集里 concept 的答案 **0% 是纯字母、0% 带「最终答案：」**（244 条全是 85 字文字）；
而 choice(131) / calc(200) / term(106) / regime_trap(73) **100% 带该前缀**。
模型学会了"简短输出 = 字母"这个表面模式，并泛化到开放题。

**这直接推翻了 v1 报告里的两个结论**：
- "concept 得分略降" → 实为格式失效，不是能力下降；
- "格式合规率 94%→63% 是缺陷" → **不是缺陷**：训练数据里本就只有 53% 的答案带该前缀
  （system prompt 要求带，但数据一半不带，**数据与 prompt 冲突**），模型正确地学了数据，
  是我按 prompt 而非按数据判分，口径错了。

### C. ⚠️ 编译 bug：选择题的 options 从未渲染进 prompt（影响 204 条训练 + 21 条评测）

`src/dataset/compile.py` 构建 user 消息时：

```python

```

yaml 里 `evt_000424` 有完整 A/B/C/D 四个选项，编译后题面里**一个都没有**，答案却是 `最终答案：A`。
→ 模型**看不到选项**，只能盲猜字母。影响：训练 204 条（choice 131 + regime_trap 73，占 21%）、
评测 21 条（占 17.5%）。这正是 B 中"字母模式泛化"的源头。

**选择题现状**：21 条正确 6 条（29%），随机基线 25%，**二项检验 p = 0.433（不显著）**
→ 无法排除蒙对。此类题在 options 修复前**不计入能力结论**。

## 七点十二、方案 B1（视觉-语言对齐层 LoRA）—— ❌ 实测无增益

### 动机

视觉塔不是"一整块"：ViT 主干只占 74.3%（302.31 M），另有 **100.71 M（24.7%）是对齐层**
（`visual.merger` 25.17 M + `visual.deepstack_merger_list` 75.54 M）。
业界实践是「Projector / 对齐层通常**不冻**」，而我们此前把它连同主干一起冻了。
B1 = 只给对齐层加 LoRA，**ViT 主干全程不动** → 零通用视觉能力遗忘风险。

### ⚠️ 实现中的致命陷阱（已实测，必须记住）

对齐层 MLP 名为 `linear_fc1 / linear_fc2`，而 **ViT blocks 里的 MLP 也叫同名**
（共 28 组：主干 24 + 对齐层 4）。若用短名 `target_modules` 会**误加到 ViT 主干 24 层**，
B1 会**静默退化成 B2**。

解法：peft 在 `target_modules` 为 **str** 时用 `re.fullmatch` 匹配完整 key，故用带路径正则：

```
r".*(?:\.(?:q_proj|k_proj|v_proj|o_proj|gate_proj|up_proj|down_proj)"
r"|\.visual\.(?:merger|deepstack_merger_list\.\d+)\.linear_fc[12])$"
```

已用 7 条用例验证：语言侧 2 类 / 对齐层 2 类命中，`blocks.mlp` / `attn.qkv` / `embed` 均不命中。
脚本断言同步改为：允许 `.visual.` 但**绝不允许** `.visual.blocks.` / `patch_embed` / `lm_head`。

### 实测结果

两版均在 **step 315 / 2.335 epoch** 被显存护栏停止（reserved 8.25 > 7.85）→ 训练量相同，**公平对比**。

| 指标 | vis200（无对齐层） | align（B1） | Δ |
|---|---|---|---|
| 视觉题 F1（n=17） | 0.176 | 0.173 | −0.003 |
| 视觉数值命中（n=13） | 0.256 | 0.254 | −0.003 |
| 可答题 F1 | 0.329 | 0.323 | −0.005 |
| 文本数值命中 | 0.593 | 0.545 | **−0.048** |
| 拒答正确率 | 0.917 | **1.000** | +0.083 |
| 选择题 | 19/21 | 19/21 | 0 |

**逐条分布（视觉 17 条）**：改善 5 / 变差 5 / 持平 7 —— **完全随机**，没有系统性方向。

### 结论

**瓶颈不在"视觉特征 → 语言空间"的翻译环节。** 若 ViT 输出的特征里本就没有精确数字，
对齐层再怎么调整也无米可炊。下一步要么动 ViT 本身（B2：小步长 r=8 + LR 2e-6，需监控遗忘），
要么接受现状转去扩数据 / 补评测。**不要再往对齐层投入。**

脚本：`--lora-align 1`；逐条对比工具：`logs/probe/p5_vis_compare.py`。

## 七点十三、⚠️ 判分器第三处缺陷：科学计数法解析（2026-09-19 修）

调查"要不要做 RLHF"时，按 `task=='calc'` 重算得 0.633，与 v3 报告的
"calc 数值命中 0.945" 对不上 → **两个口径都错**：

| 口径 | 值 | 错在哪 |
|---|---|---|
| `num_hit`（参考数字覆盖率） | 0.944 | **虚高**：公式常数（3×10⁸、2、4×10⁹）题面里就有，照抄即得分 |
| `score`（答案值匹配，旧正则） | 0.633 | **虚低**：`8\times10^{13}` 被切成 8/10/13 三个裸数字，永不匹配 8e13 |

**实锤**：`evt_000407` 参考答案 `8×10^{13}`、模型输出 `8×10^{13}` —— 一字不差，旧口径判 0 分。

**修法**：`p5_eval_report_v3.py` 加 `SCI_RE` + `nums()`（先吃 `a×10^b`
兼容 `\times / \cdot / × / x / *` 与 `10^{5} / 10^5`，剩余再抽裸数字），
`num_hit()` 与 numeric 分支均改用 `nums()`。7 条用例验证通过。

**修正后的真实水平（calc n=30）**：

| 版本 | score（最终答案值正确） | num_hit |
|---|---|---|
| 基座 | 0.500 | 0.670 |
| 无对齐层 | **0.700** | 0.904 |
| B1 对齐层 | **0.767** | 0.915 |

→ 微调在 calc 上的真实提升 **+0.200**（旧口径被两头扭曲后根本看不清）。

## 七点十四、RLHF / RLVR 选型判断（2026-09-19，用户问"后续要不要 RLHF"）

> 用户原文写 "RLTF"，按 **RLHF**（Reinforcement Learning from Human Feedback）理解；
> 但本项目真正相关的范式是 **RLVR**（Reinforcement Learning with Verifiable Rewards）。

### A. RLHF 一般用于什么场景

**共同特征：奖励信号不可自动计算，必须靠人类判断。** 典型场景：

- 主观质量：helpfulness、语气、详略、风格
- 安全对齐：拒答有害请求、降毒性
- 指令跟随的细致偏好（"照我说的格式来"）
- 长文本/多轮对话的连贯性

标准流程：SFT → 采样多个答案 → **人工标注偏好对** → 训练奖励模型 → PPO 优化。

### B. 本项目不做 RLHF —— 三条实测依据

1. **瓶颈性质不匹配**：我们的短板是"数值算错、图上数字读不准"（客观可验证），
   不是风格/对齐。RLHF 常解决的拒答与安全性，实测已 **94.7% / 93.1%**。
2. **显存直接否决 PPO**（按实测权重 3.963 GiB 推算）：

   | 范式 | 模型副本 | 估算 | 结论 |
   |---|---|---|---|
   | SFT（已跑通） | 1 | 5.56 | ✅ |
   | rejection sampling | 1（纯推理） | 4.26 | ✅ |
   | DPO + LoRA（ref 共享基座） | 1 | 6.76 | ⚠ 临界 |
   | DPO 全量 | 2 | 8.43 | ❌ 溢出 |
   | **PPO**（policy+ref+reward+value） | **4** | **17.35** | ❌ 溢出 |

3. **没有偏好数据**：人工标注 1000+ 偏好对，对单人学习型项目不现实。

### C. 那 RLVR（可验证奖励）呢？—— 覆盖率是硬约束

评测集 200 条的判分类型分布（实测）：

| 类型 | 条数 | 占比 | 有确定性奖励？ |
|---|---|---|---|
| keyword（concept/term/figure_qa…） | 114 | 57% | ❌ 只能 3-gram F1 |
| choice | 37 | 18% | ✅ |
| numeric | 30 | 15% | ✅ |
| refusal | 19 | 10% | ✅ |

**但有奖励的三类里，choice 93%、trap 100%、拒答 94.7% 都已接近饱和，
真正有空间的只有 calc 30 条（15%）。**

而**最大短板 concept（67 条 = 33.5%，F1 仅 0.080）恰恰没有确定性奖励** —— 这是硬约束。

### D. 结论与路线排序

**RL 在本项目是"锦上添花"而非"雪中送炭"，优先级低于收口与写报告。**

更对症的解法（都不需要 RL）：

| 问题 | 更优解 |
|---|---|
| calc 算术错（8/9 条） | **P6 Agent 阶段外接计算器 / Python** —— 让模型调用工具算，比让 RL 把它"练准"更靠谱、更可解释、更适合答辩展示 |
| concept F1 0.08（无奖励） | 扩数据 / **P4 RAG**（检索到原文再答） |
| 视觉读数不准 | 已排除对齐层；B2 动 ViT 或接受现状 |

若仍要做，唯一推荐 **rejection sampling（RAFT / STaR）**：
只需 1 份权重（4.26 GiB），用现有判分器当 verifier，对 calc 采样 N 次取正确的再 SFT。

⚠️ **前置验证（必做，成本几分钟）**：对 9 条错题各采样 8 次，
验证 **pass@8 是否显著 > pass@1**。若模型根本采不出正确答案（能力缺失），
rejection sampling 也救不了 —— 不能跳过这步直接开做。

工具：`logs/probe/p5_calc_recheck.py`（科学计数法修正后的 calc 重算）。

## 七点十五、⭐ calc 算错的性质 +「外接工具调用」可行性（2026-09-19）

工具：`logs/probe/p5_toolcall_feasibility.py`（只读，不训练不占 GPU）
→ 结果 `logs/probe/p5_toolcall_feasibility.txt`

### A. 是模型参数小（2B）的能力问题吗？—— 主要不是

9 条错题中 **8 条参数代入完全正确、公式也选对**，只是算术算错：

| id | 题面参数 | 模型代入 | 应得 | 模型得 | 性质 |
|---|---|---|---|---|---|
| evt_000404 | B=500 kHz, T=50 μs | `5×10⁵ × 5×10⁻⁵` ✓ | 25 | 2.5 | **指数运算错** |
| evt_000405 | B=60 MHz, T=8 μs | `6×10⁷ × 8×10⁻⁶` ✓ | 26.81 | 20.79 | 对数算术 |
| evt_000454 | 6 参数 | 全部正确 ✓ | 32760 | 10000 | 四次方根 + **凑整** |
| evt_000455 | 6 参数 | 全部正确 ✓ | 109419 | 10000 | 同上 |
| evt_000458 | N=20 | `10log₁₀(20)` ✓ | 13.01 | 13.98（=10log₁₀25） | 对数算术 |
| evt_000459 | σ₁=1, σ₂=50 | `(50/1)^{1/4}` ✓ | 2.659 | 2.924 | 开方 |
| evt_000476 | 3 参数 | 全部正确 ✓ | 2.829 | 1.98（分子算完就停） | 步骤遗漏 |
| evt_000478 | 3 参数 | 全部正确 ✓ | 141.4 | 0.0034 | **公式展开写错** |
| evt_000477 | Tc=55 μs | `5×10⁻⁵` ✗ | 6.36e13 | 7e13 | **参数填错** |

→ **自回归架构无精确算术单元**，数字逐 token 生成。参数量大了能改善但**不根治**
（GPT-4 级同样会算错大数乘法）。**知识层 OK（会选公式、会代入），执行层缺陷（算不准）。**

### B. 外接 Agent 工具调用行不行？—— 行，且是本场景最优解

**现成工具**：`src/dataset/formulas.py` 的 **24 个公式全部在 param_pool 中**
（train 239 组 + eval 96 组），可直接导出为 `<tools>` JSON schema。

**实测收益上限：calc 70% → 97%（+27 个百分点）**（9 条错里 8 条参数全对 → 可救）。

⭐ **工具调用能同时救两类错误**：
1. 算术错（8 条中的大多数）
2. **公式展开记错** —— 如 evt_000478 模型展开成 `c/(2·f_s·B_c·T_c)`（错），
   但只要调用 `max_range_fmcw(fs=1.2e8, B=3.5e9, Tc=5.5e-5)`，
   工具会用 `formulas.py` 的**正确实现**算出 141.4 m。

**唯一救不了**：evt_000477（55 μs 误作 5×10⁻⁵）→ **参数填错 = garbage in garbage out**。

### C. 要不要训练模型调工具？—— 要，但成本远低于训练算术

三条有利事实（均为实测）：

1. **模型原生支持 function calling**：`chat_template` 含 `tool`/`tool_call` 共 **46 处**，
   格式为 Hermes/Qwen 风格：
   ```
   <tool_call>
   {"name": <function-name>, "arguments": <args-json-object>}
   </tool_call>
   ```
   预训练阶段已见过该格式 → **微调起点不为零**。
2. **训练数据零人工标注**：训练 200 条 calc 中 **176 条（88%）**可用真值反查 param_pool
   **唯一命中** inputs 组（评测 30 条中 28 条 = 93%，未命中 0）；
   剩 24 条多组命中需消歧（如数值相同的不同参数组合）。
   转换即：question → `{"name": formula, "arguments": inputs}`。
3. **任务被简化了**：只需"选对公式名 + 填对参数"，**不需要算** ——
   而模型选公式的实测水平已是 8/9。

**风险**：evt_000478 这类"公式记错"的样本，转工具调用时可能**选错工具名**（约 1 条量级）。

**定位**：属 **P6 Agent 阶段**，当前不做。若要推进，建议先做低成本 pilot：
用 200 条 calc 自动生成工具调用数据 → 小样本微调 → 在评测 calc 30 条上验证。

### ⚠️ 本轮再踩一次「自动化判定静默失效」（同型第 N 次）

`p5_toolcall_feasibility.py` 初版把 9 条**全部**判成"参数错"，与人工核查完全相反。两处 bug：

1. `sub_line` 按"含 `=` 的第一行"取 → 取到 `公式：G_{\mathrm{pc}} = B\,T`（无数字），
   而参数在下一行 `代入：...5\times10^{5}...`。修：优先取含「代入」的行。
2. 参数匹配用 `any()` → 只要一个参数对就判"参数对"，
   漏掉 evt_000477（B 对、Tc 错）。修：改 `all()` 并报告 `n/m` 明细。

→ **自动判定的结果必须与人工抽查交叉验证；两者矛盾时先怀疑脚本。**
（与"预检与审计必须同源"、"显示层写死"同属一类：数据算对了但判定说错。）
