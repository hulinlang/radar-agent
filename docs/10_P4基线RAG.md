## 一、这步解决什么（Why，不做的反面后果）

切分决定 RAG 的上限：**检索器再好，也只能在切分给出的候选里挑**。切错了，后面全白做。

本项目踩到的具体反面后果（都有实测数字）：

1. **字符滑窗会把公式切成两半**。
   对 157 条 leaf section 跑 800/ov150 滑窗 → 775 个 chunk 中 **248 个（32.0%）出现奇数个 `$`**，
   即 `$$...$$` 定界符被切断 → 这些 chunk 里的公式既读不通也算不了。
2. **`book_sections.jsonl` 有父子嵌套**。201 条里 **80 条被另一条完整包含**、13 组完全重复
   （「第1章」那条 49,842 字里把整章小节原文全抄了一遍）。照它滑窗 → 同一句话被索引 2~3 遍，
   top-k 被章级大块占满，**chunk_id 溯源失去意义**（同一句话三个 id 都对）。
3. **图在正文里完全没有锚点**。`book_sections.text` 中 `![` 出现 **0 次**，
   只在 v2 的 `image` / `chart` 块里独立存在 → 想"按图标题检索"只能从块级重建。

## 二、核心原理

### 2.1 块级 vs 字符级：为什么换路线

| | 字符滑窗 | **块级（本方案）** |
|---|---|---|
| 切割依据 | 字符数 | MinerU 给出的**块边界** |
| 公式 | 会被切断（32%） | **不可能被切**：行间公式是独立块，行内公式是独立 item |
| 图 | 只是正文里一行占位符 | 独立原子块 + 图注 + 图片路径 |
| 冗余 | section 嵌套导致 2.84× 重复 | v2 扁平流过一遍，**天然零重复** |

**直觉类比**：字符滑窗是"按字数把书撕成条"，块级是"按排版元素把书拆成零件"——
撕条会把一个公式撕成两半，拆零件不会。

### 2.2 数据源：`book_pages_v2.jsonl` 是唯一真源

实测：`book_sections.text` **完全是 v2 块的一个有损渲染**
（按 `items` 顺序重渲染，201/201 条空白归一化后完全一致；渲染函数在 `scripts/p2_corpus_sections.py:123-153`）。

v2 比它多三类东西：① `list` 块 23 个（在 sections 里**静默消失**）② `table` 的 html 表体 ③ 图片/公式的文件路径。
→ **必须从 v2 重建**。

另外两条实测（直接砍掉了原计划里的复杂度）：
- ⭐ **`items` 顺序本身就是正确阅读序**。p13 实测为 `图1.1.1 → 1.1.2 → 1.1.3 → 1.1.4`（正确），
  而按 bbox 的 y 排序会得到 `…1.1.4, 1.1.3`（错）→ **不需要做 bbox 版面重排**。
- ⭐ **`(pdf_page, bbox)` 是完美连接键**。equations 589/589、tables 30/30、figures 611/611，
  两侧差集均为 0 → 用它把 v2 块与三个 index 文件接起来取 `fig_sha256`。

### 2.3 三个"不可拆"等级

| 等级 | 对象 | 实测数量 |
|---|---|---|
| 原子**块** | `image` / `chart` / `table` / `equation_interline` | 480 / 131 / 30 / 589 |
| 原子 **item** | `paragraph_content` 里的 `equation_inline` | **1391**（分布在 584/2451 个 paragraph） |
| 硬**边界** | 层级 ≤3 的 title | 201 个 |

⚠️ **头号静默失效点**：v2 里**字面 `$` 字符数为 0** —— 行内公式是结构化 item，不是 `$...$` 字符串。
渲染时若只取 `type == "text"` 的 item，**1391 个行内公式会被静默全部丢掉且不报错**。
DoD C-3 专门盯这个（实测 1391 / 584，与预期分毫不差）。

### 2.4 技术栈：纯 Python 标准库，零新增依赖

`json / re / html.parser / hashlib / dataclasses / pathlib / collections / argparse / logging`。

**为什么不用 `langchain.text_splitter`**：它是字符级切分器，解决不了"不能在公式中间切"——
装 100 MB 依赖去买一个它解决不了的问题。**为什么不用 bs4/lxml**：MinerU 的表 html 只有
`<table>/<tr>/<td>`、属性无引号、无嵌套、无实体（`&xxx;` 命中 0），`html.parser` 40 行搞定。
**为什么不用 mistune**：只需按 `##` 切 + 防代码围栏内误判，`markdown` 的 AST 是过度设计。

- 标题层级按**文本正则**推：`content.level` 不可用（level=1 只有 1 个，524 个全是 2）。

- 正文 chunk 目标 800 字；**连续行间公式段不设上限**（硬 cap 3000），保证推导链完整。
- `printed_page = pdf_page − 11`（实测全书恒定）。

### 为什么单独一套，而不是塞进教材的 `chunking.py`

数据源、编号体系、语言全都不同，硬塞会让两边都变复杂：

| 项 | 教材 | 英文论文 |
|---|---|---|
| 数据源 | `book_pages_v2.jsonl`（363 行扁平行） | 每篇一个 `content_list_v2.json` |
| 编号体系 | `第3章` / `3.1` / `1）` / `1．` | `I.` / `1.` / `3.1.` / `A.` **三种混用** |
| 语言 | 中文 | 英文（+ 少量中英双语论文） |

但**输出 schema 完全一致**（21 字段，`source_type="paper"`），
这样后面可以进同一套索引代码、同一套 DoD 断言 —— 这是刻意的。

### 核心原理：按 section 切，而不是按字数切

教材那边是「贪心打包到 800 字」；论文这边是「一个 section 一个 chunk，超过 6000 字才二次切」。
理由：**论文的论证单元是 section**。把 `III. DERIVATION` 和 `IV. PERFORMANCE ANALYSIS` 切开拼在一起，
检索到的片段会失去前提，而教材的连续叙述被切开损失相对小。
代价是长度不均匀（p50=1550、p90=3222、max=10908），对 BM25 有轻微影响，可接受。

### 5 个实测踩坑（全是"跑通了但结果错"型）

1. **content 字段名按块类型而异**：`paragraph_content` / `math_content` / `title_content` /
   `page_header_content` … → 不写死键名，改为「递归取 span」+「键名含 caption」。
2. **行内公式是 paragraph 内的 span，不是顶层块** → 只看顶层会得到「0 个」的假象，真实 **889 个 / 3 篇**。
   这是教材踩过的头号静默失败点（教材 1391 个），**跨数据源复发了一次**。
3. **块里没有 `page_idx`**：v2 是**顶层按页分组**（顶层 list 长度 = 页数），页码要自己补。
4. **`content.level` 只有 1 和 2**（1=论文标题，2=所有 section，连 `3.1.` 也是 2）
   → 不能靠它推层级；改用 **title 块本身**当硬边界（覆盖 100%，正则只有 49%）。
5. **相邻行内公式 → `$a$$b$`**：计数上 `$` 是偶数"看着正常"，但结构非法（中间的 `$$` 会被当块公式开关），
   导致行间公式虚增 3 个（97 vs 94）。修法：相邻行内公式间补空格。**教材同型坑的第 2 次复发。**

> 抽查还抓到 3 个"断言全绿但产物不对"的问题：表格是裸 HTML、摘要只认 paragraph 形态（漏 title 形态 6 篇）、
> 中英双语论文（idx=028《雷达学报》）整篇漏摘要。
> ⭐ **教训：断言守的是守恒与结构，不守"内容长什么样"。断言全绿 ≠ 产物可用，必须抽查样例。**

## 四之三、S1 · 统一索引（2026-09-20 完成）

### 1. 为什么一套库而不是两套（D3 修订）

原决策是「教材 / 文献分开建库」，理由是文献字符量是教材的 **6.2 倍**，怕英文内容挤占 top-k。
2026-09-20 **用户拍板改为统一入库**，技术上成立的前提是 bge-m3 的跨语言实测：

| 方向 | Top1 余弦 | 排序是否正确 |
|---|---|---|
| 英文→英文 | 0.773 | ✅ |
| 中文→中文 | 0.644 | ✅ |
| **中文→英文** | **0.556 ~ 0.595** | ✅ **4/4** |

⚠️ **证据等级要说清**：这是**理想句对**的实测（术语完全对应），是**上界不是期望值**。
真实查询更模糊。所以分开的能力没有丢——改为由 `sources.json` 提供，检索时按 `source_id`
前缀过滤（`["book"]` / `["paper"]` / `["paper_031"]`），P4-S2 照样能做 A/B。

> 一句话：**能 A/B 的统一，比拍脑袋的分开更严谨。**

### 2. 三路召回

1. **BM25**：精确术语（`STAP` / `对角加载` / `77GHz`）。字符 bigram（`src/retrieval/tokenize.py` 唯一实现）
2. **dense**：语义近义 + 跨语言。bge-m3，L2 归一化后**内积**即余弦
3. **图号/表号倒排**（第三路）：见下

融合用 **RRF**（`score = Σ 1/(k+rank_i)`，k=60）：
BM25 分数无量纲、会随语料长度漂移，dense 是余弦；两者量纲不同且**没有标注数据可校准权重**
→ 加权和的权重只能拍脑袋。⚠️ **两侧 top_n 必须相同**，否则某一路的"未进榜"被隐式当成
无穷大排名 = 偷偷给另一路加权，正是要避免的。

### 3. 第三路为什么必须存在

BM25 是词袋模型，**没有"数字字面相等"的概念**。实测：查 `Fig. 1 caption`，Top1 是
`paper_017_text_027`——正文写着 "In the **first** simulation"，`first` 和 `1` 被当成近似匹配。
而「按图标题检索」是立项时的硬需求。
→ `src/retrieval/filters.py` 从图注抽结构化图号，建 `key -> [下标]` 倒排，命中直接 pin 到头部。

三种编号体系共存，`extract_refs` 都要认：`Figure 4.` / `Fig. 1` / `Table I`（罗马）/ `图1.1.4` / `表1.3.1`。
关键反例必须挡住：子图面板 `(a) 灵敏度低` 不能抽成图号；`In the first simulation` 不能抽成 `1`。

### 4. Front Matter 为什么直接排除，而不是降权

34 条 / 35 篇几乎每篇都有，内容是**作者名单 + 单位 + 邮箱 + Index Terms + DOI**。
它们**没有回答价值**（唯一用途是"这篇论文作者是谁"，那是元数据查询，不是 RAG 的活）；而且已发生过真实污染：查「原子范数最小化」时第 2 名命中
`paper_028_text_002`，正文其实是「朱晗归 冯为可…空军工程大学」。
降权没有可比基准（这些 token 别处几乎不再出现），所以直接排除；产物本身**不删**，
`--include-front-matter` 可恢复。

## 四之四、S2 · 检索评测（2026-09-20 完成）

### 1. 伪标注怎么来的

P3 出题时强制每条带 `evidence.quote`（语料原文最小必要一句，`docs/07 §六`：
没有原文证据的题宁可不出）→ 把 quote 用 P3 **同一套归一化**（去空白+去标点）
回捞到 chunk，命中即 gold。**免费、客观**。

规模：200 条 → 有 quote 181 → **剔除低判别力 7 条** → **主评测集 174 条**。
未回捞的 19 条全是 `unanswerable`（本来就没依据，属正确排除）。

两组对照必须先建立，否则数字不可信：
- **下界对照**：`A3 仅查文献` Recall 必须≈0（gold 零条在 paper 上）→ 实测 **0.0%** ✅
- **空转对照**：给 3 条无关查询一个**不存在的** gold id，Recall 必须为 0
  → 实测 **3/3 全为 0** ✅（只看"会不会返回 Top1"证明不了任何事，RRF 永远能排出第一名）

### 2. ⭐ 必须剔除「低判别力」样本

quote 越短，越会在**无关** chunk 里碰巧命中（归一化把标点空白全去掉了）：

| quote 长度 | 题数 | 平均额外命中 |
|---|---|---|
| ≤10 字 | 36 | **5.94** |
| 11–20 字 | 87 | 0.44 |
| 21–40 字 | 56 | 0.45 |
| >40 字 | 2 | 0.00 |

极端：`距离分辨率`（5 字）→ gold **124** 个；`MUSIC`（5 字母）→ gold 33 个。
这种题的 Recall@1 是**白送**的，会把整体指标严重虚高 → 只保留 `gold ≤ 5`（`eval.max_gold`）。

### 3. 结果

| 组 | 配置 | R@1 | R@5 | R@10 | MRR@10 |
|---|---|---|---|---|---|
| A1 | 全库 book+mmwave+paper | 47.7% | 75.3% | 83.3% | 0.590 |
| A2 | 教材语料 book+mmwave | 47.7% | 75.3% | 83.3% | 0.591 |
| A3 | 仅文献 paper | 0.0% | 0.0% | 0.0% | 0.000 |
| B2 | 纯 BM25 | 49.4% | 70.1% | 77.6% | 0.585 |
| B3 | 纯 dense | 42.0% | 64.9% | 74.7% | 0.517 |
| C2 | 关闭图号 pin | 47.7% | 75.3% | 83.3% | 0.590 |

**A 组结论（验证 D3）**：全库与教材语料的 Recall@5/10 **完全一致**、MRR 差 0.001
→ **加入 35 篇英文文献（1639 条）对教材题召回零影响**，当初担心的"文献挤占 top-k"未发生。

### 4. ⭐ 反直觉现象：纯 BM25 的 R@1 反而更高

BM25 R@1 49.4% > 融合 47.7%，但 R@5/R@10 反过来（70.1% < 75.3%）。
不靠猜，直接算差异样本：**融合救回 15 条**（BM25 完全没召到，dense 补上）、
**丢失 5 条**（BM25 第一击就中，融合把它挤出了前 10）。

→ BM25 精确匹配在**第一击**上更强，但候选池**同质化**（top-20 都是同一批字面匹配的 chunk，
深层没有新东西）；dense 补的是语义近义，牺牲一点首位精度换来深层召回。
RRF 的意义不是让每条都更好，而是**整体覆盖率更高**。

⚠️ 但 3/174 的差距属**噪声量级**，不宜当强证据；稳健的是 R@5/R@10 的融合优势。

### 5. ⭐ calc 题召回差的根因（推翻了我的假设）

calc 题 29 条，Recall@10 失败 12 条（41%），占全部失败的 41%。
我先猜是"公式检索是短板"——**实测推翻了**：calc 的 gold **一条 equation 都没有**，全是 text。

真因是**问题与 gold 的词汇重叠极低**（实测 12 条失败样例：中位 **14%**，最低 **0%**）：
P3 的 calc 题在 `evidence.quote` 里记的是**概念出处**，而题面问的是**数值计算**。
例如 `evt_000403` 问「脉宽 1.5μs → 频谱宽度多少 Hz」，quote 却是「这称为信号的固有分辨率」，
gold 段落里根本没有频谱宽度公式。

⚠️ **这是标签问题，不是检索器问题。不应据此去改检索策略**（比如给 formula 加权）——
那是**对着一个坏标签做优化**，越调越偏离真实需求。
正确做法是为 calc 题单独构造 gold（按公式注册表匹配），**不在本次范围内**。

## 四之五、S2 补充：两个评测缺口（2026-09-20）

上一节留了两个没验证的地方，这里补上。**两个都推翻了我先前的判断**。

### 缺口 1 · calc 题的「标准答案」到底该怎么定

同一批 30 道 calc 题，只改「什么算正确答案」，其余不变：

| 标准答案的定义 | 能标出 | gold 规模 | R@1 | R@5 | R@10 |
|---|---|---|---|---|---|
| `evidence.quote` 概念出处 | 30/30 | 中位 1（max 124） | 30.0% | 50.0% | 60.0% |
| `formula_latex` 公式本体 | **9/30** | 中位 1（max 11） | **0.0%** | 33.3% | 44.4% |
| PDF 页码区间 | 23/30 | 中位 16（max 46） | 34.8% | 47.8% | 52.2% |

- **概念出处**：能标全，但语义错位（记的是"概念在哪讲"，题面问"数值怎么算"）
- **公式本体**：最精确，但只能标 9/30 —— 书里的公式是 OCR 出来的，
  写法跟标准 LaTeX 差很远（`G_{\mathrm{pc}}=B\,T` 在书里是散开的 `G p c = B T`）
- **页码区间**：能标 23/30，但一页平均 16 个 chunk → 和"短引文"同一个毛病：太宽，分数虚高

⚠️ **修正上一节的一句话**：我之前写「calc 的 gold 全是 text，所以**不是**公式检索差」——
这个说法不够精确。gold 是 text 只说明**出题时记的出处不是公式**，不代表系统能翻到公式。
换成最贴合计算需求的"公式本体"标注后 **R@1 = 0%**（9 条没有一条第一命中）、R@5 = 33.3%。
→ **calc 的真实短板是「计算公式翻不到」，不是「概念出处翻不到」**，二者解法不同。
（样本 9 条，只作线索，不作强结论。）

## 四之六、S1c · 公式概念索引（**实测负收益，默认关闭**）

### 想法：按公式的「名字」找，而不是按字面找

用户提出：每篇文章字母定义不同，同一概念的公式内容完全不同，
能不能像图有 `Fig. 1` 那样，给公式也加一个名字索引。

实测证实了必要性 —— 同一概念的写法差异分三层，后两层字符串匹配无解：

| 层 | 例子 | 可解？ |
|---|---|---|
| 排版 | `\frac { c } { 2 B }` vs `\frac{c}{2B}` | ✅ 归一化 |
| **结构** | 教材 `ΔR = cτ/2`（斜杠）vs 标准 `ΔR = c/(2B)`（分式） | ❌ **这是公式只能捞回 30% 的主因** |
| **符号** | 同一概念用 B（带宽）或 τ（脉宽） | ❌ |

### 做法：术语锚定（用户选定）

术语是自然语言，不受符号/写法影响。规则："文字里有该概念的术语 + 有公式" → 挂概念名。
种子用现成的 22 个 `answer_check.formula` 概念名（`configs/formula_concepts.yaml`）。

⚠️ **挂法是被实测逼出来的**，第一版（全文本含术语）直接踩坑：

| 挂法 | 覆盖概念 | 每概念挂几条(中位) | 抽样 |
|---|---|---|---|
| 全文本含术语（第一版） | 22/22 | 最多 226 | ❌ 「匹配滤波信噪比」挂到 `s(t)=g(t)cos…`（正文只提了一句） |
| 术语必须在章节标题 | 14/22 | 6 | 准但覆盖少 |
| **只挂公式块（采用）** | **19/22** | **7** | ✅ |

### 改成分「加分」之后：**计算题有效，全集仍轻微为负**

pin 是强制置顶（会挤掉别人），boost 只在 RRF 分数上加一点（不挤人，但**不能召回**、只对已进候选池的条目生效）。
扫描加分值（参照：RRF 单路第一名 = 1/61 ≈ 0.0164）：

**计算题 9 条（公式本体标注）：**

| 加分值 | R@1 | R@5 | R@10 | MRR@10 |
|---|---|---|---|---|
| 0（关闭） | 0.0% | 33.3% | 44.4% | 0.159 |
| 0.02 / 0.05 | 11.1% | 33.3% | 44.4% | **0.215** |
| pin（置顶） | 11.1% | 33.3% | **33.3%** | — |

注意 pin 的 R@10 **低于关闭时**（33.3% < 44.4%）—— 直接证实了"强制置顶会把答案挤出去"。

**全部 174 条：**

| 配置 | R@1 | R@5 | MRR@10 |
|---|---|---|---|
| 关闭（基线） | **47.7%** | **75.3%** | **0.590** |
| pin | 46.6% | 73.6% | 0.573 |
| boost=0.01 | 47.1% | 74.7% | 0.586 |
| boost=0.02 | 46.6% | 73.6% | 0.578 |

### ⚠️ 结论与取舍

- **在计算题上**：boost 把 MRR 从 0.159 提到 0.215（**+35%**），方向是对的
- **在全集上**：仍是轻微负收益（MRR 0.590 → 0.578）

⭐ **真正的问题不在调参，而在标注**：同一批计算题，
用「公式本体」当标准答案 → boost 有效；用「概念出处」当标准答案 → boost 有害（R@1 30%→23.3%）。
**两种标准答案给出相反结论，那就不该急着调参** —— 先把"计算题的正确答案到底是什么"定下来，
再回来测，否则就是对着一个摇摆的靶子射击。

**处置**：默认关闭（`index.use_concepts: false`），代码、概念表、两种模式（pin/boost）都保留。
**再启用的前置条件**：建立公式级真值标注（人工把 OCR 公式规范化映射到概念表），
之后用同一批题重测 —— 那时结论才可信。

## 五、面试延伸

**Q1：为什么不用 langchain 的 RecursiveCharacterTextSplitter？**
→ 它是字符级的，感知不到"这是一个不可分割的公式块"。本项目实测 32% 的 chunk 公式被切断。
块级切分的本质是**用排版结构代替字符数作为切割依据**。追问："那什么时候字符滑窗够用？"
答：纯散文、无公式表格图、对边界不敏感的场景（如长文本摘要）。

**Q2：chunk 大小怎么定？**
→ 三个约束共同决定：① embedding 模型的 token 上限（bge-m3 512 → 800 汉字留余量）；
② 语义完整性（不能跨章节边界）；③ 检索粒度（太小召回碎片、太大向量稀释）。
本项目 800 字 + 章节硬边界，实测 p50 744。加分：说明"公式密集段不设上限"这个例外及理由。

**Q3：图和正文怎么关联？**
→ 图独立成 chunk（检索文本 = 图注 + 上下文 + 页码），`parent_id` 指回所属正文 chunk，
正文 chunk 反向记 `child_ids`。命中图时可以拉出讲解正文，命中正文时可以列出本节有哪些图。
追问："为什么不把图注直接拼进正文 chunk？" 答：拼接会让图注信号被正文稀释，
"按图标题检索"（如搜"波束搜索扫描图形"）命中率下降。

**Q4：怎么保证切分没丢东西？**
→ 三层断言：① 计数不变量（行内公式总数必须 == 1391）；② 定界符栈扫描（不只数数，
能抓到 `$a$$b$` 这种计数看不出的非法结构）；③ 跨信源内容校验（eval 的 119 条原文引用全部能在 chunk 里找到）。
加分：**"跑得通"不等于"没丢东西"** —— 只取 `type=="text"` 会静默丢 1391 个公式且全绿。
