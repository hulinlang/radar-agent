# 阶段 B · B13 详细方案：Q6_K 接入 int8 / MMA 路线

> 状态：**方案，待确认**（2026-10-11）
> 上游：`docs/34`（B11，int8 激活只做 Q4_K）、`docs/36`（B12，MMA 只做 Q4_K）
> 一句话：**把那 30% 还在 fp32 路线上的参数（Q6_K）接进 int8，B12 未达成的
> D3（prefill ≥1000 tok/s）由本项接着追。**

---

## 0. 为什么做这一项

### 0.1 B12 的结论：kernel 对了，但没有增益，而且归因指向这里

B12 的 MMA kernel **逐位正确**（4 个 Q4_K 张量 layer① BIT-EXACT；引擎内 dp4a 与 MMA
两条路线的生成 id 完全相同），但**引擎内没有增益**：

| round | fp32 | dp4a (B11) | MMA (B12) |
|---|---|---|---|
| 1 | 471.1 | 714.6 | 825.0 |
| 2 | 467.2 | 707.9 | 824.8 |
| 3 | 467.6 | 712.9 | 828.1 |

MMA/dp4a = **1.16×**；再做一轮含占用率（`RADAR_MMA_WARPS` 4→16）的诊断，
两条路线**互相落在对方噪声里**（dp4a 792–823 / mma 786–837）。
⇒ **W=16 下引擎根本不受内层算术限制**，换指令自然无用。

### 0.2 ⭐ 归因：30% 的参数（Q6_K）还在 fp32 路线上

直接解析 GGUF 的逐类型统计（`dsh_scratch/typesplit.sh`）：

| type | tensors | params | bytes | 占比 |
|---|---|---|---|---|
| F32 | 113 | 123,904 | 495,616 | 0.0% |
| **Q4_K**（int8 路线） | 168 | 1,203,765,248 | 677 MB | **70.0%** |
| **Q6_K**（fp32 路线） | 29 | 516,685,824 | 424 MB | **30.0%** |
| 合计 | 310 | 1,720,574,976 | 1,101,457,408 | |

每 chunk 的账（1645/825 tok/s ⇒ ≈19.3 ms/chunk，attention ≈5.7 ms）：

| 项 | 估算 |
|---|---|
| attention | 5.7 ms |
| Q4_K（70% 参数，走 int8） | ≈5.4 ms |
| **Q6_K（30% 参数，仍走 fp32 `gemv_mc`）** | **≈8.2 ms** |

流量对账：GEMM 段 ≈1.41 s 处理 113 GB ⇒ 有效 **≈80 GB/s**（峰值的 31%）；
而 MAC 数按 dp4a 管道只需 ≈180 ms、按 MMA ≈45 ms —— **两者都远小于 1.41 s。**

⇒ **fp32 路线每参数贵得多，而它还在承担 30% 的参数。**
这是 B11 范围控制决策（`docs/34` §6）的代价，当时看不出来（B11 的收益已由 Q4_K 兑现），
现在被参数分布暴露。

### 0.3 数值工作已经做完了

`matvec_q6_k_q8_1_host`（`cpp/src/int8_act.{h,cpp}`）**已实现并与 B11 的独立 NumPy 参考
逐位一致** —— `test_b11.sh` 的输出就是证据：

```
PASS: layer1 blk_0_attn_v_weight_q6k: 2 exact, 1 bit-exact
PASS: layer1 blk_0_ffn_down_weight_q6k: 2 exact, 1 bit-exact
```

**缺的只有 CUDA 侧 kernel** —— `int8-ref-test` 里那行
`cuda Q6_K int8 gemv SKIPPED (still on the fp32 route)` 就是它。
⇒ **本项不需要任何新的数值设计工作，风险显著低于 B11/B12。**

### 1.1 ⚠️ 口径提醒：本项**必然**改变端到端 id

B12 之所以能保住「逐 id 相同」，是因为它换的是**指令**、数值一字不改。
本项不是：把 Q6_K 的激活从 fp32 换成 int8 **本身就丢精度**（同 B11 对 Q4_K 做的事）。
所以：

- **层① 仍然是 bit-exact**（我们的 CUDA 实现对一份钉死的规格 vs 独立 NumPy 实现），
  这是能保住的硬口径；
- **端到端 id 会变** ⇒ D2/D4 走 **Tier B**（teacher-forcing + logit 位移 + 质量对照），
  与 B11 当初的口径一致，不是退步。

## 2. Q6_K 的形状（已核实源码）

### 2.1 一个 256 值 super-block = 210 字节

| 字段 | 偏移 | 内容 |
|---|---|---|
| `ql` | 0–127 | 低 4 bit，两组各 64 字节 |
| `qh` | 128–191 | 高 2 bit，两组各 32 字节 |
| `sc` | 192–207 | 16 个 **int8** 缩放（有符号！） |
| `d` | 208–209 | fp16 |

值 `i`（0..255）的解包（`gpu_quants.cuh` 的 `q6k_at`）：

```
nn = i>>7;  r = i&127;  qq = r>>5;  l = r&31
byte = ql[nn*64 + l + (qq&1)*32]
nib  = (qq < 2) ? (byte & 0xF) : (byte >> 4)
q6   = (nib | (((qh[nn*32 + l] >> (2*qq)) & 3) << 4)) - 32
scale= sc[nn*8 + l/16 + 2*qq]
dequant = d * scale * q6
```

### 2.2 ⭐ 两个决定 kernel 形态的约束

#### (a) 缩放粒度是 **16 个值**，不是 32

`matvec_q6_k_q8_1_host` 的结构（这是规格，不是实现细节）：

```
for nn in 0..1: for qq in 0..3:          # g = nn*4 + qq，共 8 个子块
    for half in 0..1:                    # ★ 每 16 个值一个 dot
        dot = sum_{l=half*16}^{half*16+15} q6 * q8[l]      # 精确 int32
        scg = sc[nn*8 + half + 2*qq]
        sd[g] += d8 * f32(dot * scg)
    acc += d6 * sd[g]
```

⇒ **`−32` 偏移修正项必须按 16 值半块来算**，因为两个半块乘的 `scg` 不同。
这是与 Q4_K 最关键的差别（Q4_K 是 32 值粒度，正好等于 MMA 的 K=32）。

#### (b) `Σ q8` 只存了 32 值整块的和，没有半块和

`Q8_1Ds.sum_q` 是 32 值块的和（B11 钉死的布局，与 llama.cpp CUDA 对齐）。
而 §2.2(a) 要求半块的和。**这是本项唯一真正的设计决策**，见 §3.3。

## 3. 设计

### 3.1 范围控制

- 只加 **ggml type 14（Q6_K）** 的分支；Q4_K 的 int8/MMA 路线、F16、decode **一律不动**
- 新 kernel 独立文件 `gpu_q6k_int8.cu`，便于回滚
- `gemv_prefill` 的分派条件从 `w.type == 12` 扩到 `(w.type == 12 || w.type == 14)`

### 3.2 数值语义（必须与 `matvec_q6_k_q8_1_host` 逐位相同）

1. `dot` 按 **16 值**分组，**精确 int32**（整数加法顺序无关）
2. `sd[g] += d8 * f32(dot * scg)` —— `scg` 是 **int8**（有符号，注意别当成 uint8）
3. `acc += d6 * sd[g]`，`__fmul_rn`/`__fadd_rn`，`g` 升序、`b` 升序
4. 全程 `-ffp-contract=off`（host）/ 显式 `__fmul_rn`（device），与 B11 同

### 3.3 ⭐ 核心设计：怎么拿到 16 值的 dot

**统一先讲偏移项。** 记 `v = q6 + 32 ∈ [0,63]`，则

```
dot = Σ_{16} q6·q8 = Σ v·q8 − 32·Σ q8
```

三项都在 int32 内**精确**（上下界：`Σ v·q8 ≤ 63·127·16 = 128016`；
`32·Σ q8 ≤ 32·127·16 = 65024`；合计远小于 2³¹）。

⭐ **关键观察：`Σ q8`（半块）与权重无关** —— 它只依赖列、`g`、`half`。
所以它可以**按列算一次、在所有行上复用**（一个 16 行 tile 摊 16 倍）。

于是两条实现路线：

| 路线 | 做法 | 优劣 |
|---|---|---|
| **A. dp4a** | 每 4 个值：`v` 打包成 int8 一次（取 `ql` nibble + `qh` 2 bit 合成），**1 次 dp4a**；偏移项用一次 `ones`-dp4a 或复用整块 `sum_q` | 与 B11 的 Q4_K dp4a kernel 同构，好复用；但偏移项在"一 lane 一 (row,col)"的结构下**不能跨行摊薄** |
| **B. MMA** | 用 **`m16n8k16`**（K=16，正好 = 半块粒度！），A = `v`（0..63 装得下 int8），偏移项在 MMA 外按列算一次 | 粒度天然吻合；偏移项摊薄 16×；且 B12 的分片经验可直接复用 |

> ⭐ **`m16n8k16` 是本项的一个好消息**：B12 用的是 `m16n8k32`（K=32），
> 而 Q6_K 需要 K=16 —— PTX 里**恰好有 `m16n8k16` 的 int8 版本**。
> 也就是说 Q6_K 的 16 值粒度不是障碍，反而和 ISA 对上了。
> A 分片 2 个寄存器、B 分片 1 个寄存器、C/D 仍 4 个（形状见 §3.4）。

**建议顺序**：先做 **A（dp4a）** 拿到位精确与性能基线（它能在 B11 的结构上直接改），
再做 **B（MMA）**。理由与 B12 相同：dp4a 版本更容易对拍，MMA 版本才是终点。

### 3.4 `m16n8k16` 分片（若走路线 B）

| 分片 | 寄存器 | 每线程元素 |
|---|---|---|
| A（16×16 int8, row） | 2 × int32 | 8 个 int8 |
| B（16×8 int8, col） | 1 × int32 | 4 个 int8 |
| C/D（16×8 int32） | 4 × int32 | 4 个 int32 |

⚠️ lane 映射**实现时照 PTX 文档抄**，然后由 B12 那条已验证的方法兜底：
`int8_act` 里加一组 `mma16_a_map/b_map/c_map` + 覆盖自检 + 走分片的 host 孪生实现，
**先在 CPU 上把映射逐位验对，再写 CUDA**（`docs/36` §7.6 的做法）。

### 3.5 A/B 开关

沿用既有约定：`RADAR_Q6K_INT8=1` 启用（默认关），`RADAR_Q6K_MMA=1` 走 MMA 变体。
默认关保证 B11/B12 的全部记录可复现。

### 3.6 三层对拍（沿用 B11/B12，**本项目看家方法**）

| 层 | 内容 |
|---|---|
| ① | CUDA Q6_K int8 gemv ↔ `matvec_q6_k_q8_1_host`（**逐元素 bit-exact**，2 个张量）；host 参考本身已与 NumPy 参考 bit-exact |
| ② | teacher-forcing vs llama.cpp CUDA ≥ 49/50，且 ≥ 当前路线 |
| ③ | logit 位移分析（`docs/34` §7.5 的方法）+ 质量对照 |

⚠️ 层① 必须覆盖：**半块边界**（16 值）、`sc` 的有符号性、`qh` 的 4 种 2-bit 位置。

## 5. 风险

| # | 风险 | 量级 | 对策 |
|---|---|---|---|
| R1 | Q6_K 的提取比 Q4_K 贵（要合成 nibble + 2 bit），可能把瓶颈推回 ALU | 中 | 步骤 1 先量；用 `m16n8k16` 让偏移项跨行摊薄 |
| R2 | 半块 `Σ q8` 的取得方式选错（重算 vs 扩布局） | 中 | §3.3：优先"按列算一次、跨行复用"，**不动 `Q8_1Ds` 布局**（它是对齐 llama.cpp 的资产） |
| R3 | `sc` 是 int8（有符号），当成 uint8 会静默错值 | 中 | 层① 逐元素对拍 + 单测里显式构造负 scale 的用例 |
| R4 | 半块粒度导致 dp4a 次数 ~1.5–2× 于 Q4_K | 中 | 先量再定；路线 B 可回避 |
| R5 | 端到端 id 会变 ⇒ 失去 B12 那种"逐 id 相同"的强口径 | **必然** | §1.1 已声明走 Tier B；用 logit 位移把"变多少"量化出来 |
| R6 | 收益不及预期（B12 的教训：孤立探针只能给上界） | **高** | 步骤 6 的引擎内配对是唯一判据 |

## 6. 明确不做（防范围蔓延）

- **KV 量化、投机解码、FP8**（Tier C，属 `docs/35` Phase 3）
- **attention 重写**（= B14，独立立项）
- **放大 W / 层主序 prefill**（`docs/36` §7.5/§7.8 已表明它不是当前瓶颈）
- **改 `Q8_1Ds` 布局**（它是对齐 llama.cpp CUDA 的资产，动了会破坏 B11 的复用基础）
- **F32 的那 113 个小张量**（norm/bias，共 12 万参数，无量化意义）
- **Q6_K 的 decode 路径**（decode 是带宽受限的 gemv，int8 无收益）

## 7. 验收结果

### 7.1 ✅ 步骤 1：roofline 已量（2026-10-11）

**这次先对着 `gpu_quants.cuh` 的 `q6k_at` 核实布局再建模**（B12 的教训：探针答的是
"我问的问题"）。核实确认了 §2.2(a) 的 16 值粒度，并给出一个方案里没料到的好消息：
**K=16 与 K=32 的 tensor-core 上限相同**（实测 1023.7 vs 1023.8 MAC/SM/clk）。

#### F) Q6_K 提取系数

| 形式 | values/SM/clk | 系数 `c` | 所需 W ≥ 16c |
|---|---|---|---|
| 3 项拆分（`nib` 与 `hi2` 分开） | 37.6 | **1.70** | 27.2 |
| **先合成** `v = nib \| (hi2<<4)` | 47.1 | **1.36** | 21.8 |
| （对照）Q4_K 真实提取 | 95.2 | 0.67 | 10.8 |

⇒ ⭐ **"先合成"比"三项拆分"更便宜**（c 1.36 vs 1.70），而 MMA 本来就必须先合成。
**所以 §3.3 表里"dp4a 可用三项拆分"那个备选应当砍掉** —— 两条路线都走先合成。
Q6_K 的提取成本是 Q4_K 的 **2.0×**（1.36 / 0.67），与 §5 风险 R1 的预期一致。

#### G) `m16n8k16` + 现场提取的 Q6_K A 分片

| R | W=8R | MAC/SM/clk | vs k16 天花板 | vs dp4a 管道(256) |
|---|---|---|---|---|
| 1 | 8 | 337.7 | 33.0% | 1.32× |
| **2** | **16（当前 chunk）** | **595.6** | **58.2%** | **2.33×** |
| 4 | 32 | 891.4 | 87.1% | 3.48× |
| 8 | 64 | 939.4 | 91.8% | 3.67× |

⚠️ W=16 时 Q6_K 只有 **595.6**，是 Q4_K 同条件（906.8）的 **66%**。
**⇒ Q6_K 走 int8 的收益天然小于 Q4_K。**

#### ⚠️ 订正：方案 §0.2 的段落拆分算错了

原文写"Q4_K ≈5.4 ms、Q6_K ≈8.2 ms（占 GEMM 60%）"，那是错的。按实测配对比值反推
（fp32 28.35 / dp4a 16.73 / MMA 13.66 ms per chunk，attention 5.7 ms 固定）：

| 段 | fp32 路线 | dp4a 路线 | MMA 路线 |
|---|---|---|---|
| Q4_K（70% 参数） | 19.83 ms | **8.22** | 5.15 |
| **Q6_K（30% 参数，仍 fp32）** | 8.51 ms | **8.51** | 8.51 |
| gemv 合计 | 28.35 | 16.73 | 13.66 |

⇒ **两段几乎相等（8.22 vs 8.51 ms），不是 60/40。**
（该拆分是"fp32 成本 ∝ 参数数"的**推断**，非直接测量 —— 引擎目前没有按类型分段的计时。）

这也解释了 B12 为什么只有 1.16×：Q4_K 段 8.22 → 5.15 = **1.60×**，
摊到 gemv 总量 16.73 → 13.66 = −18%，即 tok/s ×1.16。

#### 投影：两个界差得很大，必须并列

| 口径 | Q6_K int8+MMA | 每 chunk | prefill | 结论 |
|---|---|---|---|---|
| **管道界**（Q6_K 达 595.6） | ~0.2–3 ms | 11–14 ms | **1150–1300 tok/s** | ✅ |
| **经验折扣**（按 Q4_K 实测只兑现 1.60×，再乘 0.66 的提取劣势） | ~5.35 ms | 16.2 ms | **~986 tok/s** | ❌ 差一点 |

⭐ **这正是 B12 的教训在起作用**：孤立探针给的是**上界**（它预测 Q4_K 3.54×，
实测只兑现 1.60×）。所以 **B13 的落点很可能在 986–1300 之间**；
即使只到 986，叠加 B14（attention 5.7 ms，届时是第一大项）也能过线。

**⇒ 判据只能是步骤 6 的引擎内同会话配对测量**（§5 风险 R6）。

### 7.2 ✅ 步骤 2：host 分片原型（2026-10-11）

照 B12 验证过的做法（`docs/36` §7.6）：**先把 lane 映射在 CPU 上逐位验对，再写 CUDA**。

新增 `cpp/src/int8_act.{h,cpp}`：

| 产物 | 作用 |
|---|---|
| `mma16_a_map` / `mma16_b_map` / `mma16_c_map` | `m16n8k16`（8-bit）的 PTX 分片映射 |
| `mma16_fragment_coverage_ok()` | 证明三张映射各是**双射**（16×16 / 16×8 / 16×8） |
| `matvec_q6_k_q8_1_mma_host()` | 与 `matvec_q6_k_q8_1_host` **同数学**，但每个 A/B 元素**经分片映射取数** |
| `q6k_value()` | Q6_K 的取值公式，与 `gpu_quants.cuh` 的 `q6k_at` 逐字一致 |

**实测（2 个 Q6_K 张量，零编译警告）**：

```
mma16 fragment maps  A 16x16 / B 16x8 / C 16x8  BIJECTIVE
host Q6_K int8 gemv via m16n8k16 FRAGMENTS  16 x 2048 x 1024  BIT-EXACT   (attn_v)
                                            16 x 6144 x 2048  BIT-EXACT   (ffn_down, nb=24)
```

**买到了什么**：① `m16n8k16` 的 lane 映射**逐位证实正确**（映射写错会配错乘积，
于是对不上布局无关的参考 —— 所以这条 bit-exact 同时验证了映射与 **16 值半块边界**、
`qh` 的 4 种 2-bit 位置）；② CUDA kernel 写完后只要与这个原型逐位一致，
映射就自动成立；③ `ffn_down` 的 `nb=24`（`in=6144`）顺带覆盖了长 k 循环。

> **下一步（步骤 3/4）**：`gpu_q6k_int8.cu`，先 dp4a 再 `m16n8k16`，
> 要求与 `matvec_q6_k_q8_1_mma_host` **逐位一致**。

### 7.3 ✅ 步骤 3/4/5：kernel 已位精确并接入引擎（2026-10-11）

**一处方案简化（已落实）**：§3.3 把"怎么拿到半块 `Σ q8`"列为**唯一真正的设计决策**，
但写 kernel 时发现**它根本不需要**：Q6_K 的 `q6 = v − 32 ∈ [−32,31]` **装得进 int8**，
所以把 A 操作数直接建成**有符号的 q6** 即可，抵消项自动消失：

```
int8(v − 32) = (v + 0x60606060) ^ 0x80808080     ← 逐字节、无进位（v ≤ 63 故成立）
```

代价只有 2 条打包指令 / 4 个值。⇒ **`Q8_1Ds` 布局一个字都不用动。**

**kernel**（`cpp/src/gpu_q6k_int8.cu`）：`m16n8k16`，warp 负责 16 行 × `NTILE*8` 列，
`sd` 按 `(nn, qq, half)` 顺序累加（这是规格），`acc += d6*sd`。

**⚠️ 踩到一个真 bug（值得记）**：Q6_K 的 super-block 是 **210 字节**，而 `210 % 4 == 2`
⇒ **奇数 `b` 的块起点只有 2 字节对齐**，4 字节 `u32` 加载直接 `misaligned address` 崩。
Q4_K 不会踩到（144 % 4 == 0），`gpu_quants.cu` 里既有的 Q6_K kernel 用逐字节加载也不会。
改用两次 `u16` 拼装。**⇒ 换量化类型时，"块大小能否整除 4"是一条要先查的对齐约束。**

**实测（层①，2 个 Q6_K 张量，零编译警告）**：

```
cuda Q6_K int8 m16n8k16 gemv  16 x 2048 x 1024  BIT-EXACT   (attn_v)
                              16 x 6144 x 2048  BIT-EXACT   (ffn_down, nb=24)
```

### 7.4 ❌ 步骤 7：先量"提取到底占多少"——结论是**不做**那个对齐重排

计划中的优化是"把 Q6_K 权重按 4 字节对齐重排，去掉 §7.3 那个 `u16` 拼装"。
按本项目"先量再写"的规矩，先加一个**测量专用**的消融开关
`RADAR_Q6K_ABLATE`（数值故意算错，只看时间；已随代码保留为可复现的仪器）：

| 级别 | 含义 |
|---|---|
| `0`（默认） | 完整实现 |
| `1` | 去掉打包符号转换 |
| `2` | **去掉整个 A 分片提取，含全部加载** |

**实测（Q4_K MMA + Q6_K int8，顺序逐轮交替以避免热漂移混入）：**

| round | `off`（真实） | `ablate1` | `ablate2` |
|---|---|---|---|
| 1 | 1102.6 | 1094.5 | 1261.0 |
| 2 | 1105.5 | 1129.1 | 1226.7 |
| 3 | 1051.8 | 1129.8 | 1282.5 |
| 4 | 1134.3 | 1131.2 | 1296.6 |

**⇒ 把整个提取（含所有加载）拿掉也只快约 15%。**

| 结论 | 依据 |
|---|---|
| **提取不是瓶颈** | `ablate2` 上界 15% |
| 对齐重排最多赢其中一部分（≈4%） | 它只去掉 `u16→u32` 那一半加载 |
| **⇒ 不做这个优化** | 收益远小于改动面（要在加载期加一条 padded 重排路径 + 424 MB 副本） |

**那时间花在哪？** Q6_K 段的 MMA 本身只需 ≈0.135 ms/chunk（8.27e9 MAC ÷ 61.4 TMAC/s），
而实测该段 ≈6.2 ms —— **差 46×**。同时权重流量只有 424 MB / 6.2 ms ≈ 68 GB/s，
**也不在带宽墙上**。⇒ **是并行度/延迟受限**：`out/16` 限制了总 warp 数
（`ffn_down` 只有 128 个 warp，24 个 SM ⇒ **每 SM 仅约 5.3 个 warp**），
而每个 `(nn,qq,half)` 迭代是"4 次加载 → 2 条 MMA → 读回"的短依赖链，没有足够 warp 去掩盖。

**⇒ 正确的下一步是提高并行度或加长每条依赖链上的 MMA 批次（即加宽 W / `NTILE`），
而不是抠提取指令数。** 这条留给 B13 的后续或 B14 之后再定。

### 7.6 ✅ 步骤 8：加宽 W —— **D3 达成（2247 tok/s = 3.55× fp32）**

§7.4 的消融把方向指到了并行度/延迟，加宽 W 是唯一被实测支持的杠杆。
改法（`MAX_MC` 的双重身份按 `docs/36` §7.5 拆开）：

| 改动 | 内容 |
|---|---|
| 常量拆分 | `MAX_MC = 16` 保留为 **batch 上限**；新增 `MAX_PREFILL = 64` 为**缓冲区最坏宽度** |
| 运行时可调 | `RADAR_PREFILL_W`（1..64，默认 16）—— **不用重编译就能扫 W**；默认 16 让 B11/B12 记录可复现 |
| kernel 摊薄 | `RADAR_MMA_NTILE` ∈ {2,4,8}：一个 warp 每次 A 分片加载啃几个 8 列片 |
| 缓冲区 | B8a 的 8 个 `d_*m` + `d_q8s/d_q8ds` 全部按 `MAX_PREFILL` 分配 |

#### ⚠️ 安全网抓到一个**预先存在**的洞（这是本轮最有价值的发现）

为这次重构立的安全网是"**改 W 不许改任何 id**"（B8a 已证多列与单列逐位相同）。
第一次跑就红了：

```
dp4a W=32 : IDS DIFFER   <-- 不安全
dp4a W=64 : IDS DIFFER
mma  W=32 : ids IDENTICAL to W=16   ✓
```

根因：`gemv_q4k_mc` / `gemv_q6k_mc` 的分派**最大只有 `NC=16`，且没有兜底分支**，
而 kernel 把 32 条 lane 映射成 `R*NC` 个输出，所以 NC 最多到 16。
W>16 时**第 16 列之后的输出从来没被写过**（缓冲区里是残留值）。

**这个洞一直存在**，只因为"prefill 宽度恰好也是 16"而不可见 ——
与 §7.3 那个 `210 % 4 == 2` 的对齐洞是同一类：**常量在两个语义上恰好相等，掩盖了耦合。**
（MMA 路线当时没红，是因为那条路 Q6_K 也走 int8、根本不调 `gemv_mc`。）

修法：按 16 列分组、用**偏移基指针**迭代（kernel 索引是 `x[c*in+off]`，所以偏移成立），
每列算术不变 ⇒ 仍与单组启动逐位相同。修后四条配置全部 IDENTICAL。

#### ⚠️ 翻默认时又踩到一个"静默 no-op"（第二次同类）

`NTILE` 默认从 2 改成 4 后，`int8-ref-test` 的 CUDA 半边**全挂**：
`cuda Q4_K int8 MMA gemv MISMATCH 16384/16384`。根因是那条越界保护

```cpp
if (stride < ((ncol + 31) / 32) * 32) return;   // 测试传 stride=16，需要 32
```

**静默 `return` 什么都没算**，`y` 保持 memset 的 0 ⇒ 全元素错。
测试传 `stride=16`（golden payload 的实际布局）是**合法的**，是我的保护写错了。

**修法：`NTILE` 由可用步长自动收敛**，而不是跳过工作 ——
取满足 `round_up(ncol, 8N) <= stride` 且 `N <= 请求值` 的**最大** N：

```cpp
if (ntile_env >= 8 && ((ncol + 63) / 64) * 64 <= stride) nt = 8;
else if (ntile_env >= 4 && ((ncol + 31) / 32) * 32 <= stride) nt = 4;
else if (((ncol + 15) / 16) * 16 <= stride) nt = 2;
if (nt == 0) return;   // 真正的调用方违约
```

> **教训**：**"保护"不该表现为静默跳过工作。** 一个 `return` 让输出保持未初始化，
> 比报错难查得多 —— 与 §7.6 那个"NC=16 无兜底导致列不写"是同一类：
> **守卫条件写错时，失败模式是"少算了"而不是"报错"。**
