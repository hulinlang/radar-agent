## 1. 交付总览

**一个零 LLM 库依赖的 C++ 推理引擎**（`radar-agent/cpp/`，~3000 行，WSL2 gcc/nvcc）：

```
GGUF 加载（mmap 零拷贝）→ byte-level BPE 分词 → 前向（CPU/CUDA 双后端）
→ greedy 生成；后端可选：scalar / OpenMP / AVX2 / OpenBLAS(对照) / CUDA
```

## 2. 方法论资产（可复用的验收基建）

- **双实现交叉验证**：GGUF 解析（C++ vs Python）、dequant（自研 vs libggml，3.3 亿值逐位 EXACT）；
- **逐层对拍**：HF f32 golden dump，allclose(atol+rtol) 口径（驯服 massive activation 13201 的阈值问题）；
- **teacher-forcing 一致率**：解决"两条合法数值路线如何比正确性"（自研 Q4 49/50 ≥ llama.cpp 48/50）；
- **平局个案处置**：greedy 分叉时以 top-2 logit 差判定合法平局（p5，差 0.016，记录不究）；
- **每个优化都必须过同一份对拍**（OpenMP 行分区 bit 级不变是验收而非期望）。

## 3. 关键技术发现（面试弹药）

1. transformers 5.x `hidden_states` 末位是 final_norm 输出，裸末层不在元组里；
2. Qwen 的 massive activation 维（sink token 残差 13201）使绝对误差阈值失效；
3. transformers 分词器带 NFC normalizer，GGUF/llama.cpp 链路不带——部署一致性陷阱；
4. llama.cpp 的 Q4 kernel 是 Q4_K×Q8_K（激活也量化）——"同一 Q4 模型"在不同引擎下
   数值不同，对拍前必须先定义数值口径；
5. decode gemv 生产上不走 cuBLAS（llama.cpp/TRT-LLM 同）——边界决策的意外修正；
6. "量化不配融合 kernel 等于白量化"（Q4 标量 dequant 比 F16 还慢 0.89×）。
