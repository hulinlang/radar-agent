## 1. 交付总览

**一个零 LLM 库依赖的 C++ 推理引擎**（`radar-agent/cpp/`，~3000 行，WSL2 gcc/nvcc）：

```
GGUF 加载（mmap 零拷贝）→ byte-level BPE 分词 → 前向（CPU/CUDA 双后端）
→ greedy / 采样生成；后端可选：scalar / OpenMP / AVX2 / OpenBLAS(对照) / CUDA
→ 批量 prefill + continuous batching → 零依赖 HTTP 服务（radar-serve）
```

## 2. 方法论资产（可复用的验收基建）

- **双实现交叉验证**：GGUF 解析（C++ vs Python）、dequant（自研 vs libggml，3.3 亿值逐位 EXACT）；
- **逐层对拍**：HF f32 golden dump，allclose(atol+rtol) 口径（驯服 massive activation 13201 的阈值问题）；
- **teacher-forcing 一致率**：解决"两条合法数值路线如何比正确性"（自研 Q4 49/50 ≥ llama.cpp 48/50）；
- **平局个案处置**：greedy 分叉时以 top-2 logit 差判定合法平局（p5，差 0.016，记录不究）；
- **逐 id / 逐字节对拍全覆盖**：B4 端到端 440/440、B8 逐 id 8/8 + 连续批 16/16、B9 LCP 逐字节相同
  ——**每一次优化都必须过同一份对拍**（OpenMP 行分区 bit 级不变是验收而非期望）；
- **profile 驱动优化**：每一版 kernel 都先拿 CUDA events 分段计时（`RADAR_GPU_PROFILE=1`）再动刀，
  而不是"改完看看快没快"（B6b/B7 的迭代史见 `docs/26` §B6b 差距分析、`docs/28` §6.3）；
- **GPU 重任务串行纪律**：回归与评测并发会 GPU 争抢 → 评测 1 小时超时"假死"（不是引擎 bug，`docs/30` §6.3）。

## 3. 关键技术发现（面试弹药）

1. transformers 5.x `hidden_states` 末位是 final_norm 输出，裸末层不在元组里；
2. Qwen 的 massive activation 维（sink token 残差 13201）使绝对误差阈值失效；
3. transformers 分词器带 NFC normalizer，GGUF/llama.cpp 链路不带——部署一致性陷阱；
4. llama.cpp 的 Q4 kernel 是 Q4_K×Q8_K（激活也量化）——"同一 Q4 模型"在不同引擎下
   数值不同，对拍前必须先定义数值口径；
5. decode gemv 生产上不走 cuBLAS（llama.cpp/TRT-LLM 同）——边界决策的意外修正；
6. "量化不配融合 kernel 等于白量化"（Q4 标量 dequant 比 F16 还慢 0.89×）；
7. **fp32 精确 dequant 的指令发射墙在 ~150 GB/s**（B7/B8 共同结论）——所以生产级 prefill
   用 int8 激活 + dp4a/MMQ **不是选择而是必然**（代价：数值口径变为 teacher-forcing）；
8. **Q4-on-GPU 的收益来自"融合"而非"量化"本身**：dequant 与 dot 融合后，显存 3.9→1.6 GB
   的同时反超 llama.cpp；对比第 6 条，同一量化等级在"融合 vs 不融合"下相差近两个数量级的行为；
9. **decode attention 的 `d_scores` 跨头竞争是 latent bug**：不崩、不报错，只让 argmax 恒 0
   （生成全 0）——"结果荒谬但无异常"这一类必须靠逐 id 对拍兜底（`docs/29` §7.5）；
10. **会话级前缀复用可以做到 bitwise 等价**：位置 p 的 KV 只由 token p 与前缀状态决定
    ⇒ token 级 LCP 复用与全量重跑逐字节相同（B9 实测 REUSED=37 全命中），
    这给了"前缀缓存正确性"一个可证明的判据，而不是"看起来一样"。
