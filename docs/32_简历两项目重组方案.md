### 项目二｜自研 C++/CUDA LLM 推理引擎（个人项目｜独立完成）2026.08 – 2026.10

```text
自研 C++/CUDA LLM 推理引擎 ｜ 个人项目｜独立完成               2026.08 – 2026.10
• 从零实现零第三方 LLM 库依赖的推理引擎（约 3000 行 C++/CUDA）：GGUF 权重加载 →
  手写 byte-level BPE 分词 → Transformer 前向 → 量化 kernel → 连续批处理 → HTTP 服务化，
  并把它接为前述问答系统的生成后端（22 题端到端与 llama.cpp 基线 Δ=+0.0000）。
• 先做 CUDA/Triton GEMM 算子打底：RTX 4060 Laptop 上 FP32 1024³ 达 5542 GFLOPS
  （Naive 的 7.2×、cuBLAS 的 96%），并用 Nsight Compute 归因；进一步算出该规模受
  wave quantization 限制（64 tile / 24 SM = 3 波，tile 级上限 88.9%），故不宜用它测峰值。
• 正确性用「同权重同协议」对拍逐 token 验证：F16 路线端到端 440/440 token 与 llama.cpp
  逐一相同；Q4 属另一条数值路线（激活是否量化不同），改用 teacher-forcing 一致率比较，
  自研 49/50 vs llama.cpp 48/50。
• 性能达同机 llama.cpp 水平：CUDA F16 62.5 tok/s（llama.cpp 60.8 的 103%）、
  自研 Q4_K/Q6_K 融合反量化 kernel + CUDA Graphs 后 119.4 tok/s（llama.cpp 116.9 的 102%），
  显存 3.9 GB → 1.6 GB；批量 prefill 567–616 tok/s（4.8–5.3×）、B=8 聚合 469.6 tok/s（3.96×），
  逐 id 8/8 与连续批 16/16 完全一致。
• 建立 Roofline 性能模型串联算子层与引擎层：decode 算术强度 ≈1.0 FLOP/Byte，
  而该 GPU 屋顶线转折点为 59.3 FLOP/Byte → 定量确认为带宽受限；模型预测 CUDA F16
  达带宽屋顶 99.3%、Q4 仅 61.5%（瓶颈在 fp32 精确反量化的指令发射而非带宽），
  并算出 prefill 由访存受限转为算力受限的临界 prompt 长度约 59 token。
```

## 4. 预判追问与答题骨架

**Q1｜为什么只训 0.82% 的参数，不掉点吗？**
骨架：8 GiB 显存决定上限（全参需 ≈15.8 GiB：权重 3.96 + 梯度 3.96 + Adam 7.92，`docs/09` §1）
→ LoRA 低秩增量 → 冻结边界是"视觉塔 + 词表 + 输出头"，只训语言侧投影。
加分：说明**冻结视觉塔不只是省显存**——主链路是纯文本，动视觉塔有遗忘风险且无收益；
并给实测：视觉读数能力确实**零提升**（数值命中 0.467→0.467），归因是视觉样本只有 83 条。

**Q2｜评测集怎么保证不是"自己出题自己满分"？**
骨架：① 评测集**先于**微调冻结并记 sha256 ② 三集合物理隔离 ③ 去污染三项（n-gram + 图像 sha256）
④ 判分口径 v3 全项目复用 ⑤ **评测集一变，历史结果全部作废**，基线与微调同题面重跑。
加分：主动说"keypoints 严格子串**不能**判自由生成"——基座与微调在该口径下得分完全相同（0.0383），
是判分器的问题不是模型的问题。

**Q3｜你这条负面结论（开检索后掉分）怎么解释？**
骨架：现象（0.370→0.295）→ 归因（检索总能返回东西 → 模型"过度自信"不肯拒答，94.7%→78.9%）
→ 判断（这是小模型 RAG 的经典副作用，不是配置没调好；收益天花板在数据与模型侧）。
加分：说明"唯一确定性收益是引用可溯源（130 个编号零编造）"——**这是可机器验证的价值**。

**Q4｜440/440 token 一致是什么意思？**
骨架：同一份 F16 权重、同一 prompt、同一 greedy 解码，我的引擎与 llama.cpp 逐 token 输出
**完全相同的 id 序列**（5 个 prompt，共 440 个 token）。这是阶段 B 的总验收标准。
加分：说明参照系为什么不用 llama-server 的 HTTP——它的响应只回 token **字符串**不回 id，
间接重建 id 会引入新变量，所以改用 30 行 C++ 直接链接 libllama（`docs/24` §3）。

**Q5｜Q4 为什么不能也用逐 token 对拍？**
骨架：llama.cpp 的 Q4 kernel 是 Q4_K×**Q8_K**（激活也量化），我是 fp32 精确反量化——
**两条不同的数值路线**，逐 id 相同在数学上就不该成立。
→ 改用 teacher-forcing 一致率（同前缀喂两边看下一步是否同）：49/50 vs 48/50。
加分：这说明"对拍前必须先定义数值口径"，否则会把合法差异当成 bug 死磕。

**Q6｜119.4 vs 116.9 只快 2%，凭什么说做得好？**
骨架：**方向反了**——不是"我比 llama.cpp 快"，而是"在一个成熟引擎已经贴着物理极限的场景下，
我从零实现达到了同等水平"。更重要的证据是 Roofline：两者都只到带宽屋顶的 ~61%，
说明**瓶颈不在实现而在 fp32 精确反量化的指令发射**（`docs/28` §2.2 的 144 B/0.66 μs 预算账）。
加分：说出下一步的生产答案——int8 激活 + dp4a/MMQ，代价是数值口径要改成 teacher-forcing。

**Q7｜Roofline 模型是你编的公式还是真能用？**
骨架：**能用，而且做了外推验证**：模型对自研 CUDA F16 预测 63.0 tok/s，实测 62.5，**误差 0.8%**；
对 Q4 预测 194.1，实测 119.4（差的那部分正是模型明确排除的 dequant 指令开销）。
且全部参数在 `configs/perf_model.yaml` 一处定义，13 条断言守护（权重字节与磁盘文件对账等）。
加分：主动说模型的已知简化（不含 launch 开销、激活访存是一阶估计、时钟 2.1 GHz 是推算）。

**Q8｜手写 GEMM 只到峰值 43%，是不是不行？**
骨架：**先给三个数**（`docs/16` §4.2 要求的三问）：① 占峰值 43.0%
② **wave quantization**：1024³ 按 128 tile 是 64 个 tile，24 SM 装不下 → 3 波，
tile 级天花板 88.9%，**所以这个规模本来测不出真峰值**（要达到 88.9% 需换更大矩阵或更小 tile）
③ 不用 tensor core 是因为 FP32 路线不通，换 FP16/TF32 会改变数值口径。
累计这些，说明我知道"43% 这个数该怎么读"，而不是"我写了个慢 kernel"。
