# 技术栈详解（面试技术追问底稿）

> 用途：面试被追问"为什么这么选"时的技术依据。**每一条都带选它的理由和被它淘汰的方案。**
> 数字区分「实测」与「推算」——把推算说成实测是这里最容易犯的错。
> 更新：2026-09-22

---

## 0. 栈全景

| 层 | 选型 | 一句话理由 |
|---|---|---|
| 基座 | Qwen3-VL-2B-Instruct（2.128 B） | 8 GiB 卡能塞下的最大档多模态模型 |
| 微调 | HF transformers + PEFT LoRA | 需要梯度和灵活改前向，推理引擎做不了 |
| 推理/部署 | llama.cpp + GGUF Q4_K_M | Windows 原生、VL 双文件、可控量化 |
| 向量模型 | BAAI/bge-m3（1024 维） | 多语言、长上下文 8192、自带稀疏能力（本项目只用了 dense） |
| 字面召回 | BM25（自实现打分 + 中文 bigram） | 词袋与语义互补，且几乎零延迟 |
| 编排 | 自写 ReAct（不套 LangChain） | 要精确控制每一步的护栏与 trace |
| 服务 | FastAPI + 单页 HTML | 要展示"思考过程"，gradio 的 Chatbot 塞不下分层结构 |

**为什么自写 ReAct 而不用 LangChain**：本项目最值钱的是**中间过程**（调了什么、返回什么、怎么决定下一步、最后引用了哪段），需要逐步的耗时统计与护栏计数。框架的封装会把这些吞掉，而且我需要对自己说清"每一步为什么这么做"。

## 一、推理侧：引擎选型

### 1.1 先分清两个瓶颈，否则选型必错

| 阶段 | 干什么 | 瓶颈 | 关键指标 | 优化手段 |
|---|---|---|---|---|
| **Prefill** | 一次算完整个 prompt，生成 KV Cache | 计算密集 | **TTFT** | FlashAttention、prefix cache |
| **Decode** | 逐 token 生成，每 token 读一遍全部权重 | **带宽密集**（算术强度 ≈ 1） | **TPOT / ITL** | 算子融合、**量化**、KV 分页 |

→ **量化只优化 Decode 阶段要读的字节数，对 Prefill 几乎没帮助。**
这条后来被实测验证（见 1.4：TTFT 基本没动）。

### 1.2 三类引擎的定位（面试高频）

```
① 框架级：HF transformers        灵活性最好，代价是 Python 逐 token 循环、无算子融合
② 调度级：vLLM / SGLang          优化"并发下的显存利用率"，核心是 PagedAttention
③ 内核+量化级：llama.cpp / GGUF  优化"单请求的绝对速度"，C++ 内核 + 权重量化
```

> ⭐ **面试必答的一句话**：**"PagedAttention 不让任何单个请求变快，它让更多请求同时跑。"**
> 所以判断该不该用 vLLM 的标准是**并发度**，不是"它快不快"。

### 1.3 六条硬约束 → 排除过程（这是选型的真正输入）

| # | 约束 | 证据 | 结论 |
|---|---|---|---|
| C1 | GPU 只有 8188 MiB，权重已占 3.96 GiB | 实测 | 量化是刚需 |
| C2 | Windows 11，**WSL 被安全策略封禁**，无 Docker | 实测 | **vLLM / SGLang / TensorRT-LLM 全出局** |
| C3 | 多模态，视觉塔占 19.1% | 实测 | 引擎要支持 mmproj 双文件 |
| C4 | P8 要 GGUF 量化，P5 会产出 LoRA | 需求 | 要 HF → merge → GGUF 工具链 |
| C5 | 要训练 + 要 logits评测 | 需求 | **必须保留 HF** |
| C6 | 演示是单用户，并发 ≈ 1 | 需求 | 调度级优化收益≈0 |

```
C2 → 排除 vLLM / SGLang / TensorRT-LLM / LMDeploy   ← 决定性
C3 → 排除对 VL 支持弱的引擎（如 ONNX Runtime GenAI）
C5 → 必须保留 HF transformers                        ← 双引擎的必然性
C1 + C4 → llama.cpp 是唯一同时满足"可控量化 + 低显存 + Windows 原生 + VL"的
```

> **核心判断**：引擎选型不是选"最强"，是选**约束下最优**。
> 最容易失分的回答是"vLLM 最快所以选 vLLM"——它同时错了两件事：忽略可运行性约束，
> 且"最快"指吞吐，而单用户场景要的是延迟。

**最终分工**：推理/部署 = llama.cpp；训练/评测 = HF transformers；Ollama 只做可选演示壳
（它把 mmproj / 量化等级 / 显存卸载——恰恰是要学的细节——全藏起来了）。

### 1.4 实测结果（E1，3 次重复）

| 指标 | HF bf16 | llama.cpp Q4_K_M | 变化 |
|---|---|---|---|
| 吞吐 | 24.0 tok/s | **128.8 – 158.2** | **×5.2 – 6.6** |
| P99 ITL | 55.1 – 58.6 ms | **7.0 – 7.8 ms** | 改善 **7.5×** |
| TTFT | 0.045 – 0.106 s | 0.038 – 0.120 s | **基本不变** |
| 显存峰值 | 5680 – 5905 MiB | 4777 – 4791 MiB | −19% |
| 能效 | 0.50 tok/J | **1.82 tok/J** | **3.6×** |

**两条归因结论**：

1. **实测倍率（5.2–6.6×）超过了"纯带宽"能解释的上限（3.107×）**
   → 说明原本有相当一部分时间浪费在**Python 逐 token 循环与 kernel 派发**上，不只是搬数据慢。
2. **TTFT 几乎没动**，精确验证了"量化对 prefill 收益有限"这条理论预期。

> ⚠️ **测量纪律（面试可以主动提，很加分）**：实测发现**跨 session 吞吐漂移 17.3%**，
> 远大于组内波动（0.6–3.6%）。所以：
> **引擎间的倍率可以引用，绝对吞吐值不可跨 session 引用。**
> 要做 A/B 必须**同一 session 内交替跑**（A/B/A/B），不能上午跑 A 下午跑 B。

### 1.5 量化档位：为什么是 Q4_K_M + mmproj F16

**(a) VL 模型为什么要拆两个 GGUF 文件**
官方 GGUF 仓库明确把模型拆成 Language model（FP16/Q8_0/Q4_K_M）和 Vision encoder / mmproj（FP16/Q8_0）。四个理由：

1. **量化敏感度不同**：语言侧 1.72B 参数，权重均匀，压到 4bit 掉点可控；
   视觉塔只有 0.41B，**压它省不下多少显存，却可能让整条视觉链路掉点**。
2. **使用场景可分离**：纯文本链路（本项目主链路）**可以完全不加载 mmproj**，省 0.45–0.9 GB。
3. **精度可自由组合**：Q4_K_M 语言侧 + F16 视觉侧是最常见的"省显存不掉能力"组合。
4. **工程解耦**：换视觉塔不必重转整个语言模型。

**(b) Q4_K_M 这个名字在说什么**

```
Q4_K_M
 │ │ └── M = Medium：不同张量用不同精度（混合），关键张量抬档
 │ └──── K = k-quants：分块量化，super-block 内再分子块、分层 scale
 └────── 4 = 权重约 4 bit
```

- `Q4_0`：每 **32** 个权重一个 scale（单层缩放）
- `Q4_K`：super-block 256 个权重 → 切成 **8 个子块**，子块各有 scale，全局还有一个 scale/min
- 效果：**分层缩放显著降低离群值对整块量化的破坏**（这也是 `Q4_0` 逐渐被冷落的原因）
- 哪些张量要抬档：`attn_v`（value 投影）和 `ffn_down` 对量化更敏感，它们直接决定残差流的信息保真度

**(c) 体积权衡**

| 文件 | 体积 | 说明 |
|---|---|---|
| HF bf16 | **4.25 GB**（实测 3.96 GiB） | 基线 |
| Q8_0 | 1.83 GB | "fast, best quality" |
| **Q4_K_M** | **1.2 GB** | **"fast, recommended"（选它）** |
| mmproj-f16 | 0.819 GB | **选它，不量化** |
| mmproj-q8_0 | 0.445 GB | 省显存可选 |

**选 Q4_K_M 而不是 Q8_0**：显存是硬约束（C1），要在"能跑起来"和"掉点可控"之间取。
Q4_K_M 是官方标注 recommended 的最省档，且 k-quants 的分层缩放把掉点压住了。

> 📌 推算 vs 实测：**从体积算带宽上限（Q4_K_M 约 3.5×，213 tok/s）是推算，不是实测**；
> 实测拿到 5.2–6.6×（更高，因为还省掉了 Python 开销）。**面试时别说混了。**

## 二、RAG 构建之一：切分策略

### 2.1 为什么不用"字符滑窗"

字符滑窗是最常见做法，但在雷达教材上**直接失败**：

> 实测（157 条 leaf section，800 字符窗口 / 150 重叠）→ 775 个 chunk 里
> **248 个（32.0%）出现奇数个 `$`**，即公式的 LaTeX 定界符被切断。

根因：滑窗是**字符级**的，感知不到"这 20 个字符是一个不可分割的公式"。
切断的后果不是报错，是**这段公式在检索里永远查不到、模型看到半截式子**——典型的静默错误。

### 2.2 改用块级版面感知切分

数据源用的是 MinerU 的**结构化解析结果**（`book_pages_v2.jsonl`，每页是块列表，块有类型），
而不是纯文本。这样公式天然就是一个块，按块切就**从根本上不可能切碎**。

**三个"不可拆"等级**：

| 等级 | 内容 | 规则 |
|---|---|---|
| 原子块 | image / chart / table / equation_interline | 永不被切开 |
| 原子 item | paragraph 里的 equation_inline | 永不被切开（渲染时保证完整） |
| 硬边界 | 标题层级 ≤ 3 | chunk 绝不跨越（保持语义归属） |

**其他细节**：
- 标题层级必须**从标题文本推**，不能用解析器给的 `level` 字段（实测：level=1 只有 1 个书名，524 个全是 2，这个字段不可用）
- 无编号标题（小结/思考题/参考文献/前言）一律当 3 级边界，否则会串进上一小节
- 图/公式 chunk 会带**周围正文**做上下文（图 ±150 字符，公式向前 200 字符）
- 短 chunk（< 120 字符）并入同节前一个，避免孤儿块
- 弃用的噪音块：页眉/页脚/页码/目录

### 2.3 教材与论文用两套策略（D4 决策）

| | 教材 | 英文论文 |
|---|---|---|
| 单位 | 按**节**聚合（硬边界 ≤3 级标题） | 按 **section** 整段保留 |
| 目标长度 | 800 字符 | 1500 字符 |
| 硬上限 | 3000 | 6000（**绝大多数 section 不二次切**） |
| 理由 | 教材要切细便于精确定位 | 论文靠完整论证链，上下文完整 ≫ 长度均匀 |

### 2.4 产出

| 来源 | chunk 数 | 自检 |
|---|---|---|
| 教材 | 2054（正文 917 / 图 518 / 公式 589 / 表 30 / 毫米波 200） | DoD **18/18 全绿**，连跑两次哈希一致 |
| 论文 | 1639（正文 1169 / 图 396 / 表 53 / 摘要 22） | DoD **10/10 全绿**，35 篇零失败 |
| 入索引 | **3659**（排除 34 条 Front Matter） | DoD **15/15 全绿** |

## 三、RAG 构建之二：检索策略

### 3.1 三路召回 + 融合

```
查询 → ① BM25（字面） ─┐
       ② bge-m3 dense（语义） ─┼→ RRF 融合(k=60) → top_k
       ③ 图号/表号精确索引（hit 则 pin 到头部）─┘
```

**为什么两路都要**：实测单路最好 70.1%，融合后 **75.3%**（+5.2 pp）。
字面匹配能抓住"STAP 全称"这类精确符号，语义能抓住"dispersion 和弥散"。

**融合用 RRF（倒数排名融合）而不是加权打分**：
不同打分函数的**量纲不可比**（BM25 分数可以到几十，余弦只有 0~1）。
RRF 只用名次：`score = Σ 1/(k + rank)`，天然免疫量纲问题。
k=60 是 Cormack 2009 的量级。

> ⚠️ 一个容易做错的细节：**融合时两路各取的候选数（top_n）必须相同。**
> 若一边取 20、一边取 50，等于给候选少的一路偷偷加权（"没进榜"被隐式当成无穷大排名）。

### 3.2 中文分词为什么用字符 bigram 而不是 jieba

- 领域术语（"空时自适应"、"原子范数"）**不在通用词典里**，jieba 会切碎
- 字符 bigram（`空时`/`时自`/`自适`/`适应`）**不需要词典**，对术语天然鲁棒
- jieba 分支保留作对照（`mode="jieba"`），没装也不影响（自动退回 bigram）
- **不做小写化**：bge-m3 是多语言模型，大小写对它有意义（缩写 STAP vs stap）

### 3.3 图号/表号为什么需要单独一路

BM25 是词袋模型，**分不清 `Fig. 1` 和 `first`**（实测把这个搞反过一次）。
所以给图号/表号建了精确索引，命中后 pin 到结果头部（同一图号跨 35 篇会命中多次，按 BM25 分排序取前 3 条）。

### 3.4 三个"做了之后发现没用/有害"的开关

| 措施 | 结果 | 处置 |
|---|---|---|
| Front Matter（作者/单位/邮箱/DOI）去噪 | 有效：查"原子范数最小化"曾把元数据排到第 2 | 默认开 |
| 图号/表号索引 | 对图号直查有效，对全集 **0 影响** | 保留（特定场景有用） |
| **公式概念索引** | **负收益**：MRR 0.590 → 0.573 | **默认关，代码保留** |

公式概念索引负收益的两个根因：概念表术语太宽（"多普勒频率"能挂到 36 个公式块），
且 pin 是**强制置顶**，会把真答案挤下去。→ 想法没错，**是数据精度跟不上**。

### 3.5 空检索判定（检索层防幻觉的第一道闸）

**必须判空**：全库检索**永远能返回 top_k 条**（BM25 总能凑出字面匹配，查"南极鳕鱼血液"照样返回 3 条）。
不判空，模型会以为有依据，幻觉不可避免。

判据是 **dense top1 的余弦相似度**（不是 RRF 分数 —— RRF 量纲只有 0~0.033）。
实测标定 θ = 0.55：

| 组 | 相似度范围 |
|---|---|
| 完全无关（15 条） | max **0.545** |
| 相关·跨语言（33 条） | min **0.582** |
| 相关·教材域（60 条） | min 0.600 |

→ 无关 100% 判空、相关 0% 误判，两组完全分离（间隔 +0.037）。

> ⚠️ **能力边界**：「沾雷达术语但语料里没答案」的问题（如"雷达怎么用于农业无人机播种"）
> 相似度能到 0.5965，比真问题还高，**阈值拦不住**。
> 这类只能靠生成侧读完上下文后拒答——**在检索层假装没检索到属于伪造证据，不做。**

### 3.6 检索评测结果

| 指标 | 数值 |
|---|---|
| Recall@5 | **75.3%** |
| Recall@10 | 83.3% |
| MRR@10 | 0.590 |

**三组消融**（每组回答一个具体决策）：

| 改了什么 | 收益 |
|---|---|
| 单路 → 双路融合 | R@5 **+5.2 pp** |
| 加 1639 条英文文献 | 教材题 **0 影响**（MRR 差 0.001）→ 证明不会挤占 |
| 图号/表号专用索引 | 对全集 **0 影响** |

## 四、Agent：ReAct 的构建

### 4.1 为什么不是固定流程（DAG）

固定流程（先检索 → 再判断要不要算 → 最后生成）的前提是**能提前知道需要几步**。
实际不是：有的题一行常识就够（不该浪费 20 秒检索），有的题要查两次（第一次查空了要换词）。
→ 让模型**自己决定**：调什么工具、调几次、什么时候收手。

代价是要自己做护栏（见 4.3）。**评测证据**：tool5 在常识题上误调 0%，在需要检索的题上调用率 97% —— 它确实学会了区分。

### 4.2 主循环（伪代码）

```
messages = [system + tools定义, user问题]
for step in range(max_steps):
    prompt = tok.apply_chat_template(messages, tools=tools_spec)
    seg   = model.generate(prompt, ...)
    pr    = parse(seg)                      # 四门解析
    if not pr.calls:  return seg            # 没调工具 = 最终答案
    observations = [execute(c) for c in pr.calls]
    messages += [{"role":"assistant","content":seg},
                 {"role":"tool","name":...,"content":observations}]   # ← role 必须是 tool
```

### 4.3 六重护栏（**每条都配计数器**）

> 原则：护栏没有计数器 = 不知道它有没有被触发 = 等于没有护栏。

| 护栏 | 触发条件 | 动作 | 计数器 |
|---|---|---|---|
| 最大步数 | 到最后一步 | 追加"必须给最终答案" + 解码层屏蔽 `<tool_call>` | `max_steps_hit` |
| 重复调用 | 同一（工具名，规范化参数）已调过 | 不执行，回灌"你调过了" | `dup_call` |
| 死循环 | 连续 2 步 thought 的 4-gram Jaccard > 0.90 | 强制收尾 | `loop_detected` |
| token 预算 | 累计 > 6000 | 终止 | `token_budget_hit` |
| 超时 | 单步 > 10 s（web 15 s） | observation = `<timeout>` | `step_timeout` |
| 空检索 | 检索判空 | 允许换词重试 1 次 | `empty_retrieval` |

### 4.4 两个实测出来的硬约束（面试很能讲）

1. **观察回灌必须用 `role="tool"`** —— 用 `role="function"` 时内容被**静默丢弃**：
   不报错，但模型看不到工具返回 → 循环失效。这类"跑得通但结果是错的"错误最难排查。
2. **末步屏蔽 `<tool_call>` 必须实测验证** —— transformers 的 `bad_words_ids` 不保证生效。
   实测：关掉时 5 条里 4 条会在最后一步继续发调用块；打开后 **0/5**。
   （`<tool_call>` 恰好是**单 token 151657**，所以屏蔽它可行。）

### 4.5 为什么把 few-shot 关掉了

两条实测理由：
1. 微调后不需要了 —— 不给任何示例时格式合规率已达 **98.3%**
2. **给示例有副作用** —— 它让模型对**所有题都调工具**（含常识题），即"万物皆工具"退化
3. 更关键：**评测时 B 组（有工具）必须与其他组提示词条件一致**，
   否则"检索的净收益"里会混进"多给了两个示例"的贡献，结论不可信

### 4.6 工具调用解析器：为什么不用正则

正则（哪怕非贪婪 `.*?`）在这三种输入上必错，且**不报错**：

1. **arguments 里嵌字面量标签**：`{"query":"<tool_call> 是什么标签"}` → 层数错乱
2. **多调用相邻**：`</tool_call>\n<tool_call>` → 非贪婪吞掉中间内容
3. **未闭合**：生成被截断在调用中间 → 静默判成"没调用"，表现为"模型从不调工具"

→ 改用**字符级状态机**（第 0 门），并且 **只在调用块内部**维护 JSON 字符串状态：
块外见 `<tool_call>` 必是标签（不受正文零散引号影响）；块内在字符串内则忽略一切像标签的东西。

**四门**：

| 门 | 做什么 | 失败码 |
|---|---|---|
| 0 | 状态机扫描，depth≠0 即未闭合 | `unclosed` |
| 1 | `json.loads` **严格**（非 json5、不接受单引号） | `bad_json` |
| 2 | name 白名单**精确**匹配（大小写敏感、无别名） | `unknown_tool` |
| 3 | arguments 走 JSON Schema（含 `pattern` 校验） | `schema_violation` |

> ⚠️ **修补只对"未闭合"生效**（补结束标签），**绝不对** bad_json / 参数错做修复 ——
> 那本质是替模型编参数，属于"不伪造证据"红线。

## 五、工具层的构建

### 5.1 三个工具

| 工具 | 入参 | 默认 | 说明 |
|---|---|---|---|
| `corpus_search` | `query`、`top_k`、`sources` | 开 | 检索本地语料，返回带 chunk_id 的片段 |
| `calc` | `expr`、`unit` | 开 | 安全沙箱求值（空 builtins + 只放 math） |
| `web_search` | `query` | **关** | 默认离线快照模式 |

**web_search 默认关**：联网会引入幻觉，也可能撞"语料外发"红线。
而且处理原则是——**模型看不见就不会调，比"让它调了再报错"更省 token 也更可控。**

### 5.2 白名单单源设计

三个地方要用工具名：解析器白名单、prompt 里的工具定义、训练数据生成。
如果各写一份，任何一处漏改都会让"模型调了不存在的工具"这条错误**静默通过**。
→ 统一由 `src/tools/registry.py` 导出，`to_openai_tools()` 直接喂给 `apply_chat_template`，
保证**模型看到的工具定义**与**实际能执行的工具**物理同源。

### 5.3 工具返回结构：为什么要有 `ok` 和 trace

```
ToolResult(ok=..., payload=..., error=..., elapsed_ms=..., diag=...)
```

- 「没检索到」和「检索出错」是**两种完全不同的信号**，模型的正确下一步也不同
  （前者该换查询词，后者该换工具）→ 必须分开表示，不能都 returning 空字符串
- **截断必须显式标记**（`truncated: true`）：静默截断会让模型以为"资料就这么多"，
  进而编造后面没有的内容 —— 这是本项目要防的头号幻觉来源

### 5.4 calc：为什么改成"传表达式"而不是"传公式名"

**旧接口**：`{formula: "range_resolution", inputs: {B: 1e8}}`
**新接口**：`{expr: "3e8/(2*1e8)", unit: "m"}`

改的动因是实测数据：旧接口下 30 道计算题里 **13 条（43%）栽在猜名字上**
（漏传参数、参数名猜错 `bandwidth`→应为 `B`、臆造不存在的公式名、选错公式）。

改完的结果：

| | 旧接口 | 新接口 |
|---|---|---|
| 栽在"名字"上 | **13** | **0** |
| 计算题得分 | 0.400 | **0.633** |
| 新主因 | — | 式子写错/写不全 14 条（**模型能力边界**） |

> ⭐ **根因洞察**：探针数据证明模型**会列式且列得准**（29 条里 20 条式子正确，91%），
> 且在列对式子的 20 条里算术只错 2 条。
> → **不是模型算不对，是接口这层抽象把它搞乱了。**
> 失败模式从"接口错配"（我们能修）转成了"模型能力"（边界），这是健康的转变。

**安全沙箱**：`expr` 是自由字符串，必须——
① `__builtins__` 清空，只注入 math 的有限函数；
② 字符白名单；
③ JSON Schema 的 `pattern` 在**解析阶段**就挡住 `import os`
（字符白名单是字符级的，`import` 的字母全在白名单里，不靠 pattern 挡不住）。

## 六、微调侧（简述）

| 项 | 选择 | 理由 |
|---|---|---|
| 方法 | LoRA，**只训语言侧 28 层的 7 类投影** | 17.43 M 可训练参数（**0.82%**），8 GiB 卡 40 分钟一轮 |
| 冻结 | 视觉塔 + lm_head + embed_tokens（316 张量） | 主链路纯文本，动视觉塔浪费且有遗忘风险 |
| 取舍验证 | 给对齐层也加 LoRA（B1） | **实测无增益，出局** |
| 显存 | 每步 `empty_cache` | 8 GiB 卡的峰值来自 **reserved** 而非 allocated，代价是慢 ~70% |

> ⚠️ 显存坑：Windows 下 `torch.cuda` 的 reserved 会超过物理显存（8.25–8.54 > 8.0，溢出到共享内存），
> 而真实 allocated 只有 4.2–5.7。**护栏必须用 allocated 判断**，用 reserved 会把正常训练误杀。

## 七、技术追问速查

| 追问 | 一句话回答 |
|---|---|
| 为什么不用 vLLM？ | WSL 被封、无 Docker，Windows 原生路径全无；且单用户场景 PagedAttention 零收益 |
| PagedAttention 解决什么？ | 让**更多请求同时跑**，不让单请求变快 |
| 为什么 Q4_K_M 不是 Q8_0？ | 显存硬约束 + 官方 recommended 档；k-quants 分层缩放把掉点压住了 |
| mmproj 为什么不量化？ | 视觉塔只有 0.41B，压它省不下多少却可能让视觉链路掉点 |
| 为什么量化对 TTFT 没帮助？ | 量化只减 Decode 要读的字节数，Prefill 瓶颈是**计算** → 实测 TTFT 几乎不动 |
| 为什么 fused 双路召回？ | 量纲不可比 → 用 RRF 只比名次；单路 70.1% → 融合 75.3% |
| 为什么不用滑窗切分？ | 实测 32% 的公式被 `$` 切断，且**不报错** |
| 中文为什么不用 jieba？ | 领域术语不在通用词典，字符 bigram 不需要词典 |
| 吞吐数字能直接用吗？ | **绝对吞吐不可跨 session 引用**（漂移 17.3% ≫ 组内波动 3.6%），只能引用同 session 内的倍率 |
| 解析器为什么不用正则？ | 三种输入上必错且不报错（嵌套标签/相邻调用/未闭合） |
| 工具观察为什么用 role=tool？ | `function` 会被静默丢弃，模型看不到 → 循环失效且不报错 |
| 幻觉怎么防？ | 三道闸：空检索阈值 0.55 → strip 引用必须带真实 chunk_id → 微调教它拒答 |
