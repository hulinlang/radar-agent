## 0. 组织原则：三级口径阶梯（以及为什么顺序不可颠倒）

| 层级 | 判据 | 能证明什么 | 谁用 | 可逆性 |
|---|---|---|---|---|
| **Tier A** | 逐 id 相同（bit-exact） | 改动**没有**改变任何输出 | 顺序保持型优化 | 一旦离开，**永久不可回** |
| **Tier B** | teacher-forcing 一致率（≥49/50）+ logit 位移分析 | 数值被扰动，生成轨迹基本不变 | 改变浮点累加顺序的优化 | 可退回 A |
| **Tier C** | 质量门（F1 / 拒答率 / 逐题 diff）+ 统计等价 | 分布变了，但**质量不降** | 改变数值表示的优化 | **不可退回 A/B** |

### 0.1 核心论断：Tier A 是**不可再生资源**

Tier A 的证明力来自"输出逐位相同"。而 Tier C 的每一项（KV 量化、投机解码、FP8、AWQ）
都会让输出**在某些 token 上真的不一样**——哪怕这些差异是等价的、更好的。

一旦某个组件进入 Tier C：

- 它的"逐 id 相同"证据**永远不可能再建立**（差异已经存在，参照物没了）；
- 依赖它的下游（采样、ReAct 工具调用链、评测口径）也一起被拖出 Tier A；
- 回滚只能回到"旧的实现"，不能回到"曾经被证明位精确"这个结论——因为证明本身没被保存。

### 0.2 由此推出的顺序

```
Phase 0  收尾 + 冻结 exact 基线档案（把 Tier A 的成果固化成可 diff 的物证）
   ↓
Phase 1  引擎补全（Tier A / B）—— 把不改变分布的优化全部做完
   ↓
Phase 2  口径切换闸门（一次性、不可逆）—— 先建能力，再改数值
   ↓
Phase 3  改变分布的 infra 优化（Tier C）—— 按收益/风险排序，逐项独立验收
   ↓
Phase 4  视觉编码（文本侧全部完成后，用户决定 D3）
```

⚠️ **最容易犯的错误是跳过 Phase 2 直接做 Phase 3**：改完 KV 量化、觉得质量"好像还行"，
但手上没有冻结基线和 diff 报告，无法回答"到底变了几道题、变成什么样"。那就等于没测。

## 2. Phase 1 · 引擎补全（Tier A / B，不改变分布）

| 编号 | 项 | 口径 | 前置 | 验收 | 主要风险 |
|---|---|---|---|---|---|
| **B12** | int8 MMA prefill | **A（预期）** | chunk 16→64/128；权重现场解包 | 三层对拍（D1 位精确 / D2 ≥49/50 / D3 ≥1000 tok/s） | 带宽喂不饱；`MAX_MC` 与 chunk 耦合 |
| **B13** | prefill/decode 混合批 | **A（预期）** | `MAX_MC` 扩容或限制混合比 | 与串行路径逐 id 相同 + TTFT/P99 改善 | 调度复杂度；图捕获形状变化 |
| **B14** | attention 重写（FA 式） | **B（已接受降级，D2）** | 无 | teacher-forcing ≥49/50 + 位移分析 | 浮点累加顺序改变 |

> B15（视觉塔）**移出 Phase 1** → 见 §6（用户决定 D3：文本侧全部完成之后再做）。

### 2.1 B12 为什么能保持 Tier A（值得先做的核心理由）

MMA 的累加是 **int32 精确整数**，与 B11 的 dp4a 逐位相同；只要 fp32 尾声
（`d4*sumf_d - dmin*sumf_m`，`__fmul_rn`/`__fadd_rn`、sub-block 升序）不变，
结果**逐位相同**。B11 已钉死的 Q8_1 语义、NumPy 参考、`cpp/tests/int8_ref/` 的 24 个
golden payload **全部直接复用**，数值风险接近零。

实测通道宽度（`dsh_scratch/mma_probe.cu`，同会话单波次测量）：

| 管道 | MAC/SM/clk | vs dp4a |
|---|---|---|
| FP32 FFMA | 113.8 | 0.44× |
| INT8 dp4a | **256.0**（= 64×4，打满 Ada INT32 通道） | 1.00× |
| INT8 IMMA | **1023.9**（≈1024 = 8×FP32） | **4.00×** |

`dp4a = 256.0` 独立复现了 `docs/34` §7.1 的 **2.00× 天花板**；MMA 是 dp4a 的 4×。

### 2.2 B13 的硬约束（最容易低估的一项）

`MAX_MC = 16` **同时**是：KV 块大小（`BLOCK`）、prefill chunk 宽度、dp4a tile 宽度、
int8 激活的 `ncol`、以及 `max_batch` 上限。混合批要求
`decode 行数 + prefill 行数 ≤ MAX_MC`，于是只有两条路：

- **扩容 `MAX_MC`**：牵动 B11 的 tile 形状、激活缓冲显存、KV 块布局 —— 改动面大；
- **限制混合比**（如 decode 8 + prefill 8）：改动小，但批吞吐上限被压。

⚠️ 混合批改变的是**调度**不是算术（`gemv_mc` 各列独立、与单列 bitwise 相同，B8 已验证），
所以它**应该**能保持 Tier A —— 但必须实测确认，不能假设。

### 2.3 B14：决定接受 Tier B 降级（D2）

当前 attention 会物化完整分数矩阵（`d_scores` 尺寸 = `kv_cap × n_head × max_batch`），
FA 的核心恰恰是**永不物化**它。online-softmax 改变浮点累加顺序 ⇒ Tier A 失效。

**决定**：直接做 FA 式重写，验收走 Tier B（teacher-forcing ≥49/50 + logit 位移分析）。
依据：attention 在 int8 激活后已占 prefill ~42%，是除 GEMM 外最大的单点；
且 Tier B 的判据在 B11 D2 已经跑熟，方法成本低。

| 指标 | 门限 | 性质 |
|---|---|---|
| 200 题 v3 F1 | ≥ 基线 − **δ=0.005**（暂定） | **硬门** |

> 若 σ > δ，说明评测集分辨力不足，必须先扩样本或换指标——**否则这道门是假的**。

## 4. Phase 3 · 改变分布的 infra 优化（Tier C）

| 顺序 | 项 | 收益 | 风险 | 前置 |
|---|---|---|---|---|
| 1 | **KV F32→F16** | 显存 −50% ⇒ `max_batch` 上限提升 | 最低（只降精度） | 无 |
| 2 | **投机解码**（草稿模型 / n-gram prompt lookup） | decode 1.5–2.5× | 中（需先做接受率分析） | 采样路径已有 |
| 3 | **FP8 KV / FP8 权重** | 显存 + 带宽 | 中高 | sm_89 的 FP8 MMA（与 B12 同源） |
| 4 | **AWQ / GPTQ / SmoothQuant** | 低比特下保质量 | 高（需离线校准管线 + 校准集） | 校准集 |
| 5 | **beam search / n>1 采样** | 质量上限 | 与硬口径天然冲突 | 分页 KV 的 copy-on-write |

**排序依据**：收益确定性 ÷ 改动面。每项**独立立项、独立验收、独立回滚、独立提交**，
绝不合并——否则质量变化无法归因。

## 5. 横切：A/C 双引擎的分支策略（用户决定 D3）

### 5.1 现状盘点（已核实）

| 项 | 事实 |
|---|---|
| 仓库 | `radar-agent` 单仓库，已有 `main` 与 `master` 两个分支 |
| `main` | = `origin/main` = `origin/master` = `6e3b19f`（对外发布基线） |
| `master` | = `6e3b19f` + **33 个未推送提交**（本地领先，远端没有） |
| A 路线足迹 | **8 个文件**：`scripts/p9_wsl_vllm_{install,run,serve,fix,fix2,fix3,fix4}.py` + `docs/18_A路线WSL2加vLLM实测.md` |
| C 路线足迹 | `cpp/**`（74 文件 / +9684 行）+ `src/engines/react_radarinfer.py` + `docs/20`–`docs/35` |
| 共享层 | `src/agent/react.py`、`src/serve/app.py`、`src/engines/react_llamacpp.py`、`configs/`（5）、`scripts/`（42/49）、`reports/`（8）、`docs/` 大部分 |

⭐ **关键发现：A 路线的自有代码只有 8 个文件。** 它的"引擎"就是 vLLM 本身，
我们的代码只是**接线 + 实测记录**。所以分分支的成本极低，真正的风险全在共享层。

### 5.2 目标拓扑（trunk + 薄路由分支）

```
main                  ← 共享主线（对外发布）：RAG / Agent / tools / eval / configs
├── route/vllm        ← main + 8 个 A 路线文件
└── route/radarinfer  ← main + cpp/** + react_radarinfer.py + docs/20–35
```

**迁移四步（不重写任何历史）**：

1. 先在 `master` 上完成 §1.1 清账并提交；
2. `git branch route/radarinfer master` —— C 路线就地冻结，33 个提交原样保留；
3. `git checkout -b route/vllm main` 然后
   `git checkout route/radarinfer -- scripts/p9_wsl_vllm_*.py docs/18_*.md`
   —— 只取那 8 个文件。它们是独立脚本 + 独立文档，**不依赖共享层改动，冲突面为零**；
4. 共享层的后续改动只在 `main` 上做；两条 route 分支定期 `git merge main`。

### 5.3 不变量（fence）—— 让上面这套不腐烂的唯一条件

> **route 分支只允许修改自己的路由专属路径；共享路径只读。**

满足这条不变量时，`merge main → route` **永远不会冲突**（因为 route 分支从没碰过共享文件），
共享层的一次修改只需"merge 两次"就同步到两条路线，而不是"手工改两遍"。

**真正的风险是有人违反 fence**：在 `route/radarinfer` 上顺手改了 `src/agent/react.py`，
从此每次同步都开始冲突，分支策略迅速退化成手工维护两份代码。

**对策**：加 `scripts/check_branch_fence.sh`——检测当前分支相对 `main` 是否改动了共享路径，
违规即非零退出。便宜、可枚举、能进 CI，符合项目"一键脚本"的既有风格。

### 5.4 必须讲清的代价与替代方案

**代价**：共享层改动要落两次（是 `git merge` 两次，不是手工改两遍），
且多了一套必须靠纪律（+ 脚本）维持的不变量。

**更便宜的替代方案**：仓库**已经**有引擎抽象层——`src/engines/base.py` 定义统一的
`EngineInfo`（含 `openai_api` 标志位），现有适配器 `hf_engine` / `llamacpp_engine` / `ollama_engine`
可插拔。vLLM 提供 OpenAI 兼容端点，因此"路线切换"可以是一个 **~50 行的 `vllm_engine.py` 适配器
+ 配置项**，单分支内用配置切换，零分支纪律成本。

**取舍**：分支方案的价值在**展示与可独立审阅**（能单独浏览 `route/radarinfer` 只看到引擎工作），
适合作品集场景；适配器方案的价值在**零维护成本**，适合长期演进。
两者不互斥——**推荐做法是：分支用于展示与冻结里程碑，适配器保留在 `main` 上用于日常运行。**

## 6. Phase 4 · 视觉编码（文本侧全部完成之后，用户决定 D3）

**触发条件**：Phase 1–3 全部完成，且文本侧的 Tier A/B/C 判据全部冻结归档。

| 子项 | 内容 | 风险 |
|---|---|---|

| **mrope** | Qwen3-VL 的 3D 位置编码 | ⚠️ 文本也走 mrope（退化情形）→ **必须验证文本分布不变** |
| image token 展开 | 图像占位符 → 实际视觉 token 数 | 影响 KV 长度与 `max_batch` |
| 对拍 oracle | HF `Qwen3-VL` 的图像输入路径 | 需要新建（现有 oracle 只覆盖文本） |

⚠️ **不要假设"加了视觉、文本不受影响"**：mrope 的引入会改动 RoPE 的施加方式，
即使文本位置上退化成一维，也必须用 §1.2 的 exact 档案**实测确认**文本侧逐 id 不变。
若不成立，则文本侧也要一起进入 Tier B/C，本路线图的闸门顺序需要重排。

## 10. 分支迁移前必须先解决的一个历史问题

### 10.1 问题的成因

`master` 的 **33 个提交里，共享层与 C 路线是混在一起的**（同一个提交同时改了
`cpp/` 和 `src/agent/react.py`）。而 `main`（发布基线 `6e3b19f`）既没有 `cpp/`，
也没有 A 路线的 8 个文件。

于是"trunk + 薄路由分支"要落地，必须先决定**这 33 个提交怎么处理**。

### 10.2 三个候选方案

**方案 1 · 压缩共享层，保留 `master` 作完整历史（推荐）**

1. 提交清账（已完成）；
2. 在 `main` 上做**一个**"吸收共享层"的提交：`git checkout master -- <共享层路径>`；
3. `git checkout -b route/radarinfer main`，再把 C 专属路径从 `master` 取回，提交一次；
4. `git checkout -b route/vllm main`，取 A 路线 8 个文件，提交一次；
5. `master` **原地保留**为"完整细粒度历史"分支，不再开发。

- 收益：拓扑干净，fence 可自动检查，两条 route 分支与 `main` 共享历史 ⇒ 后续 merge 干净
- 代价：`master` 的 33 个提交不再位于任何主干上（作为历史档案保留）
- ⭐ **无损性可验证**：迁移后 `git diff route/radarinfer master` **必须为空**
  （内容完全一致）；`git diff route/vllm main` **必须只列出那 8 个文件**。
  两条 diff 就是这次手术的验收判据。

**方案 2 · 不压缩，`main` 直接推进到 `master`**

- `main` fast-forward 到 `master`（于是 `main` 里也有 `cpp/`），`route/vllm` 从 `main` 拉出后
  **删除** C 专属文件。
- ❌ **不推荐**：`route/vllm` 上会有"删除 `cpp/`"的提交，之后 `merge main` 会把它们加回来
  ⇒ 永久冲突，fence 也无法表达。

**方案 3 · 只建 `route/vllm`，暂不动 `main`**

- 立即建 `route/vllm`（= `main` + 8 文件），`master` 改名为 `route/radarinfer`。
- 收益：改动最小、立刻可用
- 代价：`main` 仍不是"共享主线"（落后 33 个提交的共享层改动），fence 的基线要手工维护，
  §5.2 的拓扑名存实亡。
