## 0. 一句话结论

**你的项目在「微调」和「评测」上的深度超过校招平均线，但在「高并发推理」和「工程化部署」上是空白，并且有一条链路其实是断的——「微调完的 LoRA 没有走到 GGUF 部署」。**

三条排序结论：

1. **最急的洞**：`LoRA → merge → GGUF → llama-server` 这条链**没跑通过**（§3.2 已核实）。简历上写"端到端"，面试官一句"那你微调完的权重怎么部署的"就问穿了。补课成本约半天（§5 S1）。
2. **最值的补课**：**RLVR / rejection sampling**（JD 高频词：后训练、对齐、RLHF/DPO/GRPO），而你恰好是**唯一有低成本条件的那类人**——判分器现成、权重只占 4.26 GiB。前置验证只要几分钟（§5 S2）。
3. **最该放弃的**：CUDA / Triton 算子开发。它在 JD 里高频，但属于"C++ 系统岗"的硬门槛，短期补不出来。**策略上应该避开纯内核岗，主投「大模型应用 / 算法 / 部署工程师」**（与 `docs/README` §三 已拍板的 D1 一致）。

### 黑话 → 大白话对照（先认字，再看表）

| 黑话 | 大白话 |
|---|---|
| Prefill / Decode | 读题 / 写答案。前者一次算完，后者一个字一个字往外蹦 |
| TTFT / TPOT / ITL | 等多久出第一个字 / 之后每个字间隔多久 |
| tok/s | 每秒吐多少字（吞吐） |
| P50 / P99 | 一半的请求比它快 / 100 个请求里最慢那几个的时间 |
| 量化 Q4_K_M | 把模型压缩到原来的 1/3 左右，牺牲一点点准头换速度和显存 |
| mmproj | 多模态模型里"处理图片"的那半个模型，跟说话的那半个分开存 |
| PagedAttention / 连续批处理 | 让很多个人同时用一张卡的办法，对单个人没提速 |
| PD 分离 | 把"读题"和"写答案"放到不同机器上跑 |
| 投机解码 | 让小模型先猜一串，大模型批量复核，对了就白赚 |
| LoRA / rank | 原模型一动不动，只在外挂一小撮参数去训练（比重装房子轻得多）；rank 就是这撮参数有多大 |
| merge | 把外挂参数加回原权重，变回一个普通模型文件 |
| 对齐 / DPO / RLHF / GRPO | 教模型"什么叫好答案"的几种打分学习法 |
| RLVR | 只用能自动判对错的标准（比如计算题答案）来强化学习 |
| QLoRA | 先把模型压小再 LoRA，更省显存但更慢、依赖更多 |

## 3. 本项目逐项对照：考虑了哪些因素、选了什么

### 3.1 推理侧 —— 核心方法：**先列约束，再选引擎**

当时钉死的六条约束（全部实测，不是拍脑袋）：

| 约束 | 实测值 | 后果 |
|---|---|---|
| GPU 只有 8 GiB | 8188 MiB，权重已占 3.96 GiB | 大模型/高并发方案全出局 → **量化是刚需** |
| Windows + **WSL 被安全策略封禁** + 无 Docker | `wsl.exe` 在黑名单 | **vLLM/SGLang/TRT-LLM 全部不可运行**（这条把一个技术权衡题变成了事实题） |
| 多模态 | 视觉塔 0.41 B（19.1%） | 引擎必须支持 mmproj 双文件 |
| 还要能训练 + 要 logits | 需求硬约束 | **必须保留 HF transformers** → 双引擎分工不是偏好，是必然 |
| 演示是单用户 | 并发 ≈ 1 | PagedAttention / 连续批处理收益 ≈ 0 |

**选了什么**：推理/部署 = `llama.cpp` + `Qwen3-VL-2B-Q4_K_M.gguf` + `mmproj-F16`；训练/评测 = HF transformers。

**实测收益（E1，3 次重复）**：吞吐 24.0 → 128.8~158.2 tok/s（**×5.2~6.6**）；P99 ITL 7.5× 改善；显存 −19%；能效 0.50 → 1.82 tok/J（3.6×）；**TTFT 基本不变**（0.045~0.106 s → 0.038~0.120 s）。

**最值钱的一条归因**：实测倍率 5.2~6.6× **超过了纯带宽能解释的 3.107× 上限** → 证明瓶颈不仅在搬数据，还有大量浪费在 Python 逐 token 循环与 kernel 派发上。所以实验顺序必须是"先换引擎、再降精度"，反过来会把框架开销误判成精度问题。

**面试最硬的一句话**：「 PagedAttention **不让任何单个请求变快，它让更多请求同时跑**」——所以选不选 vLLM 的判据是**并发度**，不是"它快不快"。

### 3.2 部署侧 —— ⚠️ 这里有一个真缺口

**已做的**：
- `src/serve/app.py` + FastAPI + uvicorn + 手写单页 HTML（不用 gradio，因为 gradio 的 Chatbot 塞不下"每一步调了什么工具"的分层结构）
- **关键设计**：服务端直接复用 `src.agent.react` 与 `src.tools`，不另写推理逻辑，确保演示的和评测的是同一套代码
- 能切换「完整系统 / 无工具对照」，把 P7 的负面结论直接演示出来
- 引用原文可点开，出处真实性由 `strip` 校验带真实 chunk_id

**⚠️ 没做的（本次核实，此前没写在任何文档里）**：
- P1 决策说"部署 = llama.cpp/GGUF"，但 **P8 实际跑的是 HF transformers bf16 进程内加载 + peft adapter**（`src/serve/app.py` 第 80~89 行明确如此）
- `models/gguf/` 下**只有基座下载的** Q4_K_M 与 mmproj-F16，**没有任何 merged 权重**
- 没有 `merge_and_unload` / `convert_hf_to_gguf` / `llama-quantize` 任何一个脚本
- → 也就是说：**「微调 → 合并 → 转 GGUF → 量化 → 起服务」这条链一次都没跑通过**，P1 与 P5 之间有缝

后果不只是简历难看：这条链上每个环节都可能**静默错位**（词表三值不一致已在 P0 实测：151936 / 151669 / 151643），没跑过就不知道会错在哪。

**其他部署缺口**：无 Docker/K8s、无并发（不清楚 QPS 上限）、无监控观测、无多实例。

### 3.3 微调侧 —— 这是你的强项区

**为什么 LoRA 而不是全参**（有实测账，不是跟风）：
- 显存冒烟实测：全参 + 不开 checkpointing = **14.86 GiB / 675 s/步**（溢出到共享内存）；开了 ckpt = 9.52 GiB 仍超物理 8 GiB
- 推算总账：全参 ≈ 15.8 GiB ❌；LoRA ≈ **6.3 GiB** ✅；pilot 实测峰值 **5.53 GiB**
- QLoRA 被评估后主动放弃：bitsandbytes 在 Windows 有安装/运行风险，且更慢

**最终配置与每条依据**：

| 参数 | 取值 | 依据 |
|---|---|---|
| LoRA r / α | 16 / 32（α/r=2） | 领域适配不需大 rank；2 是社区默认缩放比 |
| target_modules | 语言侧 28 层 7 类投影 | **视觉塔全程冻结**（主链路纯文本，动它有遗忘风险） |
| 可训练参数 | **17.43 M = 0.82%** | 冻结 316 张量（含 embed / lm_head） |
| lr / epochs | 1e-4 / 3（实际跑到 2.856 epoch） | 小数据取下沿；护栏在 step 342/360 因显存停止 |
| batch / accum | 1 / 8 | **实测 batch=2 反而更慢**（40.7 vs 21.9 s/样本，溢出惩罚） |
| gradient ckpt | True | 硬需求，非优化项 |

**踩到并归因的两条硬结论**（面试直接可用）：
1. **8 GiB 卡的"显存满"来自 reserved 不是 allocated**：allocated 只有 4.18~5.66 GiB，reserved 却冲到 8.25~8.54（>物理 8.0，溢出到共享内存）。`expandable_segments` 在 Windows 不支持。**唯一有效手段是每步 `empty_cache()`**（峰值降到 7.92 GiB，代价慢约 70%）→ 护栏判据必须用 allocated。
2. **CPU offload 视觉塔对峰值无效**（推翻了 200 条探测得出的"有效"结论）：因为决定峰值的那一步恰恰含视觉样本，临时搬回来后占用与常驻相同。

**微调收益（口径 v3，可引用）**：可答题 F1 0.149 → 0.329；calc 0.267 → 0.908；拒答正确率 0 → 0.917；选择题 90%。**视觉读数几乎没提升**（0.467 → 0.467），已用 blindness 对照实验排除"没看图"，真因是视觉训练样本只有 79/953 = 8.3%。

**为什么不做 RLHF**（JD 会问"要不要/有没有做对齐"）：三条实测依据——瓶颈是"算错、读不准"（客观可验证），不是风格；PPO 需要 4 份权重 ≈ 17.35 GiB **直接溢出**；没有偏好数据。并且算出 **RLVR 的确定性奖励只覆盖 eval 的 15%（calc 30 条）**，而最大短板 concept（33.5%，F1 0.080）恰好没有可验证奖励。→ 结论：RL 在本项目是锦上添花。这个论证本身就是加分答案。

## 5. 补充施工方案（按性价比排，每个都给出验收判据）

### S1 ｜跑通「微调 → GGUF → 服务」（半天，最高优先）

```
① merge_and_unload()  →  HF 全量权重（**必须 bf16/fp32 合并**）
② convert_hf_to_gguf.py → f16 GGUF
   ⚠️ 先确认脚本支持 Qwen3-VL 架构，否则白干（P1 文档早已标记此坑）
③ mmproj 单独转换，不能塞进语言侧文件
④ llama-quantize f16 → Q4_K_M
⑤ llama-server 起 OpenAI 兼容接口 → 用 P8 的 5 个示例问题各问一遍
```

**验收（缺一不可）**：
- [ ] ⑤ 的回答与 HF 版**语义一致**（措辞不同但结论相同不算失败，关键数字必须一致）
- [ ] 显存 ≤ HF bf16 版 −15%
- [ ] 同一题 tok/s 对比表落地到 `reports/`
- [ ] 词表三值不一致**没有**造成静默错位（转换前后同一 prompt 的首 token 必须一致）

**已知风险**：无法转怎么办 → 回退方案 B（llama.cpp 直接 `--lora <adapter>`），但要接受"对架构覆盖面窄"的代价并如实说明。

### S2 ｜后训练：先做 5 分钟的"可行性验证"，再决定要不要做（最高性价比）

你现在的处境是**最好的那种**：判分器现成（能当 verifier）、rejection sampling 只需 1 份权重（4.26 GiB，已推算不溢出）、QA 里有 30 条 calc 有确定性奖励。

```
Step 1（5 分钟，必做）：对 9 条错题各采样 8 次，验证 pass@8 是否显著 > pass@1
   → 若采样不出正确答案 = 能力缺失，rejection sampling 救不了，直接收手
Step 2（若 Step 1 成立）：对 calc 30 条采样 N 次，取答对的样本做一轮 SFT
Step 3：在同题面上复测，与现有 0.633 对比
```

**收益**：简历上能写 **RLVR / RAFT / STaR**，并且 STEP 1 无论成败都能讲——"先验证再投入"本身就是工程判断。

### S3 ｜补一组 rank 消融（约 1.5 小时）

训练一次约 16 分钟，评测约 10 分钟。做 **r = 8 / 16 / 32 三档 × 同一 eval 200 条**，产出一张"F1 / 数值命中 / 训练时长 / 峰值显存"的四维表。

**验收**：能回答"我为什么最终选 16"，而不是"大家都用 16"。
（意外收获：如果 r=8 效果相同，你就有了一条"更小的 rank 换到同样效果"的结论，这是很漂亮的工程故事。）

### S4 ｜把"不会做"的并发知识变成"能量化"的东西（约 2 小时，零 GPU 成本）

本机跑不了 vLLM，但可以补两种别人没有的量化成果：

1. **写一个 KV Cache / 并发显存计算器**：给定模型配置，输出"并发 N × 上下文 L 需要多少显存 + 剩余空间能放多少层 `-ngl`"。这恰好是 docs/02 里 Q5 的标准答法（SLO 倒推，不是调出来的）。
2. **给 P8 加一个并发压测**：起 1/2/4/8 个异步请求打 `/api/ask`，画出延迟-并发曲线，然后用 §2.2 的原理去解释拐点出现在哪。**这一步把"我没做过高并发"变成"我量化了它什么时候崩"**——后者在工程岗眼里更强。

### S5 ｜（可选，简历关键词）装一个 `llama-factory` 跑同一份数据

不为了更好，而是为了在 **JD 点名的工具**上有一手经验，并且能对比"自己写 ~150 行 vs 用框架"的取舍。成本约 1 小时。**收益主要是简历关键词与面试谈资**，技术上很可能是负收益（你自己写的那条管线更贴合数据）。

## 6. 面试话术：怎么把"没做过"讲成加分

**⛔ 千万别说**："我环境装不了 vLLM"、"我只有一张 8G 卡"、"我用不了分布式"。

**✅ 换成这个三段式**：「约束是什么 → 我在约束下选了什么 → 约束解除后我会怎么改」

示范（推理岗追问"你为什么不用 vLLM"）：

> "我的场景是 Windows 单机单用户，WSL 被安全策略封禁、没有 Docker，所以 vLLM 的所有 Windows 路径都不可用——这是事实约束。我先确认了这一点再选型，没有花一晚上撞墙。
> 但在做决定前我判断的是**收益**：PagedAttention 的价值是让更多请求同时跑，我的并发是 1，理论收益接近 0——所以排除它的代价也很低，这是我敢排除的依据。
> 我用**引擎分工**补上了这一课：训练/评测留在 HF 保可微性，推理/部署走 llama.cpp 拿执行效率。
> 如果换到多用户线上场景，我会切到 vLLM/SGLang，切的条件是并发度上去之后——**选型跟着场景走，不跟着热度走**。"

同样的话术适用于：并发、Docker、分布式训练、PPO。**每一条都要落地成"切过去的条件是什么"**，这才是体现工程判断的地方，而不是背名词。
