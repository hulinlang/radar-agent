## 一、先立住叙事：三层串联闭环

### 1.1 一句话

> 我给一个 **2B 的小模型**配了「开卷考试 + 计算器」的外挂（RAG + ReAct Agent），
> 微调它学会引用出处；**然后从零手写了一个 C++/CUDA 推理引擎来跑它**，
> 在 8GB 笔记本显卡上把 decode 做到了和 llama.cpp 平价（Q4 119.4 vs 116.9 tok/s）。

### 1.2 90 秒主线（三层，缺一不可）

```
算子层  手写 CUDA/Triton GEMM：FP32 1024³ = 5542 GFLOPS（cuBLAS 的 96%）  ← 算力受限侧
   │
   │   ★ 桥 = Roofline 性能模型（把"快"翻译成"离屋顶线多远"）
   ▼
引擎层  自研 C++/CUDA 推理引擎（阶段 B，B0–B9）                            ← 带宽受限侧
        GGUF→BPE→前向→kernel→continuous batching→服务化
   │
   ▼
系统层  radar-agent：RAG + ReAct Agent + 检索 + 工具 + 评测（P0–P8）        ← 端到端业务价值
```

**为什么这个组合稀缺**：大多数人只做其中一层。三层都做过、且**每层都有实测数字**、
并且**能用同一张 Roofline 图把它们串起来**——这是"性能直觉"的证据，不是背书。

## 三、专题 A：RAG 与 Agent

> 本节的展开底稿在 `docs/13`。这里只留**面试最该说的那几句 + 数字**。

### 3.1 检索：三路召回 + RRF

- **稠密**（bge-m3）：抓语义，但**跨语言有上限**、对专有名词弱。
- **稀疏**（BM25，中文用**字符 bigram** 而非 jieba）：抓字面与术语，中文分词器与 embedding 侧不一致会静默出错。
- **图号/表号第三路**：`Fig. 2.4`、`表 3-1` 这类查询靠语义检索永远排不上来，必须精确匹配。
- **RRF 融合**：不用加权求和（量纲不同、要调参），用**排名倒数**融合，天然免归一化。

⭐ **一句话结论**：改检索策略的收益都在**个位数百分点**（单引擎→两路融合 R@5 +5.2pp；
加 1639 条英文文献对教材题 **0 影响**；图号索引对全集 **0 影响**）。

### 3.2 Agent：为什么是 ReAct 而不是固定流程

| 方案 | 优点 | 为什么没选 |
|---|---|---|
| 固定 DAG（先改写→检索→生成） | 可控、可预测 | 常识题（"1+1"）也会去翻雷达教材；计算题要走已经确定的路径 |
| **ReAct（选它）** | 模型自主决定调不调、调几次 | 需要护栏，否则会打转/重复调用 |

**六重护栏**（每条都配计数器，可复盘）：重复调用检测、循环检测、步数上限、墙钟超时、
单步超时、**末步屏蔽 `<tool_call>`**（逼它出最终答案）。

⭐ **一个很能讲的实测细节**：`<tool_call>` 在词表里**恰好是单 token（151657）**，
所以"末步屏蔽"可以用 `logit_bias = -100` 精确实现，**零误伤**。
实测：不开屏蔽 4/5 会继续调工具，开了 0/5。

### 3.3 工具设计：一次由评测驱动的接口改造

**问题**：早期 `formula_calc` 让模型填「公式名 + 参数名」。P7 逐条 trace 发现 30 道计算题里
**13 道栽在"猜名字"上**（漏传 / 参数名猜错 / 臆造公式名 / 选错公式）。

**改造**：改成 `calc`，只收**算术表达式**（如 `3e8/(2*100e6)`），用无 builtins 的安全沙箱求值。

**结果**：

| | 传公式名（tool5） | 只传表达式（tool6） |
|---|---|---|
| calc 得分 | 0.400 | **0.633** |
| 与"不给工具"基线 0.700 的差距 | −0.333 | **−0.067** |
| 栽在"猜名字" | **13 条** | **0 条** ✅ |

⭐ **失败模式被彻底改写**：从「接口把模型搞乱」（设计问题，已修完）
变成「模型自己写不全式子」（2B 能力边界，14 条）。**这个转变本身就是改造成功的证明。**

典型剩余失败：RCS 从 1→50，正确是 $(\sigma_2/\sigma_1)^{1/4}$，它传给工具 `50.0/1.0`（漏了 1/4 次方）。

## 四、专题 B：微调

### 4.1 冻结边界（面试必问）

```
可训练：语言侧 28 层的 7 类投影           → 17.43 M 参数（占总量的 0.82%）
冻结：  model.visual（视觉塔）             → 全程冻结 + no_grad
        lm_head / embed_tokens            → 共 316 个张量
```

**为什么冻视觉塔**：8GB 显存下多模态微调显存放大是高风险（`docs/00` §9.2），
且主链路已拍板走**纯文本**；图表问答作为独立实验。

### 4.2 两个高危静默错误（`docs/00` §4.6 清单里的）

1. **loss mask 边界**：把 prompt 也算 loss → 模型学会"复读问题"而不是"回答问题"。
2. **padding_side 训练/推理不一致**：训练用 right padding、推理用 left → 生成质量悄悄劣化，不报错。

### 4.3 微调收益（口径 v3，200 题冻结集，不给工具）

| 指标 | 基座 | tool6 |
|---|---|---|
| 全部 F1 | 0.120 | **0.322** |
| 计算题 F1 | 0.280 | **0.886** |
| **该说"不知道"时** | 0.002 | **1.000** |

⭐ **一个反直觉的收获**：把计算器改成"传表达式"后，**拒答能力从 0.949 回到满分 1.000**——
上一版曾为此付出过代价，这次改造在裸问答口径上**全面不低于**旧版，没付任何代价。

### 5.3 性能演进（decode tok/s，同机同 prompt）— **这张表是面试主线**

| 形态 | tok/s | 相对 | 瓶颈诊断 |
|---|---|---|---|
| 朴素单线程 F16 | 0.35 | 1× | 纯算 |
| OpenMP F16（16 线程） | 3.67 | ×10.5 | 并行度不足 |
| OpenBLAS F32 | 1.45 | ×4.1 | ⚠️ **反证：BLAS 撞内存墙**（F32 访存量翻倍） |
| AVX2 F16 | 10.3 | ×29 | 达 llama.cpp CPU F16 的 70% |
| AVX2 Q4_K_M | 17.9 | ×51 | 达目标的 94% |
| CUDA F16（gemv v1） | 40.4 | ×115 | profile 定位层 gemv 占 **76.8%** 热点 |
| **CUDA F16（gemv v2）** | **62.5** | ×179 | half2 向量化 + warp 归约 → **反超 llama.cpp 到 103%**，等效带宽 **215 ≈ 天花板 217.4 GB/s** |
| **Q4-on-GPU（B7）** | **119.4** | ×341 | 自研 Q4_K/Q6_K fused dequant-dot + CUDA Graphs |
| 参照：llama.cpp CPU Q4 / CUDA F16 / CUDA Q4 | 37.9 / 60.8 / 116.9 | | |

**三条面试金句**：
1. **"量化不配融合 kernel 等于白量化"**——标量 dequant 的 Q4 比 F16 还慢 **0.89×**。
2. **decode 是访存受限，不是算力受限**——所以优化方向是"减少访存字节 + 提高有效带宽"，
   而不是"堆算力"。表里 OpenBLAS F32 只跑 1.45 就是最硬的反证。
3. **优化必须过同一份对拍**——OpenMP 从单线程到 16 线程是 **bit 级不变**（行分区保证），
   这是验收项而非期望。

### 5.4 关键技术发现（`docs/27` §3，面试弹药）

1. transformers 5.x 的 `hidden_states` 末位是 **final_norm 输出**，裸末层不在元组里——不看源码必错。
2. Qwen 存在 **massive activation 维**（sink token 残差达 **13201**）→ 绝对误差阈值失效，
   必须用 atol+rtol 的相对口径。
3. **transformers 分词器带 NFC normalizer，GGUF/llama.cpp 链路不带** → 部署一致性陷阱（静默）。
4. **llama.cpp 的 Q4 kernel 是 Q4_K × Q8_K（激活也量化）**——
   "同一个 Q4 模型"在不同引擎下数值不同，**对拍前必须先定义数值口径**。
5. **decode gemv 生产上不走 cuBLAS**（llama.cpp / TensorRT-LLM 同）——我原本的假设被实测推翻。
6. **平局个案处置**：greedy 分叉时用 top-2 logit 差判定"合法平局"（记录不究），
   而不是当成 bug 死磕。

### 5.5 数值口径：怎么比"两条都合法"的路线

⭐ **这是最能体现工程判断力的一点。**

自研 Q4 与 llama.cpp Q4 是**两条不同的数值路线**（激活是否量化、dequant 顺序、累加顺序），
逐 token 相同**在数学上就不该成立**。所以不能用逐 id 对拍。

**解法：teacher-forcing 一致率**——把同一个 token 前缀喂给两边，看下一步 argmax 是否一致。

| | 一致率 |
|---|---|
| 自研 Q4 | **49/50** |
| llama.cpp Q4 | 48/50 |

→ 结论从"对不上"变成"**两条路线在各自精度下的等价**"。

### 5.6 Kernel 迭代史（`docs/28` §6.3，展示 profile 驱动优化）

Q4-on-GPU 不是一次写成的，是**逐版 profile 驱动**：
v1 warp-per-row + lane-per-sub-block → 未达 118.6 目标 → v2 调优 → 定位 **issue-bound**
（fp32 精确 dequant 的指令发射墙在 ~150 GB/s）→ 加 CUDA Graphs 吃掉 ~450 launch/token。

⚠️ **诚实标注**：fp32 精确路线已与 llama.cpp 平价；**再往上要换 int8 激活 + dp4a/mma**
（llama.cpp MMQ 路线），但那会改变数值口径（届时对拍改用 teacher-forcing）。
这条路我**没做**，能说清"为什么不做、以及做的代价"。

### 5.7 服务化：B9 的两个设计点

1. **为什么从 ctypes 改成最小 HTTP**：ReAct Agent 跑在 **Windows 宿主** Python，
   引擎在 **WSL guest**——ctypes 跨不了 OS/进程边界。
   （原来的"单进程 demo"假设是错的，这是动工前发现的事实错误，`docs/30` §3.2）
2. **会话级 LCP 前缀复用**：ReAct 每一步的 prompt 与前一步大量重叠。
   记录上次完整 token 序列，算 token 级最长公共前缀，只对后缀做 prefill。
   **正确性论据**：位置 p 的 KV 只由 token p 与前缀状态决定，相同前缀 ⇒ 相同 KV
   （B8 已证 bitwise）→ 与全量重跑**逐字节相同**（实测 REUSED=37 全命中）。

### 5.8 顺手修掉的 3 个 latent bug（`docs/29` §7.5）——很能体现"发现静默错误"

1. **decode attention 的 `d_scores` 跨头数据竞争**（B6b 遗留）：scratch 被 16 个头的 block 共享，
   长 prompt 时交叠覆写 → softmax 坏 → NaN → **argmax 恒 0（生成全 0）**。
   修完 F16 逐 id 从 99/100 → **100/100**。
2. **`kv_cap` 只算首条 prompt**（批模式）：后续更长 prompt 越界 → illegal memory access。
3. **槽位中途分配丢首 token**（调度器）：assign 发生在一个步的"发射阶段"之后、
   "步进阶段"之前 → 新请求的第一个预测 token 从未发射就被覆盖。修为 per-slot `emitted` 标记。

⭐ 面试讲法：**这三个都不是崩溃型错误，是"跑得通但结果错"的静默错误**——
正是 `docs/00` §4.6「静默错误优先原则」要求的排查优先级。

### 5.9 项目闭环（B9 的叙事价值）

> 雷达 Agent（Windows 宿主，ReAct + 检索 + 计算器）的生成后端，
> **已从 llama-server 切换为自研 C++/CUDA 引擎**（WSL 内 `radar-serve`），
> 口径 v3 下 22 题得分 **完全一致（Δ=+0.0000）**，16/22 输出逐字相同。

即：**自研引擎不是玩具，它真的在支撑业务链路。**

## 六、高频追问 Q&A 库

> 答题骨架 + 加分点。更完整的在 `docs/12` §五、`docs/13` §七。

**Q1｜为什么不全手写引擎，GEMM 却要接库？**
骨架：先划"学习价值 vs 生产做法"两条线 → 引擎本体（前向图/KV/采样/量化 kernel）手写是学习目标；
GEMM 是成熟到没有边际收益的基础设施，生产上也是接库 → 手写 BLAS 的代价是周级时间换 0 收益。
加分：能说清"decode 走 gemv 不走 cuBLAS"这个反直觉事实，以及为什么。

**Q2｜你的 RAG 到底有没有用？**
骨架：**没有提升最终答案**（0.370→0.295），但**唯一确定性收益是引用溯源**（130 个出处、坏引用 0）。
→ 主动给负面结论 + 归因（检索总能返回东西 → 模型不肯说"不知道"，拒答 94.7%→78.9%）。
加分：说明"评估比优化更难"——我为了得到这个结论先建了无检索基线。

**Q3｜为什么 2B 模型不用更大的？**
骨架：约束驱动（8GB 显存 + 学习目标 + 本地全链路）→ 定位是**小成本微调的可复现实验台**，
不是"追 SOTA" → 所有结论都标注了模型天花板（复杂公式推导必然弱）。
加分：主动说"收益天花板在数据与模型侧，不在检索算法侧"，并给出量级对比（个位数 pp vs 几十 pp）。

**Q4｜怎么保证评测不是"自己出题自己满分"？**
骨架：① 评测集**先于**微调冻结（sha256 冻结）② 三集合物理隔离 ③ 去污染（n-gram + 图像 sha256）
④ 判分口径 v3 全项目复用 ⑤ **评测集内容一变，历史结果全部作废**，base 与微调同题面重跑。
加分：说清"keypoints 严格子串不能判自由生成"（基座与微调得分完全相同 0.0383 就是证据）。

**Q5｜LoRA 为什么有效？秩怎么选？**
骨架：ΔW 低秩假设（预训练权重已接近"任务无关的低秩流形"）→ 只学 BA，参数量从全参降到 0.82% →
秩不是越大越好（`docs/14` S3 有 rank 消融方案）。
加分：连带讲**冻结边界**（视觉塔 + lm_head + embed_tokens）以及为什么。

**Q6｜ReAct 和固定 pipeline 的取舍？**
骨架：见 §3.2 表。关键词：常识题不该调工具、计算题路径固定、需要自主性 → ReAct + 六重护栏。
加分：引"末步屏蔽 `<tool_call>`，因为它是单 token 151657，零误伤"。

**Q7｜显存怎么估？为什么 reserved 会超过物理显存？**
骨架：权重 + 激活 + KV cache + 碎片。8GB 卡训 2B 多模态时，**reserved 8.25–8.54 > 物理 8.0**
是溢出到共享内存，而 **allocated 只有 4.2–5.7** → **护栏必须用 allocated 判危险**，用 reserved 会误判。
加分：`expandable_segments` Windows 不支持；CPU offload 视觉塔对峰值无效；
**唯一有效 = 每步 `empty_cache`**（代价慢 ~70%）。

**Q8｜为什么 PDF 解析用 MinerU 而不是 pymupdf？**
骨架：教材的公式/表格是**结构**不是文本 → pymupdf 抽出来公式全碎（论文双栏还会把左右栏横向拼进同一行）
→ MinerU 保住真 LaTeX（164 条行间公式括号 100% 配平）+ 结构化图注（绑定率 7/7）。
加分：⚠️ 但 **MinerU 会犯"看起来对"的错**——p78 把 $u_2 = c\,u_1$ 识别成 $u_1 = c\,u_1$，
语法合法、语义错误 → **公式 LaTeX 必须人工核对，不得直接抄**。

**Q9｜切分为什么不能按固定字数？**
骨架：会切断公式、表格、图注；元数据（页码/标题）会与实际内容错位 → 静默错误。
→ 改用**块级版面感知**切分（`items` 顺序即阅读序，`(pdf_page, bbox)` 做连接键，差集 0）。
加分：caption 字段名随块类型变（`image_caption` / `chart_caption` / **`_table_caption_`**），我踩过 3 次。

**Q10｜稠密 vs 稀疏，RRF 是什么？**
骨架：稠密抓语义/跨语言、稀疏抓字面/术语；RRF 用排名倒数融合，**免归一化、免调参**。
加分：中文用**字符 bigram** 而非 jieba（分词器与 embedding 侧不一致会静默出错）。

**Q11｜阈值 θ=0.55 怎么定的？**
骨架：**实测标定**，不是拍的。无关问题最高 0.545、相关问题最低 0.582 → 取 0.55 刚好分开
（无关组 100% 判空、相关组 0% 误杀，间隔 +0.037）。
⚠️ 诚实补一句：**"带雷达术语但语料里没有答案"的 0.5965 拦不住**。

**Q12｜量化后为什么变快？精度损失多少？**
骨架：降比特 → 权重体积↓ → decode 访存字节↓ → 带宽受限场景下直接线性加速。
精度：200 题回归实测退化 **−0.035**（轻微）。
加分：⚠️ **必须配融合 kernel**，否则 dequant 开销吃掉收益（标量路径 Q4 比 F16 慢 0.89×）。

**Q13｜怎么判断 RAG 错在检索还是生成？**
骨架：构造**"给定黄金上下文"对照组**——把正确答案的证据句直接塞进 prompt。
若正确率显著上升 → 瓶颈在检索；仍错 → 瓶颈在生成/微调。
加分：⚠️ 我实测发现这个诊断本身有个坑——黄金段落由 `evidence.quote` 反查得到，
那是**概念出处**而非计算题真正需要的公式，**标注本身语义错位**（0/22 反查不到，退化成"无资料"）。

**Q14｜延迟和吞吐怎么权衡？P99 为什么重要？**
骨架：必须**成对报告**（只报 tok/s 不报延迟视为无效数据）；必须给 **P50 与 P99**（长尾决定体验）。
加分：我的实测教训——**跨 session 漂移 17.3% ≫ 组内 0.6–3.6%**，
所以绝对吞吐**不可跨 session 引用**，必须同 session A/B/A/B 交替测。

**Q15｜自研引擎和 llama.cpp 比分，凭什么信？**
骨架：① 阶段 B 总 DoD = 与 llama.cpp **440/440 token 逐一相同**（同数值路线下）② Q4 是另一条路线
→ 用 **teacher-forcing 一致率**（49/50 vs 48/50）③ 性能用同协议对打（同 prompt、100 token ×3 取中位）。
加分：主动说测量噪声 —— 单 tensor 反复跑的微基准会吃 **L2 暖缓存**虚高，必须以 e2e profile 为准。

**Q16｜continuous batching 解决什么问题？**
骨架：静态 batch 要等最慢的序列；continuous batching 让完成的槽位立刻被新请求复用。
→ 我的实现：KV 槽位池 + 调度器（EOS 释放 / 中途 prefill 插入）+ 批量 decode 整步 CUDA Graph。
实测 prefill 4.8–5.3×（567–616 tok/s）、B=8 聚合 3.96×（469.6 tok/s），逐 id 8/8 + 连续批 16/16 一致。

## 七、负面结果怎么讲

> 这是差异化最强的一节。**面试时主动讲，比只讲漂亮数字可信得多。**
> 完整版在 `docs/11` §二、`docs/12` §四。

| 负面结果 | 数字 | 归因（关键：不能只报现象） |
|---|---|---|
| **开检索后综合分下降** | 0.370 → 0.295 | 检索总能返回东西 → 模型"过度自信"不肯拒答（94.7%→78.9%）。**小模型 RAG 的经典副作用，不是配置没调好** |
| **公式概念索引是负收益** | MRR 0.590 → 0.573 | 两个根因：① 概念表术语太宽（"多普勒频率"挂到 36 个公式块）② **计算题的标准答案本身就摇摆**（用"公式本体"当答案说有效、用"概念出处"说有害）→ **靶子在动，不该急着调参** |
| **视觉读数能力零提升** | 数值命中 0.467 → 0.467 | 视觉训练样本太少（83 条）。**已排除** blindness 与分辨率（加大分辨率也测过，无效） |
| **中文提问查英文论文差** | R@5 24.2% | 用对照实验分离出**两层**：中文语料截胡（屏蔽后 R@10 39.4%→63.6%）+ **跨语言本身有上限**（只翻英文 R@10 也只 63.6%） |
| **检索策略的收益都是个位数 pp** | +5.2pp / 0 / 0 / 负 | → 核心判断：**收益天花板在数据与模型侧，不在检索算法侧**（数据侧问题几十 pp 量级） |

⭐ **讲负面结果的三个纪律**（`docs/12` §四）：
1. **先说现象，再说归因，最后说"我判断该不该修"**——只报现象显得没主见，只报归因显得像找借口。
2. **数字必须能追溯到原始日志**，说"未验证"也比编一个强。
3. **区分"设计问题"和"能力边界"**：前者该修（如 calc 接口），后者该承认（如 2B 写不全公式）。
