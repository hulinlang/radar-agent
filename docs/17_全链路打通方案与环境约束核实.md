## 0. 一句话结论

**「WSL 被封」是 WorkBuddy 自己的「程序黑名单」拦的，不是 Windows、不是学校、不是公司——你随时可以解除。**
但更重要的发现是：**你要打通的那条主链路（微调→合并→转 GGUF→量化→起服务）根本不需要 WSL**
——本机工具链已实测齐备。**唯一的真缺口是"我们没做"，不是"环境不许"。**
真正跟 WSL 相关的只有 **vLLM/SGLang** 那一块（§5）。

## 1. 「WSL 被安全策略封禁」到底是什么（实测）

### 1.1 拦截原文（两次实测，都是 WorkBuddy 的执行层）

第一次（用 `Start-Process` 调）：

```
Command blocked for security: Start-Process with a shell/interpreter/LOLBin/system-tool
target spawns a child process that bypasses PowerShell command validation
```

第二次（直接 `&` 调 `wsl.exe`，**拿到确切答案**）：

```
PROGRAM BLOCKED BY SECURITY POLICY - The sandbox prevented a program on the
configured Program Blacklist from starting:
  - wsl.exe (C:\WINDOWS\System32\wsl.exe)
This block cannot be approved or bypassed from the current command.
If the user wants to allow this program, they must remove it from
Security Center -> Command Security -> Program Blacklist.
```

### 1.2 结论与更正

| 项 | 结论 |
|---|---|
| 谁在拦 | **WorkBuddy 的「安全中心 → 命令安全 → 程序黑名单」**（用户侧配置） |
| Windows 拦了吗 | **没有**。`C:\WINDOWS\System32\wsl.exe` 文件存在，可访问 |
| 学校/公司 MDM 拦了吗 | 无从证明，但**本次拦截链条指向的是 WorkBuddy**，不是 OS |
| 怎么解除 | **安全中心 → 命令安全 → 程序黑名单 → 移除 `wsl.exe`** |

> ⚠️ **我的第二处判断错误（2026-09-29）**：
> `MEMORY.md` 里一直写着「`wsl.exe` 被封 + 无 Docker → vLLM 不可实机跑」。
> 我记录的只是**现象**（跑不起来），没记录**来源**（是谁拦的），
> 于是后面一路都把它当成"OS 级硬约束"，进而推出"vLLM 本机不可能"——**这个推论站不住**。
> 实测后订正为：**这是可解除的用户侧配置；且主链路根本不依赖它。**
>
> 教训（与项目既有第 7 条同源）：**"跑不起来"必须追到"谁拦的"，否则会把可选项误当硬约束。**

## 3. 三个真实的执行风险（都不是环境封锁）

### 3.1 ⚠️ 多模态会拆成两个文件，mmproj **不能被量化**

Qwen3-VL 转 GGUF 后是**两个文件**：
- **语言模型** GGUF（可量化）
- **mmproj**（视觉投影）GGUF —— P1 实测：**必须保持 F16**，量化会明显退化视觉能力

⭐ **可省的一步**：微调时 `model.visual` 是**全程冻结**的（`docs/09`），
所以 **mmproj 可以直接复用基座那份** `mmproj-Qwen3VL-2B-Instruct-F16.gguf`（781 MiB），不必重新导出。
→ **只需转换并量化语言模型部分。**

### 3.2 ⚠️ `convert_hf_to_gguf.py` 需从 llama.cpp 源码获取，且版本要对齐

winget 只装了**二进制**，没有 Python 转换脚本。需要：
- `git clone` llama.cpp 源码（**git 已装**），或直接取 `convert_hf_to_gguf.py`
- 装 `gguf` 与 `sentencepiece`（两个都 MISSING）
- 版本尽量对齐二进制的 **build 10951**，避免 GGUF 格式/元数据差异

### 3.3 ⚠️ 词表口径必须重新核对（P0 的老雷）

P0 实测过词表**三值不一致（151936 / 151669 / 151643）**。
转换与起服务前必须确认：merge 后模型的 `vocab_size`、tokenizer 实际长度、GGUF 元数据里的 `n_vocab` **三者一致**。
→ **这是最容易静默出错的地方**：不一致不会崩，只会让输出变成乱码或提前截断。

## 5. vLLM / SGLang：唯一真正跟 WSL 相关的部分

### 5.1 已核实的事实（2026-09-29 检索）

- **vLLM 至今没有官方 Windows 支持**。官方安装文档只列 Linux（CUDA / ROCm / XPU）与 CPU；
  maintainer 长期把 Windows 原生 issue 指向 WSL2。
- **WSL2 路径的代价**：GPU 直通 + Hyper-V 调度带来 **20%~40% 吞吐损失**。
- **Docker Model Runner**（2025-12 起支持 vLLM）底层**仍然是 WSL2**，继承同样的税。
- **原生第三条路**：社区 fork `SystemPanic/vllm-windows`，**v0.20.0（2026-04-30）** 提供
  原生 Windows wheel（Python 3.12 + CUDA 13 + PyTorch 2.11），并首次支持 **NCCL + 张量/流水线并行**。

### 5.2 三条路对比

| 路 | 要不要动 WSL 黑名单 | 代价 | 适用 |
|---|---|---|---|
| **A. WSL2**（官方推荐） | ✅ 要解除 | 20–40% 性能税；要装 Ubuntu + guest CUDA | 想完全跟官方生态一致（FA3/FP8/投机采样全套） |
| **B. `vllm-windows` 原生 wheel** | ❌ **不用** | 社区维护、版本滞后于上游；需 wheel 与本机 torch/CUDA 对齐（本机是 **cu128**，v0.20.0 要 CUDA 13） | ⭐ **想在本机原生跑、不想付虚拟化税** |
| **C. Docker Model Runner** | ✅ 要解除（且本机无 Docker） | 要先装 Docker Desktop | 最省事但依赖最多 |

### 5.3 我的判断（推测，但基于 E1 实测）

**vLLM 对你这台机器的性能没有帮助**——E1 已实测：单用户场景下 llama.cpp Q4_K_M 比 HF 快 **5.2~6.6 倍**，
而 **vLLM 的优势是并发**（batching / PagedAttention），你的并发≈1，**它的强项用不上，8 GiB 还更紧**。
→ **装 vLLM 的价值是"读懂调度器 + 简历上多一个名字"，不是"跑得更快"。**
→ 因此建议：**优先 B（原生 wheel，不动黑名单）；只有想跟官方生态完全一致时才解除 WSL。**
