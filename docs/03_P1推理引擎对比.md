## 【① 这一步要解决什么】

P0 证明了"能跑"，但只跑到 **24.36 tok/s**，而按带宽推算上限是 60.2 tok/s —— **利用率仅 40.5%**。
P1 要回答的是：**那 60% 的差距去哪了？换引擎能拿回多少？量化又能再加多少？**

**不做这一步会怎样**：会带着一个"猜出来的瓶颈"进入 P8。比如误以为是"模型太大、精度太高"，
于是花大量时间去做更激进的量化——而真实瓶颈可能是**框架开销**，量化一分钱都换不回来。

> **P1 的产出不是"跑起来了"，而是「一条可解释的性能因果链」+「一套可复用的测量台」。**

## 【② 核心原理】

### 2.1 假设与验证设计

P0 留下一个未解释的现象：**只用满了 40.5% 的带宽**。可能的瓶颈有三个：

| 假设 | 若成立的预期 | 验证手段 |
|---|---|---|
| H1 **框架开销**（Python 逐 token 循环 + kernel 派发） | 换 C++ 引擎后吞吐大幅提升，且**与量化无关** | E1：同模型、同 prompt、同解码参数，只换引擎 |
| H2 **带宽受限** | 换引擎收益有限；降低权重大小才有效 | E1 若无显著提升则成立 |
| H3 **prefill 受限** | TTFT 会随引擎更换明显变化 | E1 里单独看 TTFT |

**E1 的纪律**：两个 run 的 `overrides` 都是空 `{}` —— 即**唯一变量就是引擎本身**。

### 2.3 结论：H1 成立，H2/H3 不成立

1. **瓶颈是框架开销，不是带宽。**
   若带宽受限，实测提升应约为**语言侧权重体积之比**：
   ```
   HF bf16 语言侧  = 1,720,574,976 × 2 B = 3.441 GB
   GGUF Q4_K_M 语言侧 = 1,107,409,952 B  = 1.107 GB
   体积比 = 3.441 / 1.107 = 3.107×   ← decode 阶段带宽上限的放大倍数
   ```
   实测到了 **5.2–6.6×**，**超过**纯带宽能解释的上限 ——
   说明有相当一部分时间原本浪费在 Python 逐 token 循环与 kernel 派发上。

   > **口径更正（自查）**：本节原先写「`4.25 GB / 1.20 GB ≈ 3.5×`」，两处都偏了：
   > ① 分子应取**语言侧**权重（3.441 GB）——视觉塔那 0.814 GB 在 decode 时**不会被读**
   > （只有 prefill 时跑一次），拿全模型体积当分子会高估带宽收益；
   > ② 分母应取**本机实际文件**（1.107 GB），而非社区仓库页面的标称 1.2 GB。
   > 更正后比值从 3.5× 降到 **3.11×**，**结论反而更强**：实测超出理论上限更多。
   >
   > 这类"拿错分子分母"是 RAG/推理报告里最常见的隐蔽错误 —— 它不会报错，
   > 只会让结论悄悄偏小或偏大。**凡是比值，都要写清两侧各是什么、为什么是它。**

2. **prefill 没有变快（TTFT 持平，VL 用例甚至从 0.106s 退化到 0.120s）。**
   这**精确验证了**面试考点 Q4 的推理：量化减少的是 decode 阶段要读的**权重字节数**，
   而 prefill 是 compute-bound，收益本就有限。**我们的数据把这个理论预测测出来了。**
3. **P99 的改善幅度（7.5×）大于吞吐的改善幅度（6.3×）** —— 说明 HF 的延迟长尾更差，
   对交互式体验伤害更大。

### 2.3b 两个维度的正交性（后端 ≠ 精度）

**"Vulkan" 与 "F16/Q4_K_M" 是两个互相独立的维度，任意组合都成立。**

| 维度 | 取值 | 管什么 |
|---|---|---|
| **推理后端 / 内核** | Vulkan / CUDA / CPU / Metal / SYCL | **怎么算** —— 用哪套 kernel 执行矩阵乘 |
| **权重精度 / 量化** | F16 / Q8_0 / Q6_K / **Q4_K_M** / Q4_0 … | **算什么数据** —— 权重以多少 bit 存储 |

本机实测的落点：

| | 后端 | 精度 | 实测 bpw | 文件 |
|---|---|---|---|---|
| HF 路径（基线） | PyTorch CUDA kernel | bf16 | 16 | `model.safetensors` 4.255 GB |
| llama.cpp 路径 | **GGML Vulkan**（`ggml-vulkan.dll`） | **Q4_K_M** | **5.149** | `Qwen3VL-2B-Instruct-Q4_K_M.gguf` 1.031 GiB |

**"Q4_K_M 是 4bit" 这个说法并不精确。** 实测张量分布（直接解析 GGUF 张量信息段得出）：

| 量化类型 | 参数量 | 占比 |
|---|---|---|
| **Q4_K** | 1,203,765,248 | **69.96%** |
| **Q6_K** | 516,685,824 | **30.03%** |
| F32 | 123,904 | 0.01% |

→ `_M`（Medium）后缀的实际效果就是把**约 30% 的敏感张量抬到 Q6_K**（即 `attn_v` / `ffn_down` 这类），
整体 **5.149 bits/weight**，而不是 4.0。这正是 §2.6(b) 讲的"混合精度"在真实文件上的样子。

**mmproj 侧**：实测 **16.108 bpw**（F16 占 99.33% + F32 占 0.67%），即**确实没有量化**，
与社区"mmproj 建议 F16、不要量化"的实践一致。

**参数量交叉校验（两个 GGUF 合起来 == HF 全量）**：
```
语言侧 GGUF  1,720,574,976
视觉侧 mmproj  406,957,056
合计          2,127,532,032  ← 与 HF safetensors 的 2,127,532,032 **差 0**
```
这份一致性同时验证了三件事：① 拆分没丢参数；② 视觉塔占比 19.1% 在两侧口径一致；
③ 我们的解析脚本与 P0 的 safetensors 统计是两条独立路径、结论相同。

### 2.4 一个意外的收获：能效比（tokens/J）

§5.9 要求"尽可能包含 nvidia-smi 实测功耗，换算 tokens/J"。数据到手后可以算了：

| 引擎 | 吞吐 (tok/s) | GPU 平均功耗 (W) | **能效 (tok/J)** |
|---|---|---|---|
| HF bf16 | 24.03 | 47.7 | **0.50** |
| llama.cpp Q4_K_M | 158.18 | 87.16 | **1.82** |

→ **llama.cpp 每焦耳产出 3.6× 的 token。**
虽然它**绝对功耗更高**（87W vs 48W，因为把 GPU 真正吃满了），但**单位能耗产出显著更优**。

> ⚠️ 标注：功耗来自 `nvidia-smi power.draw` 的**板卡总功耗**（含桌面基线），两引擎同法采样、可比；
> 但采样窗口时长不同（HF 99 个样本 / llama.cpp 14 个样本），故这是**量级结论而非精确值**。

### 2.5 ⚠️ 必须诚实报告的对照瑕疵：输出长度不一致

**`text_open` 用例：HF 输出 974 token，llama.cpp 只输出 465 token（−52%）。**

这是同一 prompt、同一 `max_new_tokens=1024`、同为贪心解码。差异只能来自
**量化改变了模型的输出分布**（§2.7 的 D1 隔离实验已排除模板、EOS 集合、采样参数三个干扰项）。
这带来两个后果：

1. **`tok/s` 仍可比**（它是**速率**，已按 token 数归一）；
   但 **`E2E`（40.55s vs 2.94s，×13.8）不能理解为纯引擎加速** —— 它同时包含"速度更快"和"写得更短"两个因素。
2. **输出质量层面对比**（原文摘录）：
   - HF 的答案更详尽，但**出现了自我重复**：
     "通过合成孔径技术…合成出一个大孔径，从而获得高分辨率的图像" 与紧邻上一条几乎同义。
   - llama.cpp 的答案更紧凑，结构清晰，内容正确。
   → 在本例中，**量化后的答案质量并不更差，甚至更干净**；但这不能推广为"量化提升质量"，
   只是这一个样本的观察（§5.7：单次结果不构成结论）。

> **由此得出一条方法论**：跨引擎对比时必须检查**输出长度是否一致**。
> 若不检查，很容易把"模型变得话少"误读为"引擎变快了"。
> 本报告的处置方式是**同时给出 tok/s（速率）与 E2E（含长度差异）**，并显式说明。

### 2.7 归因实验 D1：输出长度差异到底来自哪里？

§2.5 留下一个必须回答的问题：`text_open` 上 HF 输出 974 token、llama.cpp 输出 465 token，
**两者都没触顶 `max_new_tokens=1024`**。这个差异是"模型行为"还是"我们配置不同"？

四个候选原因，逐个排除（**全部实测，不是推断**）：

| 假设 | 检验方法 | 结论 |
|---|---|---|
| **H2 采样参数不同** | 读 `llama-server` 的 `/props` → `default_generation_settings` | **排除**。所有惩罚项都是中性值：`repeat_penalty=1.0`、`presence_penalty=0.0`、`frequency_penalty=0.0`、`dry_multiplier=0.0`、`xtc_probability=0.0`。两边都是纯贪心。 |
| **H3 chat template 不同** | 解析 GGUF KV 元数据里的 `tokenizer.chat_template`，与 HF `tokenizer_config.json` 的逐字节比对 | **排除**。两边都是 **5292 字符**，`完全相同 == True`。 |
| **H4 EOS 集合不同** | HF `generation_config.json` 是 `[151645, 151643]`（两个），GGUF 只有 `151645`（一个）→ **把 HF 的 EOS 收紧到与 GGUF 一致，重跑** | **排除**。见下表：收紧后输出**逐字节相同**（sha256 一致），长度完全不变。 |
| **H1 量化改变输出分布** | 前三条排除后，剩下的唯一解释 | **成立（但见下方保留意见）** |

**D1 实验数据（`outputs/p1_bench_20260914_214618/`，每 run 2 次重复）**

| run | eos 集合 | 输出 tok | stop_reason | last_token_id | 文本 sha256（前 12 位） |
|---|---|---|---|---|---|
| `hf-eos-default` | `[151645, 151643]` | **974** | `eos` | **151645** | `127ea0272de6` |
| `hf-eos-single-151645` | `[151645]` | **974** | `eos` | **151645** | `127ea0272de6` ← **完全相同** |
| `llamacpp-q4km-vulkan0` | `[151645]` | **465** | `eos` | 未暴露 | `5f3766e80c1a` |

**三条扎实的结论：**

1. **两边都是"自然停止"，不是被上限截断。** `stop_reason` 全部为 `eos`；
   HF 还给出了 `last_token_id = 151645`，即模型自己吐出了 `<|im_end|>`。
   → **长度差异不是测量瑕疵，是模型行为差异。**
2. **两边实际生效的结束符其实相同。** HF 虽然配置里有两个 EOS，但本次生成命中的是
   `151645`，与 GGUF 唯一的 `151645` 一致。把 HF 收紧成单个 EOS 后输出**一字不差**，
   证明 **H4 虽然是一处真实的配置漂移，但在本次生成中没有起作用**。
3. **两边都是完全确定性的。** 长度跨重复稳定（`output_len_stable=True`），
   文本跨重复**逐字节一致**（sha256 相同）。→ 差异不是随机噪声。

**⚠️ 保留意见（必须写明）：H1 还不能算 100% 坐实。**
E1 同时改了**引擎**与**精度**两个变量。即使权重完全相同，**不同推理内核**
（PyTorch CUDA kernel vs GGML Vulkan kernel）的浮点累加顺序不同，也会产生微小 logits 差异，
理论上可累积成不同的生成轨迹。

要彻底分离，做法是**固定后端、只换精度**：让 **llama.cpp（仍是 Vulkan 后端）跑 F16 GGUF**
（`general.file_type` 会变成 MOSTLY_F16，bpw ≈ 16）。
注意这里**不是**"换成 Vulkan 跑 F16"—— 后端与精度是两个正交维度（§2.3b），
换的只是后者。需额外下载 ~3.45 GB，已列入待办。

### 2.8 ⚠️ 新发现的方法论问题：跨 session 波动远大于组内波动

本轮复盘时把 E1 与 D1 的 HF 数字并排，发现**同一配置、同一用例**却有明显差异：

| | E1（20:39–20:44） | D1（21:46–21:51） | 差异 |
|---|---|---|---|
| HF `text_open` 吞吐 | **24.03 tok/s** | **19.88 tok/s** | **−17.3%** |
| HF `text_open` E2E | 40.55 s | 49.00 s | +20.8% |
| HF `text_open` ITL P50 | 39.62 ms | 46.65 ms | +17.7% |
| **组内波动（3 次重复）** | 3.6% | 0.64% | — |
| GPU 平均功耗 | 47.7 W | 44.71 W | −6.3% |

**排查结果**：当前 GPU 温度 57°C、空闲功耗 17.6 W、SM 占空 6% —— **不是持续热节流**。
因此这是**笔记本 GPU 的动态功耗/频率管理与桌面负载共同造成的 session 间漂移**，
而非我们的配置变化。

**这条方法论结论比数字本身更重要：**

> **§5.9 要求的「关键结论至少重复 3 次并给出波动范围」，只覆盖了组内波动，覆盖不了跨 session 漂移。**
> 实测：组内 0.64%–3.6%，跨 session 17.3% —— **差一个数量级**。
> 如果只在一次 session 内重复 3 次就宣称"可复现"，是**假的可复现**。

**对本报告数字的影响（诚实评估）：**
- ✅ **引擎间倍率（×5.2–6.6）仍然成立**：E1 的两个 run 在**同一 session 内顺序执行**，
  共享同样的机器状态，因此**相对比较有效**。
- ❌ **绝对吞吐数字不可跨 session 引用**。要引用就注明来源 session 与当时的机器状态。
- 🔧 **改进方向（P8 性能实测必须采用）**：把测量顺序改成 **A/B/A/B 交替**，
  而不是"先跑完 A 再跑完 B"；并记录每次测量的 GPU 温度与功耗作为协变量。

### 2.9 视觉能力回归（量化掉点的任务级判据）

判据来自 `src/vl_probe.py` 里**写死真值**的合成距离-多普勒图（3 个目标、轴范围 0–100km / ±500Hz）。

| 引擎 | 结论 | 必需词 | 目标数 | 轴范围 |
|---|---|---|---|---|
| HF bf16 | **PASS** | Range, Doppler, km, Hz | 三 | 100, 500 |
| llama.cpp Q4_K_M | **PASS** | Range, Doppler, km, Hz | 三 | 100, 500 |

**但粗粒度 PASS 掩盖了一个真实退化（如实报告）：**

| | HF bf16 | llama.cpp Q4_K_M |
|---|---|---|
| 目标描述 | "**三个**明亮的黄绿色**斑点**…呈现**圆形**…典型的**高斯分布**" | "**三条曲线**…呈现**椭圆形**" |

- ✅ 数量（3）、两个轴标签、两个轴范围**全部读对** —— 粗粒度能力保住了；
- ⚠️ **形状描述退化**："斑点/圆形/高斯分布" → "曲线/椭圆形"。
  → 本项目的合成图用高斯亮斑，正解是"斑点/圆对称"；说成"三条曲线"是**错的**。

**结论**：Q4_K_M 对**粗粒度事实**（数字、标签）几乎无损，对**细粒度形态**（形状、分布）有可测退化。
**这条结论只有靠"真值已知"的合成图才能拿到**——用真实教材图做测试就无法区分"模型看错"和"我们不知道正确答案"。

> 方法论收获：`required_terms` 这类**粗粒度门禁不够**，细粒度退化会被漏掉。
> 下一步应把"形状/分布"也纳入判据（例如要求同时命中"斑点"或"圆形"）。

### 2.10 显存的双信源交叉校验（§5.8）

| 引擎 | 设备级峰值（nvidia-smi） | 进程内峰值（torch） | 差值 |
|---|---|---|---|
| HF bf16（`vl_rdmap`） | **5904 MiB** | **4143 MiB** | **1761 MiB** |
| llama.cpp Q4_K_M | **4791 MiB** | `None`（外进程，取不到） | — |

两个结论：
1. **进程内读数低估了设备占用 42%**。那 1.7 GiB 是桌面占用 + CUDA context + 分配器 reserved 碎片。
   规划显存预算时**必须用设备级数字**，否则会在部署时发现"明明算够了却 OOM"。
2. **llama.cpp 是外进程，torch 根本看不到它的显存。**
   如果适配器图省事用 `torch.cuda.memory_allocated()` 给它报显存，会得到 0 或陈旧值，
   而且**完全不报错** —— 这正是 §4.6 要防的静默错误。
   因此测量台统一用 `nvidia-smi` 采样（见 `src/bench.py::GpuSampler`）。

## 【③ 代码】（落盘位置与架构）

### 本次踩到的 3 个坑（含根因与修复）

#### 坑 1（静默且致命）：llama.cpp 检测到**两块 GPU**，可能静默跑核显
- **现象**：`llama-cli --list-devices` 返回
  `Vulkan0: NVIDIA RTX 4060 Laptop (7956 MiB)` 与 `Vulkan1: AMD Radeon(TM) Graphics (32602 MiB, 共享内存)`。
- **根因**：本机是 Ryzen 9 7845HX（含 Radeon 核显）+ 独显的双 GPU 配置。不指定 `--device` 时，
  负载可能落到核显上——**不报错，只是慢**。
- **修复**：① 配置显式 `device: "Vulkan0"`；② 适配器 `start()` 里用 `--list-devices`
  **反查该索引背后的物理设备名**，不含 "NVIDIA" 就直接抛错（fail fast）；③ 断言层再校验一次。
- **性质**：**典型静默错误**。若不做这层校验，可能会得到一组"看起来合理、实际是核显"的性能数据，
  并据此做出完全错误的选型结论。

#### 坑 2：build 10951 的路由表不稳定，`/health` 返回 404
- **现象**：适配器按常规打 `/health` 做就绪探针、`/v1/chat/completions` 发请求，
  结果请求返回 `404 {"error":{"message":"File Not Found","type":"not_found_error"}}`。
- **诊断过程**（不猜，逐步收敛）：
  1. 先怀疑端口被占（Windows 上 `SO_REUSEADDR` 允许重复绑定）→ 查 `netstat`：8080 无监听者，**排除**。
  2. 读取**服务端日志**：只有 2 个 POST 真正到达模型，说明被 404 挡掉的请求**根本没进入推理**；
     响应体是"静态文件兜底 handler"的文案，即**该路由在此 build 上不存在**。
  3. 做**对照实验**：用与适配器完全相同的参数在不同端口重探 → 路由表一致，
     确认 `/props` 稳定 200、`/health` 稳定 404。
- **修复**：
  ① 就绪探针改用 `/props`，并校验响应体含 `default_generation_settings`
     （这同时是"我们确实在和 llama.cpp 说话"的交叉信源证据）；
  ② 适配器改为**路由自发现**：按候选列表探测，命中即缓存，并把 `chat_route` 写进引擎指纹，
     便于他人复核"到底打的是哪个端点"。
- **为什么不硬编码**：正因为它在不同启动中表现不一致，硬编码某一条会随 build 变化而失效。

#### 坑 3：矩阵中的 `${paths.*}` 占位符未展开（**运行前静态检查抓到的**）
- **现象**：`--list` 打印出的 overrides 是字面量 `"${paths.models_gguf}/xxx.gguf"`。
- **根因**：bench 的顺序是「先 `load_engine_config`（此处替换占位符）→ 再 `apply_overrides`」，
  于是矩阵里的占位符**永远轮不到被替换**。
- **危害**：不会报错，只会以"文件找不到"的形式在更晚的阶段暴露，根因却被掩盖。
- **修复**：矩阵加载后**显式**再替换一次（`src/engines/__init__.py::substitute_paths`）。
- **收获**：`--list` 这类"只读不跑"的入口价值很高——它让这个 bug 在下载任何东西之前就暴露了。

## 【⑤ 面试延伸】

### Q1. 同模型同参数，换个引擎快 5–6 倍，差距从哪来？你怎么证明？

**答题骨架**
1. **先给结论再给证据**：瓶颈是**框架开销**，不是带宽也不是算力。
2. **证据链**：
   - 若纯带宽受限，预期提升 = `权重体积之比` = `4.25 GB / 1.20 GB` ≈ **3.5×**；
   - **实测 5.2–6.6×，超过了带宽能解释的上限** → 说明另有一块时间被消除；
   - 那块时间就是：**Python 逐 token 循环 + 每个 step 多次 kernel 派发**（C++ 实现直接消除）。
3. **反向验证**：如果瓶颈是带宽，那么**量化收益应该与吞吐收益成正比**；
   但我们看到 prefill（TTFT）**几乎没变**，只有 decode 变快 —— 与"decode 是 memory-bound、
   量化减少访存字节数"的机理一致。

**追问方向**
- *"那你原来算的 40.5% 带宽利用率是不是错的？"* → 不算错，但**容易被误读**。
  它只说明"没有达到带宽上限"，**不能反推"瓶颈就是带宽之外的东西"**。
  正确的用法是把它当**上界参考**，再通过"换实现"和"换精度"两个正交实验去定位。
- *"怎么进一步证明？"* → ① 用 profiler 看 kernel 之间的空隙（CPU 派发等待）；
  ② 对比 `batch=1` 与 `batch>1` 的吞吐曲线；③ 加 CUDA Graph 看小 batch 是否变快。
- *"P99 为什么比均值改善更多？"* → 均值受稳定的 decode 速率主导；P99 还包含调度抖动与
  内存分配抖动。C++ 引擎的分配与调度更稳定，所以**长尾改善幅度更大**。这也说明：
  **只报均值会低估引擎差异对用户体验的影响。**

**加分回答**：主动说"我先算了带宽能解释的上限，再用实测去对比它"——
**用推算值给实测值设一个参照系，而不是拿推算值当结论**。

### Q2. 你的数据里 TTFT 几乎没变，这说明了什么？

**答题骨架**
1. **TTFT 由 prefill 决定**，prefill 是 **compute-bound**（大矩阵乘 + O(L²) 注意力）。
2. **量化只减少权重字节数（访存），不减少计算量** → 对 compute-bound 的 prefill 收益有限。
3. **本项目的实测正好印证**：`text_short` TTFT 0.045s vs 0.045s（持平）；
   `vl_rdmap` 甚至从 0.106s 退化到 0.120s（llama.cpp 略慢，可能与其视觉编码器实现有关）。
4. **工程推论**：**RAG 场景的 TTFT 优化不能靠量化**。要做的话得用：
   前缀缓存（system prompt + 检索模板固定）、Chunked Prefill、减少 chunk 数/长度。

**追问方向**
- *"那 RAG 的 TTFT 一般多少算可接受？"* → 交互式问答通常希望 < 1s 首字；本项目实测远低于此，
  因为 prompt 短（14–220 token）。**真正的压力来自 P4 挂上检索后的 1500–2500 token 上下文**，
  那时 TTFT 会显著上升，是 P7 要实测的重点。
- *"为什么 VL 用例的 TTFT 更高？"* → 视觉 token 使 prefill 长度从 ~17 涨到 220（+196 视觉 token），
  且视觉塔本身要前向一次。

**加分回答**：把"延迟拆成 TTFT 与 decode"这个习惯本身讲出来——
**不拆开的延迟数字无法指导优化**，因为你不知道钱该花在 prefill 还是 decode 上。

### Q3. 你怎么保证跨引擎对比是公平的？这次有没有不公平的地方？

**答题骨架（主动暴露自己的瑕疵，是最强的加分项）**
1. **做对的地方**：
   - 两个 run 的 `overrides` 都是空 `{}` → 唯一变量是引擎；
   - 同一批 prompt、同 `max_new_tokens`、同为贪心解码、同 seed；
   - 每次测量 1 次预热 + 3 次计时，报均值与波动；
   - 显存用同一种采样方式（`nvidia-smi` 设备级）。
2. **必须承认的不公平（本次真实存在）**：
   - **输出长度不一致**：`text_open` 上 HF 写 974 token，llama.cpp 只写 465（−52%）。
     所以 **E2E 的 ×13.8 不能当作纯引擎加速**（它混合了"更快"与"更短"两个因素）。
     处置：另外报告 **tok/s**（速率，已归一），并显式声明这一点。
   - **量化本身也是一个变量**：严格说 E1 同时改了"引擎"和"精度"。
     要分离两者，需要加"llama.cpp 跑 F16 GGUF"或"HF 跑 4-bit"的对照 —— 归入 E2。
   - **后端不同**：winget 装的是 **Vulkan** 后端，不是 CUDA。同引擎不同后端也值得单列一组。

**追问方向**
- *"为什么不干脆强制两边输出同样长度？"* → 可以通过 `min_new_tokens` 或忽略 EOS 来强制，
  但那样测的是"生成固定长度文本的速率"，**偏离真实使用**。更好的做法是**两个口径都报**：
  速率用 tok/s，体验用 E2E，并说明差异来源。
- *"3 次重复够吗？"* → 对**稳态吞吐**够（实测波动 0.6–5.5%）；
  但要看**热节流**的影响需要更长窗口 —— 笔记本 GPU 有 95W 功耗墙，长任务必然降频。

**加分回答**：主动指出"**我这次 E1 其实同时改了两个变量**（引擎 + 量化），
下一步会用 F16 GGUF 补齐对照"——**自己能指出实验设计的漏洞，比报一个漂亮数字可信得多**。

### Q4. 量化后模型的视觉描述从"三个斑点、圆形、高斯分布"变成"三条曲线、椭圆形"，你怎么看？

**答题骨架**
1. **先分类**：粗粒度事实（数量 3、轴标签、轴范围）**全部保住**；
   细粒度形态描述**退化**。
2. **为什么会这样**：视觉特征经 ViT → merger → 注入 LLM。Q4_K_M 量化的是**语言侧**权重，
   退化发生在"用语言描述视觉特征"这一步——**是表达能力下降，不是感知错误**。
   模型仍然"看到了三个亮斑"（数量对），但用来描述形状的词汇分布被量化扰动，
   漂移到了"曲线/椭圆"这种更泛化的表述。
3. **工程处置**：
   - 把"形状/分布"纳入回归判据（当前 `required_terms` 粒度太粗，放过了这个退化）；
   - 视觉敏感的任务可以考虑 **mmproj 用 F16 而不量化**（正是 E3 要测的）；
   - 若形态描述重要，可能需要**提高量化等级**（Q6_K / Q8_0）。

**追问方向**
- *"为什么不用困惑度评估量化掉点？"* → 困惑度在这类任务上不敏感：
  它衡量"预测下一个 token 的平均难度"，而"圆形"和"椭圆形"都是高频词，
  困惑度不会区分哪个是正确答案。**必须用任务级、且真值已知的判据**。
- *"你怎么确定是量化造成的，不是两个引擎的 prompt 模板差异？"* → 这是个好问题，**我目前不能确定**。
  要分离，需要跑"llama.cpp + F16 GGUF"（同引擎、同模板、只改精度）。
  这也是当前报告的**已知局限**，已写入待办。

**加分回答**：承认"**我这条结论还不能归因到量化**，因为引擎和精度同时变了"——
这比强行给一个解释更专业。

### Q5. RAG 场景下你会怎么用这套结论？

**答题骨架**
1. **decode 侧**：换 llama.cpp + Q4_K_M 拿到了 6× 吞吐与 7.5× 的 P99 改善，
   这意味着**单机能支撑的并发交互数大幅上升**（或同等交互下功耗更低）。
2. **prefill 侧**：TTFT 没改善，而 RAG 的 prompt 会从 ~20 token 涨到 1500–2500 token，
   **那时 TTFT 会成为主要成本**。对策：前缀缓存（检索模板与 system prompt 固定）、
   控制 chunk 数与长度、必要时上 Chunked Prefill。
3. **显存侧**：设备级峰值从 5905 MiB 降到 4777 MiB，省下的 1.1 GiB 可直接换成
   **更长的上下文或更多并发**（KV Cache 需 112 KiB/token，1.1 GiB ≈ 1 万 token）。
4. **质量侧**：粗粒度检索问答应该安全；若涉及图表形态判断，需再评估量化等级。

**追问方向**
- *"为什么说前缀缓存对 RAG 特别有效？"* → RAG 的 prompt 结构是
  `[system 指令][检索模板][N 个 chunk][用户问题]`，前 3 段在多轮/多请求间**高度重复**，
  复用其 KV 可跳过大部分 prefill → 直接降低 TTFT。

**加分回答**：把结论落到**具体数字**上（1.1 GiB ≈ 1 万 token 的 KV），
而不是笼统说"显存更省了"。
