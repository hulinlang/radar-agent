# 阶段 B · B11 详细方案：prefill 的 GEMM 级性能（int8 激活 + dp4a）

> 状态：**已实施**（2026-10-11）。数值方案 B 已确认并落地；D1/D2 达成，
> **D3（≥1000 tok/s）未达成且已用实测证明 dp4a 路线到不了** —— 见 §7.1。
> 前置：B10 已收官（分页 KV + 跨请求前缀复用，`docs/33`）。
> 位置：`docs/27` §4 遗留表 —— **唯一一个"关掉未达标 DoD"的候选**。

## 0. 为什么做这一项

### 0.1 它关掉的是一个**未达标**的 DoD

`docs/29` §7.1 的验收表里，B8 的 DoD#2 写的是「⚠️ **部分达成**」：

| DoD | 目标 | 实测 | 判定 |
|---|---|---|---|
| prefill 正确 + **≥1000 tok/s** | ≥1000 tok/s | **567–616 tok/s**（相对逐 token 是 4.8–5.3×） | ⚠️ 部分达成 |

其余六项 DoD 都是 ✅。也就是说 **B8 留下了一个明确没做到的目标**，而 `docs/29` §7.3
当时就给出了根因与生产答案：

> fp32 精确 dequant 多列 kernel 是**指令发射 bound**，生产答案是 **dp4a/MMQ**，另立项。

### 0.2 P11 已经把"为什么上不去"量化了

`reports/P11_Roofline性能模型.md` §4（独立于 B11 立项的建模）给出：

| prompt T | 实测 tok/s | 算力屋顶 tok/s | **利用率** |
|---|---|---|---|
| 132 | 612 | 3749 | **16.3%** |
| 572 | 616 | 3747 | **16.4%** |
| 1280 | 568 | 3744 | **15.2%** |

即 **prefill 只跑到算力屋顶的 16%** —— 而且三个长度上几乎恒定。
恒定这件事本身就是证据：**瓶颈不是访存、也不是长度，而是每字节权重要花掉的指令数**。

`docs/28` §2.2 的账更能说明问题：Q4_K 一个 super-block 是 **144 B**，
纯访存口径的预算是 **~0.66 μs**，而 unpack 256 个 nibble（shift/and/查 scale/乘加）
的整数运算串行度吃掉了余量 —— 我们用的是 **fp32 精确**路线，指令数比 dp4a 高一个量级。

### 0.3 参照系是存在的（本方案开工前刚核实）

曾经担心的问题是"没有 int8 激活的参照可对拍"。核实后**恰恰相反**：

| 路径 | 激活 | 证据 |
|---|---|---|
| llama.cpp **CUDA** Q4_K **decode** | **Q8_1** | `ggml/src/ggml-cuda/mmvq.cu:38` `vec_dot_q_cuda_t(const void*, const block_q8_1*, ...)`；`vec_dot_q4_K_q8_1` |
| llama.cpp **CUDA** Q4_K **prefill**（小批） | **Q8_1** | MMQ 用 `block_q8_1_mmq`；`ggml_cuda_should_use_mmq` 在 `ne11 < MMQ_DP4A_MAX_BATCH_SIZE` 时为真 |
| llama.cpp **CPU** Q4_K | **Q8_K** | 项目文档里"Q8_K"说法的来源 |

⇒ **llama.cpp 的 CUDA Q4 路径一直在量化激活**；我们那条 **fp32 精确反量化**路线才是这条对拍里的"异类"。
所以 B11 不是在"发明一条无法验证的路线"，而是**向参照靠拢**。

> ⚠️ 由此**订正一处文档错误**：`docs/27` §3 第 4 条与 `docs/28` §2.2 写「Q4_K×Q8_K」，
> CUDA 路径实际是 **Q8_1**（Q8_K 是 CPU 路径）。方向性结论（"激活也量化"）没错。

## 2. 现状与数据（已核实源码）

### 2.1 我们现在的 prefill 路径

`cpp/src/gpu_model.cu`：

- **多列 gemv**（`gemv_*_mc`，`MAX_MC = 16`）：权重读一次、算 16 列。
- Q4_K/Q6_K 走 `gpuq::gemv_q4k/gemv_q6k`（`gpu_quants.cu`）：**fp32 精确反量化**后与
  fp32 激活做浮点点积。
- 整套验收建立在"**每个优化都必须过同一份对拍**"上（`docs/27` §2），
  B8a 的多列 kernel 与逐 token 路径是 **id-identical** 的（`test_b8` 的
  `B8a batch-prefill parity (4 lengths, id-identical)`）。

### 2.2 为什么 fp32 激活上不去

- 每读 144 B 的 Q4_K super-block，要做 **256 个 nibble 的 unpack**（shift/and/查 scale/乘加），
  而 dp4a 一条指令吃掉 4 个 int8 MAC ⇒ **指令数差约一个量级**。
- P11 的实测证实：三个 prompt 长度上利用率恒为 **~16%**（与长度无关 ⇒ 非访存问题）。

### 2.3 要改的边界

| 组件 | 现在 | B11 之后 |
|---|---|---|
| Q4_K/Q6_K **prefill** | fp32 激活 + 精确反量化 | **int8 激活 + dp4a**（目标） |
| Q4_K/Q6_K **decode** | fp32 激活（B7 已验证 102%/86%） | **不动**（见 §3.1） |
| **F16** 路线（prefill + decode） | fp32 激活 | **不动** |

## 3. 设计

### 3.1 ⭐ 范围控制：int8 激活**只用于量化路线，且只改 prefill**

这一条是本方案能否保住既有验收的关键，必须写在最前面：

1. **只在量化（Q4_K/Q6_K）路线上启用 int8 激活**。F16 权重 + fp32 激活本来就是自然的 F16 路线，
   没有理由动它。⇒ **`test_b4`（F16，440/440 逐 id 对拍）完全不受影响**。
2. **只改 prefill，不改 decode**。理由：decode 是**带宽受限**（P11 §0：AI≈1.0 vs 转折点 59.3），
   它的瓶颈是"读多少字节"，不是"每字节多少指令" —— 换 int8 激活对 decode 收益近零，
   却会**改变 decode 数值**、破坏 B7/B10 已建立的验收（40.4/62.5/119.4 那套数字全部作废）。
3. 于是受影响的验收只剩"同样改动的两次运行相比"那几条，它们**自动仍然成立**：
   - `test_b7` 本身就是 teacher-forcing（异路线），不要求 bit-exact
   - `test_b8` 的 `B8a parity` 比的是批量 prefill vs 逐 token —— 两条都走新路径
   - `test_b9` 的 LCP 逐字节、`test_b10` 的"池大小不改变输出"同样都是自比

> ⚠️ **会变的那个数字**：`docs/30` §6.3 与 `python scripts/p9_compare_radarinfher.py` 那条
> 「22 题 vs llama-server **Δ=+0.0000**」是在 Q4 上测的。改了 prefill 数值口径后**必须重测**，
> 并如实报出新的 Δ（预期不再是 0.0000）。**这是 D4 的一部分，不是回归失败。**

### 3.2 数值方案（**已定：B**，2026-10-10 确认）

三种候选，差别在"激活怎么量化"：

| 方案 | 做法 | 与 llama.cpp CUDA 的距离 | 代价 |
|---|---|---|---|
| **A. per-32 对称 int8** | 每 32 个激活一组，`scale = amax/127`，int32 dp4a 累加，组末乘回 `w_scale*a_scale` | 中（Q8_1 是**每 32 元素带 `d` 与 `s`** 两项，我们只带 `d`） | 实现最简 |
| **B. 对齐 Q8_1** | 每 32 元素带 `d`（缩放）与 `s`（元素和，供 w 的 offset 项用），与 llama.cpp 同构 | **最近** ⇒ D2 的一致率应最高 | 多一个 `s` 项；需要处理 Q4_K 的 `dmin` 偏置项 |
| **C. per-128/per-superblock** | 按 Q4_K 的 super-block 粒度量化激活 | 远（llama.cpp 是 per-32） | 精度更差但更省 |

**推荐 B**：`docs/28` §6.3 的整段分析都建立在"与我们对比的 llama.cpp 是同一条 Q4_K×Q8_1 路线"上，
选 B 才能让 D2 的"一致率应上升"成为一个**干净的可证伪判据**；选 A/C 则一致率的变化会被
"块大小不同"这个额外变量污染。

#### 3.2.1 方案 B 的确切语义（实现前先钉死，D1 层①对拍的就是它）

激活量化**逐 32 个连续值一组**，与 llama.cpp CUDA 的 `quantize_q8_1` 逐句对齐
（`ggml/src/ggml-cuda/quantize.cu:54`）：

```
amax = max_l |x_l|                         (fp32)
d32  = amax / 127.0f                       (fp32)
q_l  = (amax == 0) ? 0 : roundf(x_l / d32) (int8, round-half-away-from-zero)
d    = float(half(d32))                    ← 下游实际使用的 d
Σq   = Σ_l q_l                             (int32, 精确)
```

⚠️ **复刻一处 llama.cpp 的固有细节**：llama.cpp **用 fp32 的 `d32` 去量化**，
但**存进 block 的 `d` 是 fp16**，而 dot 里用的是**那个 fp16 的 `d`**。
我们照做 —— 这正是"对齐 Q8_1"的含义；换成全程 fp32 的 `d` 会更准但会偏离参照。

激活块布局（本项目的定义，**不**照抄 llama.cpp 的 36 B 块）：采用 **split**
（连续 int8 + 独立的 8B 尺度记录），与 llama.cpp MMQ 的
`block_q8_1_mmq` + `ds8` 同形，两半都能 16B/32B 对齐 —— 这是 `uint4` 装载的前提：

```c
struct Q8_1Ds {          // 8 B
    float   d;           // = float(half(amax/127))，dot 里实际用的缩放
    int32_t sum_q;       // = Σ q_l，精确整数
};
// 量化值：块主、列最内（⚠️ 必须，理由见 §7.2）
//   qs[block * ncol * 32 + c * 32 + lane]
//   ds[block * ncol + c]
```

> 为什么用 `int32 sum_q` 而不是 llama.cpp 的 `half s`：mmvq 路径的 offset 项本来就是用
> **dp4a 现算** `Σq`（`0x01010101` 与被量化的激活做 dp4a，见 `vecdotq.cuh:520`），
> 所以存精确整数**与参照同值**，还省掉 kernel 里的一次 warp 归约。

> ⚠️ `Σq` 的归约是**集合操作**：`__reduce_add_sync` 必须整个 warp 一起调用。
> 第一版把它写在 `if (lane == 0)` 里，静默返回垃圾，D2 直接 0/50（§7.4）。

权重侧的贡献式（Q4_K，逐 super-block、逐 sub-block，`j` 升序）：

```
sumf_d_b = Σ_j  f32(d8[b*8+j]) * f32(dot1_j * sc_j)      // dot1_j = Σ_l nib_l*q_l (int32)
sumf_m_b = Σ_j  f32(d8[b*8+j]) * f32(dot2_j * m_j)       // dot2_j = Σ_l q_l = sum_q (int32)
part_b   = f32(d4) * sumf_d_b - f32(dmin) * sumf_m_b
y        = Σ_b part_b                                     // b 升序累加
```

Q6_K 同构，只是"scale 组"是 **16 个值**（`sc` 为 int8，`q ∈ [-32,31]`）：

```
sumf_b = Σ_g f32(d8[block(g)]) * f32(sc_g * dot_g)       // dot_g = Σ_{16} q6_l*q8_l
part_b = f32(d6) * sumf_b
y      = Σ_b part_b
```

**浮点运算一律显式 round-to-nearest 的"先乘后加"**（CUDA 侧用 `__fmul_rn`/`__fadd_rn`
禁止 FMA 收缩），这样 NumPy 的 `a*b + c`（float32）能与之**逐位一致** —— B5 的
3.3 亿值逐位 EXACT 就是这么做的。

**累加顺序即判据**：NumPy 参考与 kernel 必须用**同一个括号化**；D1 要求逐位相等，
"顺序不同所以差一点"不被接受（否则层①就失去了定位能力）。

### 3.3 kernel 形态（已按实测定档）

- **prefill 主路径**：`gemv_q4k_q8_1_kernel<RW, NC, LC>`，warp tile = **2 行 × 16 列**
  （`RADAR_B11_TILE` 可换，见 §7.3），lane = *(row, column)*，**每个 lane 独占一个
  输出并走完整个 k**。这样做的三个理由：
  1. **完全不需要跨 lane 归约**（SM89 的 shuffle 吞吐只有 FMA 的 ~1/4，逐列归约会
     把收益吃光）；
  2. 一个 warp 只碰 **2 个**权重行地址 ⇒ 16 条 lane 对同一地址**广播**，权重 DRAM
     流量仍是 1×；
  3. fp32 部分的括号化与参考实现**逐字相同**（super-block 升序、sub-block 升序），
     这才让层①能要求"逐位相等"而不是"差不多"。
- 权重侧读 **`uint4`**：一个 32B 的 qs 组同时供 sub-block `2g`（低半字节）与
  `2g+1`（高半字节），2 次装载出 64 个值。
- 激活量化是独立 kernel（一 warp 一组 32 值），每 chunk 内被 16 列复用，摊薄后约占
  gemv 时间的 5%。
- 浮点一律 `__fmul_rn`/`__fadd_rn`，**禁止 FMA 收缩**（nvcc 默认 `-fmad=true`）。
- Q6_K **仍走 fp32 路径**：原计划"Q6_K 同法"，但 Q4_K 的实测收益（1.5×）已由 §7.1
  的 2.00× 上限解释，再花一个工作段做 Q6_K 也只能把整条 prefill 推到 ~690 tok/s，
  仍达不到 1000 ⇒ 收益不足，留待 MMA 阶段一起做。
- **MMA（int8 tensor core）不在本阶段**（§6），但 §7.1 证明它是达标的唯一出路。

### 3.4 ⭐ 三层对拍方法论（本方案的核心，因为它换的是**数值路线**）

> 背景：`docs/27` §2 的方法论是"每个优化都必须过同一份对拍"。但**换数值路线**时，
> "与 llama.cpp 逐 id 相同"在数学上不再可能（块大小、舍入、累加顺序都不同）。
> 项目在 B5/B7 已经处理过一次这种情况（换成了 teacher-forcing）。这里把方法固定成三层：

| 层 | 比什么 | 能否 bit-exact | 判据 | 项目先例 |
|---|---|---|---|---|
| **① 路由内自证** | CUDA kernel ↔ **独立的 NumPy 参考实现**（我们自己的 int8 语义） | ✅ **能** | 逐元素一致（浮点部分 bit-exact，量化部分 EXACT） | B1 GGUF 双实现逐字节；B5 反量化 自研 vs libggml **3.3 亿值逐位 EXACT** |
| **② 路由间对齐** | 与 llama.cpp CUDA（Q8_1）的 teacher-forcing 一致率 | ❌ 不可能 | **≥ 49/50**（不低于 fp32 激活路线）。⭐ 两边都量化激活 ⇒ 距离应变小；**若下降就是我们的 bug** | B5/B7 的 49/50 |
| **③ 质量代价** | 22/200 题、口径 v3，与 fp32 激活路线对照 | — | 报**退化量**（不设硬阈值，由你判断是否可接受） | 量化退化 **−0.035**（`docs/19`） |

**为什么①必须存在**：②③都只告诉你"偏了多少"，只有①能告诉你"偏在哪里"。
而①成立的前提是"把语义写清楚两遍"（一次 Python 一次 CUDA）—— 这恰好是本项目最擅长的验证形态。

### 3.5 A/B 开关（让性能与质量都能同 session 配对）

新增环境变量 `RADAR_Q4_FP32_ACT=1`：**强制走旧的 fp32 激活路径**。
⇒ 新旧两条路可以在**同一次 session 内交替跑**，满足 §5.9 的"配对测量"要求，
也是 D3 与 D4 的测量前提（`RADAR_NO_PREFIX_CACHE` 在 B10b 已经用过这个模式）。

## 6. 明确不做（防范围蔓延）

- **decode 路径的 int8 激活**（§3.1 第 2 条：decode 是带宽受限，收益近零、代价是作废全部既有 decode 验收）。
- **F16 路线的激活量化**（无意义，且会破坏 `test_b4` 的 440/440）。
- **int8 tensor core（MMA）**：先做 dp4a；MMA 作为 D3 未达标时的后手，不预先并入。
  → **D3 未达标，且 §7.1 已证明 dp4a 不可能达标**，所以 MMA 就是下一步（建议 B12），
  但它要处理 fragment 布局 / `ldmatrix` / 累加器摆放，是独立的工作段，不塞进本阶段。
- **Q6_K 的 int8 路径**：原计划做，实测后**刻意不做** —— Q4_K 的收益已被 2.00× 上限封顶，
  Q6_K 顶多把整条 prefill 推到 ~690 tok/s（§3.3），不够达标，收益不抵一个工作段。
- **KV 量化**（`docs/33` §10.3 已定性：另一条改数值口径的路线，另立项）。
- 权重侧的进一步量化（Q3/Q2）：与本项无关，且 8 GiB 下没必要。

### 7.1 ⭐ D3 为什么到不了 1000：dp4a 的 2.00× 管道上限（实测，不是推断）

新增 `cpp/tests/b11_roof.cu`，用 **8 条独立链**测两条指令流的**吞吐**（不是延迟）。
两个数字必须分开看 —— **管道上限**由硅片决定，**实测比值**是这段代码从管子里取到了多少：

| | 实测吞吐 | 每指令 MAC | 实测 MAC 吞吐 |
|---|---|---|---|
| `fmaf` | 129–196 G warp-instr/s | 1 | 6.3–7.9 T MAC/s |
| `__dp4a` | 65–76 G warp-instr/s | 4 | 9.7–14.9 T MAC/s |
| **实测比值** | | | **1.55–2.00×** |

- **管道上限 = 2.00×**：Ada 消费卡每 SM 有 **64 条 INT32 通道 vs 128 条 FP32 通道**，
  dp4a 每条吃 4 个 int8 MAC ⇒ (64×4)/(128×1) = **恰好 2.00×**。这个数与访存、tile、
  occupancy 全无关。
- **实测比值 1.55–2.00×**：它随 clocks 与调度浮动（我们的 dp4a 微基准取到 INT32 管道
  峰值的 ~61%，fma 取到 FP32 峰值的 ~78%）。**所以工程天花板在 1.5–2.0× 之间，
  而不是稳定贴着 2.0×。**

> ⚠️ **2026-10-11 订正：一个 flaky 断言（以及为什么分母选错了）**
>
> `test_b11.sh` 第 3 段原本断言 `实测比值 <= 2.06`，依据就是上面的"1.55–2.00×"。
> 2026-10-11 的复跑在**未改动任何相关代码**（`b11_roof.cu` 一个字节都没碰）的情况下
> 取到 **2.17×**，断言失败。
>
> 根因是**分母选错了**：这个商的分母是**实测 fma 速率**，而 fma 探针本身欠饱和
> （寄存器 bank 压力 + 循环开销 ⇒ 只有标称 128 MAC/SM/clk 的 ~81–89%）。用它作分母，
> 商**可以合法地超过 2.00×** 而不违反硅片上限 —— 因为 **2.00× 是相对标称 128
> 定义的**。两次之差（2.00 vs 2.17）还叠加了本机 ~15% 的漂移（见下方"绝对值口径"）。
>
> **修正**：① `b11_roof` 的输出明确标注分母是**实测** fma，并写明商可超过 2.00×；
> ② 断言改为只卡一个 **1.5–2.6×** 的合理带（仍能抓到探针坏掉），把实测值当**证据**
> 记录，而不是当**闸门**。
>
> **教训（与 §7.3 同源）**：微基准的**比值**是 session 相关的量，不能拿来卡硬件常数。
> 一个 flaky 的验收断言比没有断言更糟 —— 它会训练你忽略失败。

把它代进整条 prefill 的账（T≈1645，每 chunk 16 token，同一 session 的一组）：

| 配置 | gemv | attention | 合计 | tok/s |
|---|---|---|---|---|
| fp32 激活（基线） | 29.2 ms | 5.7 ms | 34.9 ms | **459（实测）** |
| int8 dp4a 实测（tile 2x16） | ~17 ms | 5.7 ms | 22.9 ms | **701（实测）= 1.53×** |
| int8 dp4a **打满 2.00×** | 14.6 ms | 5.7 ms | 20.3 ms | **788（理论上限）** |
| 要达到 1000 tok/s | ≤ 10.6 ms | 5.7 ms | 16.0 ms | 需 gemv = fp32 的 **2.75×** |

**结论**：1000 tok/s 需要 gemv 比 fp32 快 **2.75×**，而 **dp4a 的管道上限是 2.00×**
（实测只到 1.53×）⇒ **B11 按原范围（dp4a）不可能达标，且这不是调优问题**。
`docs/34` §5 风险表当时写的应对（"下一步是 MMA（int8 tensor core）"）**正是唯一出路**：
MMA 的 INT8 吞吐是向量单元的 4–8×，余量足够。MMA 不在本阶段范围（§6 明确不做），
应另立项（建议 B12）。

> ⚠️ 一处**方向性估算的订正**：`docs/27` 遗留表原来写"dp4a 预估上限 ~150–200 GB/s"，
> 把瓶颈归给了**访存**。实测表明瓶颈是 **ALU 通道数**（指令吞吐），与带宽无关 ——
> 权重流式只有 **0.035 B/MAC**，离带宽墙差一个数量级。这条已作为"估错方向"的实例回填 `docs/27`。

> **绝对值口径**：本 session 整机比录制 568–616 tok/s 的那次慢约 15% —— 同一
> session 内两条独立证据同幅下降：llama.cpp **decode** 132.23 → 113.17 tok/s
> （−14.4%），自研 113.28 → 96.38（−14.9%）。所以 D3 的判定只以**同 session
> 配对比值**为准（§5.9）；而无论取哪一次 session 的绝对值，**1.5× 与 2.0× 上限
> 都翻不到 1000**。

### 7.2 实测教训一：激活布局必须是"块主、列最内"

第一版把激活按 `[ncol][k]`（列主）排：一次 warp 的 uint4 装载要碰 **16 条**
128B cache line（每列一条，列间相隔 2 KB）。实测 **net 2.4× 变慢**（262 vs fp32
的 407 tok/s）—— 比 fp32 还慢。

改成 `[k/32][ncol][32]`（一个 32 值块的 16 列**连续**排布）后，同样一次装载只碰
4 条 line ⇒ 变成 1.5× 快。

### 7.3 实测教训二：tile 不能用孤立 bench 选

`gemv-bench` 连打同一个 7 MB 矩阵 200 次 ⇒ **L2 常驻**，它给出的最优 tile 是
`4x8`；引擎每次 chunk 流式读 ~900 MB（无复用），**引擎内配对 A/B** 给的答案是
`2x16`：

| tile | 引擎 prefill（T=1645，两次 session 的 3 轮中位） |
|---|---|
| 8x4 | 460 / 528 tok/s |
| 4x8 | 538 / 644 tok/s |
| **2x16** | **575–602 / 701 tok/s（采用）** |
| 16x2 | 328 tok/s |

（两次 session 整体差 ~15%，见 §7.1 的绝对值口径；**tile 的排序两次完全一致**，
这才是定档的依据。fp32 基线同两次为 400–417 / 459 tok/s。）

⇒ 定档 `2x16`，并保留 `RADAR_B11_TILE=RxC` 作为可复现的测量旋钮。
**只有引擎内的配对 A/B 算数**；孤立 bench 只能用来定位访存形态，不能用来选参数。

### 7.4 ⭐ 实测教训三：层①当时漏掉了一个 bug（方法论缺口）

第一次接进引擎后 D2 = **0/50**（完全没有命中），而层①是**全绿**的。

根因：`quantize_q8_1_kernel` 把集合操作 `__reduce_add_sync` 写在了 `if (lane == 0)`
里面。它要求掩码内**所有 lane 一起执行**，只让 lane 0 调用是未定义行为 ——
静默返回垃圾。而 `sum_q` 正是 Q4_K 的 **offset 项**（`dmin*m*Σq`），
一项错就整行错 ⇒ 整个 prefill 解码成乱码（每个 prompt 的首 token 都是同一个）。

**层①为什么没抓到**：当时的 `int8-ref-test` 喂给 CUDA gemv 的是**参考文件里 host
量化好的**激活，而**引擎走的是 CUDA 量化器** —— 两个 pass 里有一个从来没被对拍过。

已补：`int8-ref-test` 现在**逐字节**校验 CUDA 量化器的 `qs` 与 `ds`
（§7.4 表格里的 "cuda quantize_q8_1 EXACT"）。修好后 D2 从 0/50 → 49/50。

> **教训（可迁移）**：层①的正确性主张是"**kernel ↔ 独立参考**逐位一致"，
> 但 kernel **真正执行的那些 pass 必须逐个覆盖**。少对一个 pass，层①就会给出
> 一个**虚假的绿灯**，而它恰恰是三层里唯一能定位"错在哪"的一层。

### 7.5 D4 质量代价

#### (a) 逐 id 自比：**完全一致**

同 session 内对 B7 的 5 条 prompt 跑两条路（int8 vs `RADAR_Q4_FP32_ACT=1`）：
输出 id **完全一致**；teacher-forcing 也是同值 49/50。

#### (b) ⭐ logits 位移：把"一致"变成**数字**（`cpp/tests/b11_logit_delta.sh`）

"id 相同"是个没有分辨率的 yes/no —— 它不告诉你差多远。真正决定会不会翻的是
**扰动 vs top1−top2 间距**。为做这一测，本次给 CUDA 路径补上了
`RADAR_DEBUG_TOPK`（原先只有 CPU 路径有），每步 dump top-5。

5 条 prompt × 41 步 = **205 步**，两条路逐步对齐：

| prompt | steps | max\|Δtop1\| | max\|Δmargin\| | int8 最小间距 | fp32 最小间距 | 翻转 |
|---|---|---|---|---|---|---|
| p1 | 41 | 0.0555 | 0.0820 | **0.0048** | 0.0046 | 0 |
| p2 | 41 | 0.0801 | 0.0449 | 0.0570 | 0.0579 | 0 |
| p3 | 41 | 0.1170 | 0.0998 | 0.0968 | 0.0964 | 0 |
| p4 | 41 | 0.1809 | 0.1175 | 0.3104 | 0.2218 | 0 |
| p5 | 41 | 0.0650 | 0.1103 | 0.0896 | 0.0728 | 0 |

**怎么读**：
- int8 把 top-1 的**绝对分数**挪动了 ≤ **0.18**；
- 但把 **top1−top2 间距**只改变了 ≤ **0.12** —— 扰动是**相关的**（候选们一起动），
  所以绝对位移大、相对排序稳。**判据是间距，不是绝对位移。**
- ⭐ p1 里存在一个间距只有 **0.0048** 的**近似并列**步（比 B5 里那个 0.016 的并列更紧），
  两条路线都选了**同一个** token，且间距几乎没变（0.0048 vs 0.0046）。
  这是"这次换数值路线没有碰到排序"最直接的证据。
- **205 步 0 次翻转**。
