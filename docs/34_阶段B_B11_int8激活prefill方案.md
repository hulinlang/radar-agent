# 阶段 B · B11 详细方案：prefill 的 GEMM 级性能（int8 激活 + dp4a/MMA）

> 状态：**方案待确认**（2026-10-10）
> 前置：B10 已收官（分页 KV + 跨请求前缀复用，`docs/33`）。
> 位置：`docs/27` §4 遗留表 —— **唯一一个"关掉未达标 DoD"的候选**。

## 0. 为什么做这一项

### 0.1 它关掉的是一个**未达标**的 DoD

`docs/29` §7.1 的验收表里，B8 的 DoD#2 写的是「⚠️ **部分达成**」：

| DoD | 目标 | 实测 | 判定 |
|---|---|---|---|
| prefill 正确 + **≥1000 tok/s** | ≥1000 tok/s | **567–616 tok/s**（相对逐 token 是 4.8–5.3×） | ⚠️ 部分达成 |

其余六项 DoD 都是 ✅。也就是说 **B8 留下了一个明确没做到的目标**，而 `docs/29` §7.3
当时就给出了根因与生产答案：

> fp32 精确 dequant 多列 kernel 是**指令发射 bound**，生产答案是 **dp4a/MMQ**，另立项。

### 0.2 P11 已经把"为什么上不去"量化了

`reports/P11_Roofline性能模型.md` §4（独立于 B11 立项的建模）给出：

| prompt T | 实测 tok/s | 算力屋顶 tok/s | **利用率** |
|---|---|---|---|
| 132 | 612 | 3749 | **16.3%** |
| 572 | 616 | 3747 | **16.4%** |
| 1280 | 568 | 3744 | **15.2%** |

即 **prefill 只跑到算力屋顶的 16%** —— 而且三个长度上几乎恒定。
恒定这件事本身就是证据：**瓶颈不是访存、也不是长度，而是每字节权重要花掉的指令数**。

`docs/28` §2.2 的账更能说明问题：Q4_K 一个 super-block 是 **144 B**，
纯访存口径的预算是 **~0.66 μs**，而 unpack 256 个 nibble（shift/and/查 scale/乘加）
的整数运算串行度吃掉了余量 —— 我们用的是 **fp32 精确**路线，指令数比 dp4a 高一个量级。

### 0.3 参照系是存在的（本方案开工前刚核实）

曾经担心的问题是"没有 int8 激活的参照可对拍"。核实后**恰恰相反**：

| 路径 | 激活 | 证据 |
|---|---|---|
| llama.cpp **CUDA** Q4_K **decode** | **Q8_1** | `ggml/src/ggml-cuda/mmvq.cu:38` `vec_dot_q_cuda_t(const void*, const block_q8_1*, ...)`；`vec_dot_q4_K_q8_1` |
| llama.cpp **CUDA** Q4_K **prefill**（小批） | **Q8_1** | MMQ 用 `block_q8_1_mmq`；`ggml_cuda_should_use_mmq` 在 `ne11 < MMQ_DP4A_MAX_BATCH_SIZE` 时为真 |
| llama.cpp **CPU** Q4_K | **Q8_K** | 项目文档里"Q8_K"说法的来源 |

⇒ **llama.cpp 的 CUDA Q4 路径一直在量化激活**；我们那条 **fp32 精确反量化**路线才是这条对拍里的"异类"。
所以 B11 不是在"发明一条无法验证的路线"，而是**向参照靠拢**。

> ⚠️ 由此**订正一处文档错误**：`docs/27` §3 第 4 条与 `docs/28` §2.2 写「Q4_K×Q8_K」，
> CUDA 路径实际是 **Q8_1**（Q8_K 是 CPU 路径）。方向性结论（"激活也量化"）没错。

## 2. 现状与数据（已核实源码）

### 2.1 我们现在的 prefill 路径

`cpp/src/gpu_model.cu`：

- **多列 gemv**（`gemv_*_mc`，`MAX_MC = 16`）：权重读一次、算 16 列。
- Q4_K/Q6_K 走 `gpuq::gemv_q4k/gemv_q6k`（`gpu_quants.cu`）：**fp32 精确反量化**后与
  fp32 激活做浮点点积。
- 整套验收建立在"**每个优化都必须过同一份对拍**"上（`docs/27` §2），
  B8a 的多列 kernel 与逐 token 路径是 **id-identical** 的（`test_b8` 的
  `B8a batch-prefill parity (4 lengths, id-identical)`）。

### 2.2 为什么 fp32 激活上不去

- 每读 144 B 的 Q4_K super-block，要做 **256 个 nibble 的 unpack**（shift/and/查 scale/乘加），
  而 dp4a 一条指令吃掉 4 个 int8 MAC ⇒ **指令数差约一个量级**。
- P11 的实测证实：三个 prompt 长度上利用率恒为 **~16%**（与长度无关 ⇒ 非访存问题）。

### 2.3 要改的边界

| 组件 | 现在 | B11 之后 |
|---|---|---|
| Q4_K/Q6_K **prefill** | fp32 激活 + 精确反量化 | **int8 激活 + dp4a**（目标） |
| Q4_K/Q6_K **decode** | fp32 激活（B7 已验证 102%/86%） | **不动**（见 §3.1） |
| **F16** 路线（prefill + decode） | fp32 激活 | **不动** |

## 3. 设计

### 3.1 ⭐ 范围控制：int8 激活**只用于量化路线，且只改 prefill**

这一条是本方案能否保住既有验收的关键，必须写在最前面：

1. **只在量化（Q4_K/Q6_K）路线上启用 int8 激活**。F16 权重 + fp32 激活本来就是自然的 F16 路线，
   没有理由动它。⇒ **`test_b4`（F16，440/440 逐 id 对拍）完全不受影响**。
2. **只改 prefill，不改 decode**。理由：decode 是**带宽受限**（P11 §0：AI≈1.0 vs 转折点 59.3），
   它的瓶颈是"读多少字节"，不是"每字节多少指令" —— 换 int8 激活对 decode 收益近零，
   却会**改变 decode 数值**、破坏 B7/B10 已建立的验收（40.4/62.5/119.4 那套数字全部作废）。
3. 于是受影响的验收只剩"同样改动的两次运行相比"那几条，它们**自动仍然成立**：
   - `test_b7` 本身就是 teacher-forcing（异路线），不要求 bit-exact
   - `test_b8` 的 `B8a parity` 比的是批量 prefill vs 逐 token —— 两条都走新路径
   - `test_b9` 的 LCP 逐字节、`test_b10` 的"池大小不改变输出"同样都是自比

> ⚠️ **会变的那个数字**：`docs/30` §6.3 与 `python scripts/p9_compare_radarinfher.py` 那条
> 「22 题 vs llama-server **Δ=+0.0000**」是在 Q4 上测的。改了 prefill 数值口径后**必须重测**，
> 并如实报出新的 Δ（预期不再是 0.0000）。**这是 D4 的一部分，不是回归失败。**

### 3.2 数值方案（**已定：B**，2026-10-10 确认）

三种候选，差别在"激活怎么量化"：

| 方案 | 做法 | 与 llama.cpp CUDA 的距离 | 代价 |
|---|---|---|---|
| **A. per-32 对称 int8** | 每 32 个激活一组，`scale = amax/127`，int32 dp4a 累加，组末乘回 `w_scale*a_scale` | 中（Q8_1 是**每 32 元素带 `d` 与 `s`** 两项，我们只带 `d`） | 实现最简 |
| **B. 对齐 Q8_1** | 每 32 元素带 `d`（缩放）与 `s`（元素和，供 w 的 offset 项用），与 llama.cpp 同构 | **最近** ⇒ D2 的一致率应最高 | 多一个 `s` 项；需要处理 Q4_K 的 `dmin` 偏置项 |
| **C. per-128/per-superblock** | 按 Q4_K 的 super-block 粒度量化激活 | 远（llama.cpp 是 per-32） | 精度更差但更省 |

**推荐 B**：`docs/28` §6.3 的整段分析都建立在"与我们对比的 llama.cpp 是同一条 Q4_K×Q8_1 路线"上，
选 B 才能让 D2 的"一致率应上升"成为一个**干净的可证伪判据**；选 A/C 则一致率的变化会被
"块大小不同"这个额外变量污染。

#### 3.2.1 方案 B 的确切语义（实现前先钉死，D1 层①对拍的就是它）

激活量化**逐 32 个连续值一组**，与 llama.cpp CUDA 的 `quantize_q8_1` 逐句对齐
（`ggml/src/ggml-cuda/quantize.cu:54`）：

```
amax = max_l |x_l|                         (fp32)
d32  = amax / 127.0f                       (fp32)
q_l  = (amax == 0) ? 0 : roundf(x_l / d32) (int8, round-half-away-from-zero)
d    = float(half(d32))                    ← 下游实际使用的 d
Σq   = Σ_l q_l                             (int32, 精确)
```

⚠️ **复刻一处 llama.cpp 的固有细节**：llama.cpp **用 fp32 的 `d32` 去量化**，
但**存进 block 的 `d` 是 fp16**，而 dot 里用的是**那个 fp16 的 `d`**。
我们照做 —— 这正是"对齐 Q8_1"的含义；换成全程 fp32 的 `d` 会更准但会偏离参照。

激活块布局（本项目的定义，**不**照抄 llama.cpp 的 36 B 布局）：

```c
struct BlockQ8_1 {   // 40 B, 4 字节对齐
    float   d;       // = float(half(amax/127))，dot 里实际用的缩放
    int32_t sum_q;   // = Σ q_l，精确整数
    int8_t  qs[32];
};
```

> 为什么用 `int32 sum_q` 而不是 llama.cpp 的 `half s`：mmvq 路径的 offset 项本来就是用
> **dp4a 现算** `Σq`（`0x01010101` 与被量化的激活做 dp4a，见 `vecdotq.cuh:520`），
> 所以存精确整数**与参照同值**，还省掉 kernel 里的一次 warp 归约。

权重侧的贡献式（Q4_K，逐 super-block、逐 sub-block，`j` 升序）：

```
sumf_d_b = Σ_j  f32(d8[b*8+j]) * f32(dot1_j * sc_j)      // dot1_j = Σ_l nib_l*q_l (int32)
sumf_m_b = Σ_j  f32(d8[b*8+j]) * f32(dot2_j * m_j)       // dot2_j = Σ_l q_l = sum_q (int32)
part_b   = f32(d4) * sumf_d_b - f32(dmin) * sumf_m_b
y        = Σ_b part_b                                     // b 升序累加
```

Q6_K 同构，只是"scale 组"是 **16 个值**（`sc` 为 int8，`q ∈ [-32,31]`）：

```
sumf_b = Σ_g f32(d8[block(g)]) * f32(sc_g * dot_g)       // dot_g = Σ_{16} q6_l*q8_l
part_b = f32(d6) * sumf_b
y      = Σ_b part_b
```

**浮点运算一律显式 round-to-nearest 的"先乘后加"**（CUDA 侧用 `__fmul_rn`/`__fadd_rn`
禁止 FMA 收缩），这样 NumPy 的 `a*b + c`（float32）能与之**逐位一致** —— B5 的
3.3 亿值逐位 EXACT 就是这么做的。

**累加顺序即判据**：NumPy 参考与 kernel 必须用**同一个括号化**；D1 要求逐位相等，
"顺序不同所以差一点"不被接受（否则层①就失去了定位能力）。

### 3.3 kernel 形态

- **prefill 主路径**：把 `gemv_*_mc`（多列、N≤16）中量化权重的那条换成
  `int8 激活 × Q4_K 权重 → dp4a → int32 累加`。
  sm_89 有原生 dp4a（`__dp4a`），也有 MMA；**先用 dp4a**（实现简单、语义好对齐），
  MMA 作为后手（要处理 fragment 布局，收益需实测）。
- 激活量化本身是一个额外的 pass（每 32 元素求 amax → scale → 量化），
  在 prefill 的 chunk 内做一次、被 16 列复用 ⇒ 摊薄可忽略。
- Q6_K 同法（`d` 用 fp16→fp32）。

### 3.4 ⭐ 三层对拍方法论（本方案的核心，因为它换的是**数值路线**）

> 背景：`docs/27` §2 的方法论是"每个优化都必须过同一份对拍"。但**换数值路线**时，
> "与 llama.cpp 逐 id 相同"在数学上不再可能（块大小、舍入、累加顺序都不同）。
> 项目在 B5/B7 已经处理过一次这种情况（换成了 teacher-forcing）。这里把方法固定成三层：

| 层 | 比什么 | 能否 bit-exact | 判据 | 项目先例 |
|---|---|---|---|---|
| **① 路由内自证** | CUDA kernel ↔ **独立的 NumPy 参考实现**（我们自己的 int8 语义） | ✅ **能** | 逐元素一致（浮点部分 bit-exact，量化部分 EXACT） | B1 GGUF 双实现逐字节；B5 反量化 自研 vs libggml **3.3 亿值逐位 EXACT** |
| **② 路由间对齐** | 与 llama.cpp CUDA（Q8_1）的 teacher-forcing 一致率 | ❌ 不可能 | **≥ 49/50**（不低于 fp32 激活路线）。⭐ 两边都量化激活 ⇒ 距离应变小；**若下降就是我们的 bug** | B5/B7 的 49/50 |
| **③ 质量代价** | 22/200 题、口径 v3，与 fp32 激活路线对照 | — | 报**退化量**（不设硬阈值，由你判断是否可接受） | 量化退化 **−0.035**（`docs/19`） |

**为什么①必须存在**：②③都只告诉你"偏了多少"，只有①能告诉你"偏在哪里"。
而①成立的前提是"把语义写清楚两遍"（一次 Python 一次 CUDA）—— 这恰好是本项目最擅长的验证形态。

### 3.5 A/B 开关（让性能与质量都能同 session 配对）

新增环境变量 `RADAR_Q4_FP32_ACT=1`：**强制走旧的 fp32 激活路径**。
⇒ 新旧两条路可以在**同一次 session 内交替跑**，满足 §5.9 的"配对测量"要求，
也是 D3 与 D4 的测量前提（`RADAR_NO_PREFIX_CACHE` 在 B10b 已经用过这个模式）。

## 5. 风险

| 风险 | 等级 | 应对 |
|---|---|---|
| **精度不够**：int8 激活使 teacher-forcing 一致率下降 | 高 | 这正是 D2 要测的。若 < 49/50：先按 §3.4① 定位是"量化实现错"还是"精度天然更差"；后者就如实报，并考虑方案 A（per-32 但不带 `s`）是否反而更稳 |
| **性能没到 1000**：dp4a 仍撞发射墙 | 中 | dp4a 是 4 路整数 MAC，指令数比 fp32 精确路线少约一个量级，理论上应显著超过 16%；若仍不达，下一步是 **MMA（int8 tensor core）**，但那要处理 fragment 布局 |
| **改坏了别的路径** | 中 | §3.1 的范围控制：F16 不动、decode 不动 ⇒ 受影响的验收面很小 |
| **数值方案选错，返工** | 中 | 先做 §3.2 的决策再写码；方案 B 有明确参照可对，A/C 会让 D2 的判据变浑 |
| **`test_b7` 的既有数字失效** | 低 | 预期之内：一致率与 tok/s 都会变。**必须重测并更新 `docs/28`**，不能留着旧数字 |
| 22 题 Δ 不再是 0.0000 被误读为回归 | 中 | 在 `docs/33`/`test_b9` 相关处注明"该数字是 Q4 fp32 激活口径下的结论，B11 后作废重测" |

## 6. 明确不做（防范围蔓延）

- **decode 路径的 int8 激活**（§3.1 第 2 条：decode 是带宽受限，收益近零、代价是作废全部既有 decode 验收）。
- **F16 路线的激活量化**（无意义，且会破坏 `test_b4` 的 440/440）。
- **int8 tensor core（MMA）**：先做 dp4a；MMA 作为 D3 未达标时的后手，不预先并入。
- **KV 量化**（`docs/33` §10.3 已定性：另一条改数值口径的路线，另立项）。
- 权重侧的进一步量化（Q3/Q2）：与本项无关，且 8 GiB 下没必要。
